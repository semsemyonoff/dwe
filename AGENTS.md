# Repository Guidelines

## Project Structure & Module Organization

This is a Go CLI project named `dwe` (Dev Workspace Engine). DWE is a developer tool for local development environments running on Docker. Typical flow: a developer installs DWE locally, enters a project with DWE configuration, runs `dwe`, and the CLI detects the current directory as a DWE project. From there it automates deploy/setup steps, orchestrates Docker services, and runs project commands.

`AGENTS.md` is the canonical file; `CLAUDE.md` is a symlink to it. Edit `AGENTS.md` — overwriting `CLAUDE.md` will break the symlink.

The executable entrypoint lives in `cmd/dwe`; most code is under `internal/`. Tests sit next to code as `*_test.go`; fixtures live in package-local `testdata/`.

`internal/` is organized in three layers (layering rules — `depguard` activation pending):

- **`internal/cli/`** — cobra command tree. Composition root in `cli/root.go`; no domain logic. One subpackage per command subtree, each exporting `NewCmd(groupID, flags)`.
- **`internal/core/`** — domain logic, subclustered into `project/` (what is a DWE project), `execution/` (pipeline engine), `workflow/` (deploy / lifecycle / reset / snapshot / setup), `usercommands/` (declarative command system), `validate/` (static project validation), `docs/` (embedded docs subsystem), `ui/` (domain-aware renderers — sink layer, imported only by `cli/`), and `notify/` (desktop notifications).
- **`internal/shared/`** — leaf infrastructure (`docker/`, `git/`, `daemon/`, `lock/`, `pathsafe/`, `envfile/`, `render/`, `liveui/`, `tpl/`, `i18n/`, `version/`, `prompt/`, `promptcache/`).

**Per-package responsibilities, invariants, and cross-package contracts live in [`docs/internals/packages.md`](docs/internals/packages.md).** Read the relevant section there before modifying any package — it captures non-obvious load-bearing details (sequencing, sentinels, allowlists, render ordering, cross-cutting CLI patterns like JSON output mode and display-string localization) that are expensive to re-derive from the code.

## Configuration Documentation

Keep behavior and docs aligned. DWE user-facing documentation lives in `docs/reference/` (schemas) and `docs/guides/` (task-oriented recipes):

- `docs/reference/config/` — project config files (`workspace.md`, `services/`, `docker.md`, `info.md`, `styles.md`), pipelines (`deploy/`, `lifecycle.md`, `reset.md`, `conditions.md`, `state/`), user commands (`commands/`), user-level notifications and i18n (`notifications.md`, `i18n.md`), snapshot workflows (`snapshot.md`), project readiness checks (`validate.md`), setup wizard (`setup.md`), and command browser settings (`ui.md`).
- `docs/reference/render/` — render subcommands (env / ide / ai / git) and template-pack mechanics (manifest schema, local overrides, collision policies).
- `docs/guides/` — task-oriented recipes and integrations (e.g. Starship prompt). Each page solves a concrete user-facing problem that cuts across the reference. Translations live in `docs/i18n/<lang>/guides/`.

The live CLI surface (flag list, subcommand tree) is `dwe --help`; no per-command markdown files are kept in the repo.

Update these when changing schemas, commands, service toggles, deploys, or hooks.

For AI agent orientation, `dwe docs llms-txt` emits a compact llms.txt index (project context, services, commands, and docs pointers) designed for AI agents to load once and navigate the project — run it inside a project for a project-aware snapshot, or outside one for a generic dwe reference.

### Documentation site (`web/`)

`web/` holds an Astro Starlight site published to GitHub Pages (`https://semsemyonoff.github.io/dwe/`) by `.github/workflows/docs.yml` on every push to `main` that touches `docs/**` or `web/**`. It is a **build-time mirror** of `docs/reference/` + `docs/guides/` (and the `docs/i18n/ru/` mirror); `docs/internals/` and `docs/plans/` are excluded. The canonical `docs/*.md` stay byte-identical — **edit `docs/` (and the root `README.md`), never the generated tree.** `web/scripts/sync-docs.mjs` transforms `docs/` → the gitignored `web/src/content/docs/` (title-from-H1, link rewriting to base-aware slugs / GitHub blobs for internals & non-docs repo files, i18n remap), derives the sidebar from each `index.md`'s ordered TOC, and builds the per-locale root landing pages from `README.md` / `docs/i18n/ru/README.md` (images they reference are copied into the gitignored `web/public/`). Preview with `cd web && npm run dev`; `npm test` covers the transform. Dangling `.md` links in `docs/` are degraded to plain text with a build warning (not a hard failure). No Go code is involved.

## Build, Test, and Development Commands

- `make build` runs `go mod tidy`, syncs `docs/` into `internal/core/docs/embedded/` (via `scripts/sync-embedded-docs.sh`), regenerates `internal/core/docs/content_hashes_gen.go` (via `scripts/gen-docs-content-hashes.sh`), cross-compiles the bridge shim into `internal/core/bridge/shimassets/bin/` via `scripts/build-shims.sh`, builds `./cmd/dwe`, and writes `bin/dwe`. Run `make build` (not `go build`) after editing docs under `docs/reference/`, `docs/guides/`, `docs/internals/`, or `docs/i18n/` — otherwise the embedded docs in the binary will be stale.
- `make test` / `make test-v` / `make test-race` run the test suite. They depend on both `embedded-docs` and `shims`, so the sync runs before tests every time. **Always use `make test*` — `go test ./...` directly will see an empty `internal/core/docs/embedded/` tree on a fresh checkout (it is gitignored and generated) and the docs-subsystem tests will fail.**
- `make lint` runs `golangci-lint` checks.
- `make tidy` updates `go.mod` and `go.sum`.
- `make clean` removes the built binary from `bin/`.

For focused work prefer `make embedded-docs` once, then `go test ./internal/cli` or `go test ./internal/core/usercommands/... -run TestName` directly — the sync is idempotent and the embedded tree persists until the next `docs/` edit.

## Coding Style & Naming Conventions

Follow `.editorconfig`: Go files use tabs with width 4; YAML, JSON, and shell files use two spaces. Run `gofmt` and `goimports`; `golangci-lint` enforces `errcheck`, `govet`, `staticcheck`, `revive`, `gocritic`, and `modernize`.

## Testing Guidelines

Prefer table-driven tests for command parsing, config resolution, Docker orchestration, and runner behavior. Keep fixtures in `testdata/` and avoid developer-specific Docker state unless the package isolates it. Every behavior change should update nearby `*_test.go` coverage. Run `make test` before opening a PR.

## Commit & Pull Request Guidelines

Recent history uses conventional-style commits such as `feat(commands): ...`, `fix(commands): ...`, `docs(config): ...`, and `refactor(commands)!: ...`. Keep the scope tied to the package or user-facing area, and use `!` only for breaking changes. Pull requests should include a summary, verification commands, linked issues when applicable, and screenshots or terminal output when changing CLI presentation.

## Critical Patterns

Recurring traps and load-bearing contracts. Each pattern has a full write-up in `docs/internals/packages.md` — read it before touching the relevant area.

- **JSON output mode (`--output json`, `--pretty`)** — every read-only command must route through `cmdctx.WriteData[T]` / `cmdctx.WriteError`; typed errors (`cmdctx.Err`, `cmdctx.ErrWrap`) carry exit codes and serialize to a `{"error":{…}}` envelope on stderr. Diagnostic commands (`validate`) are the exception — they emit diagnostics-as-data even at severity=error. See § CLI cross-cutting behaviors.
- **Display-string localization** — never read `def.Description` directly in display code; thread `rflags.I18n` (or `i18n.TranslatorOrNop` on completion paths) and use the typed `store.*` helpers. Storage/hashing sites stay English. See § CLI cross-cutting behaviors.
- **Binary accessors** — never read `cfg.Binaries.*` fields directly. Always use nil-safe accessors `config.DweBin / DockerBin / ShellBin / GitBin / MmdcBin`. Deploy/condition step `when:` predicates intentionally use hardcoded `sh` for portability. See § Core — Foundation (`project/config/`).
- **YAML loader strictness** — deploy / reset / lifecycle / command-file / manifest loaders use `yaml.Decoder.KnownFields(true)` (unknown fields are hard errors). Info / styles / docker / localconfig / topology loaders use lenient `yaml.Unmarshal`. Match the surface when adding loaders. Exception: the four strict pipeline loaders (`LoadLifecycleConfig`, `loadProjectDeployConfigDecode`, `loadServiceDeployConfigDecode`, `loadDeployConfigDecode`) also tolerate `io.EOF` from an all-comment/empty file — empty doc is treated as absent, so the built-in default applies unchanged. This was introduced to support `dwe init`'s inert scaffold overrides. Mirror this pattern when adding new strict pipeline loaders. See § Core — Foundation.
- **Strict root + `vars:` sandbox + top-level `update:`** — the merged 3-layer project root (`workspace.yml` → `defaults.yml` → `local.yml`) is strict: `LoadConfig` rejects any top-level key outside `allowedRootKeys` (`internal/core/project/config/workspace.go`) with a hard error + `vars:` hint, iterated **per layer** so the message names the offending file. `allowedRootKeys` includes `schema_version` as reserved forward-compat metadata — tolerated at the root but not interpreted (not a separate exception path; it is a plain allowlist member). **Adding a new formalized top-level config field requires adding its key to `allowedRootKeys`** — otherwise every fixture using it load-fails. The check runs per layer alongside the `binaries:`/`tools:` legacy rejections (which keep their own migration messages and now also name the offending file) and BEFORE `__configPath`/`injectServicesIntoRaw`. Legacy `binaries:`/`tools:` are rejected per layer too, so a layer carrying only such a key (dropped by `deepMerge`) still surfaces its migration error. Arbitrary free-form values have exactly one home: the `vars:` block (strict at root, unvalidated/nestable inside; resolves via `Raw` dot-paths — `${vars.db.x}`, `from: vars.db.x`). The self-update policy is the formalized top-level `update: { mode: on|off }` block (`UpdateConfig`, 3-layer merged, `EffectiveMode()`: nil→off, empty→on); `LoadConfig` value-validates `mode ∈ {on,off}`. It **replaced** `lifecycle.yml`'s `run.update` (enabling update no longer blanks `run` phases); the consumer reads `cfg.Update.EffectiveMode()`, and `git.Decide` is binary `ModeOn`/`ModeOff` only. See § Core — Foundation (`project/config/`) and § `internal/shared/git/`.
- **Validation framework** — per-domain validators register via `All()` functions and run independently per-file; `env/` + `checks/` also participate in preflight, others only in `dwe validate`. Severity-gated exit codes. See § Core — Validation.
- **Preflight + locks ordering** — lifecycle commands (`deploy run` / `run` / `stop` / `restart` / `reset run`) MUST call `preflight.Run` BEFORE any side effect, then call `lock.AcquireProjectLocks(baseDir)` for project mutations (acquires `deploy.lock` then `snapshot.lock` alphabetically; releases in reverse). Never call `lock.Acquire` directly on either lock file. CLI command sites should acquire via `cmdctx.AcquireProjectLocksOrReport(baseDir, w)` — it wraps `lock.AcquireProjectLocks`, prints `*lock.ProjectLockHeldError` via the writer and returns it unchanged (preserving exit code 2), and wraps any other error as `acquiring project locks: %w`. Do not re-roll the 9-line acquire-and-report block. **Live-alt-screen exception:** a call site that runs while a full-screen TUI is up (the in-TUI vars edit overlay) must NOT print to stderr mid-frame — use `cmdctx.AcquireProjectLocksSilent(baseDir)` instead, which has the *identical* error contract but writes nothing, and surface the returned lock-held error in-TUI (a status flash). Docs subsystem and `dwe logs` are read-only — no preflight, no locks. See § `preflight/` and § `shared/lock/`.
- **Config-load helpers** — after `config.LoadConfig`, the plain `loading config: %w` wrap is centralized in `config.LoadConfigOrWrap(workspacePath)` (reachable from both `cli/` and `core/workflow/`); use it instead of re-wrapping. The typed `cmdctx.ErrWrap("project_invalid_config")` contract is a **separate** path — do not collapse it into `LoadConfigOrWrap`. For the docker-config load-or-empty idiom (`os.ErrNotExist` → `&DockerConfig{}`, else `loading docker config: %w`), use `config.LoadDockerConfigOrEmpty(baseDir, cfg)`. See § Core — Foundation (`project/config/`).
- **Grouped commands: no child `PersistentPreRunE`** — cobra does NOT chain `PersistentPreRunE`; a child's hook *replaces* the parent's. For grouped subtrees needing shared setup, use a per-`RunE` loader helper (see `loadStatusContext` in `cli/status/`). See § `internal/cli/status/`.
- **Completion path safety** — cobra's hidden `__complete` path bypasses `PersistentPreRunE`. `ValidArgsFunction` callbacks must call `cmdctx.CompletionConfigPath(flags, cmd)` before any config-dependent work; on any error return empty completions + `cobra.ShellCompDirectiveNoFileComp` silently. See § `cmdctx/`.
- **Section renderer signature contract** — `internal/core/project/stack/` collectors and `internal/core/ui/render/` renderers return strings (and per-row errors where applicable); `internal/cli/` is the single writer to stdout/stderr. Do not pass `io.Writer` into `stack/` or `ui/render/`. See § `internal/core/ui/render/`.
- **Pipeline defaults** — `workspace/deploy.yml`, `workspace/reset.yml`, and each section of `workspace/lifecycle.yml` are optional. Each has paired `Default*Config()` + `Ensure*Config(loaded) (cfg, defaulted bool)` constructors. The bool drives `cmdctx.EmitDefaultNotice` (suppressed in JSON mode). Composition is full-replacement, **except** `EnsureStopConfig` which always prepends `autoReapPhase()`. See § Core — Workflow.
- **Single-block → multi-command sugar** — declarative command types like `type: daemon` expand at registry-load time into N virtual `CommandDef`s. Pattern: source command dropped from `byID`, synthetic group node `ensureGroup`'d, each synthetic carries `DerivedFrom*` + a `Source*Spec` pointer (`yaml:"-"`) for inspect. Registry expansion is config-blind. See § Core — User Commands.
- **`info.yml` auto-blocks** — `type: auto-urls` and `type: auto-hosts` items expand at *render* time, not load time. **Service iteration in renderers MUST go through `config.DeployOrder(...)` — never `range cfg.Services` directly** (map iteration is randomized → flaky golden tests). Adding new top-level fields to `service.yml` requires updating BOTH `allowedFieldsFor` in `internal/core/project/config/workspace.go` AND `servicesAllowedFields` in `internal/core/validate/config/workspace.go` — `service.yml` uses `KnownFields(true)` strict decode. See § `internal/core/ui/render/`.
- **Pending-state lifecycle** — `dwe services enable/disable` (without `--apply`) writes `local.yml` immediately and tracks deferred work in `state.Services.pending`. Pending writes are gated on `journalSnapshot.everDeployed` (see `loadJournalSnapshot` in `internal/cli/service/service_toggle.go`): any prior deploy attempt counts (StatusDeployed / StatusFailed / StatusInProgress / StatusPartial on any service, OR `state.Project.LastRun != nil`, OR `state.Project.Status != "" && != StatusNotDeployed`). Journal load errors default to `everDeployed = true` to avoid silently swallowing pending on a corrupt file — `AddPendingOps` then either repairs the file or hard-fails. The gate is closed only when there has been NO deploy attempt at all: in that case both the pending write and the "stack not running" banner are skipped (silent `local.yml`/`.env` update plus a one-line `run dwe deploy` hint after the plan). With `--apply` the docker probe still runs even when never-deployed, so a broken docker setup surfaces an early diagnostic. Toggle executor must use `ClearPendingOps` with a contributor-derived `clears` slice — NEVER `ClearPending` (would erase unrelated pending from other sessions). See § `workflow/deploy/journal/`.
- **Compose-bypass for per-service stop/reset/restart** — `dwe stop <name>` stops via `docker stop <containerName>` directly (compose overlay is filtered out for disabled services). `dwe restart <name>` restarts via `docker restart <containerName>` directly (also bypasses compose and lifecycle hooks; runs NO preflight, acquires NO project locks — lighter than the full-lifecycle restart; `ErrNoSuchContainer` surfaces as a user-facing "run `dwe deploy run` first" hint). `dwe reset run --service <name>` drives stop+remove through a synthetic `docker_stop_remove_container` builtin (NOT `stopServiceLocked`). Volume cleanup is opt-in via `docker_remove_project_volumes`. See § `internal/cli/lifecycle/`.
- **Per-service folder symmetry** — every service lives in `workspace/services/<name>/`; folder name = map key (no `name:` field). `service.yml` is required; `deploy.yml` / `reset.yml` are optional pipeline declarations valid for any service type. When adding a new file type to a service folder, add it to the `services_folder` validator in `internal/core/validate/config/`. See § `project/config/`.
- **Snapshot template scope gate** — `${snapshot.*}` resolves only inside snapshot workflow blocks. Three scope values (`SnapshotScopeNone`, `SnapshotScopeCreate`, `SnapshotScopeRestoreOrRemove`); `tpl.RenderCommand` calls `validateSnapshotScope` before `CompileVarSyntax`. Never add scope logic to `CompileVarSyntax` — it must stay pure-syntactic with no error path. See § `internal/shared/tpl/`.
- **Live view & state pointers** — the pipeline live view uses `bubbles/v2` models directly via `Model.View()` — never `tea.NewProgram`, `term.MakeRaw`, or terminal capability queries. Nine non-negotiable invariants are documented in `internal/shared/liveui/liveline.go`. See § `internal/shared/liveui/`.
- **Prompt hot path** — `dwe prompt` and `dwe prompt --check` bypass cobra entirely via an early dispatch in `cmd/dwe/main.go`. `internal/shared/prompt` deliberately does NOT use lipgloss (auto-downgrades to no-color when stdout is piped). The cobra command is `Hidden: true` (still works with `--help`/completion, just dropped from listings). See § `internal/shared/prompt/`.
- **Prompt cache contract** — `.dwe/prompt-cache.yml` (TTL 2 min) backs the prompt's stack-state icon. Authoritative writers: `dwe run` / `restart` (no arg) / `services …--apply` write `running`; `dwe stop` / `reset run` (no arg) write `stopped`; top-level `dwe status` writes the exact aggregated `stack.HealthState(h)`. Scoped mutations (`--service`, snapshot restore/rollback, `dwe deploy run`) **invalidate** via `promptcache.Remove`. `dwe prompt`'s own refresh only ever writes `running` — **never `stopped`** (no-downgrade rule: zero-result from `docker ps` is indistinguishable from a wrong-label filter); a confirmed zero-result is still *rendered* as stopped once the stale value is older than `staleTrustCap` (5× TTL = 10 min) — the rule bounds writes, not rendering. Layering: `shared/promptcache` is leaf (string in/out); `core/project/stack.HealthState(Health) string` does the enum→string mapping in `core/`. Cache writes are best-effort everywhere (`_ = promptcache.Write(...)`). See § `internal/shared/promptcache/`.
- **Docs subsystem read-only** — never call `lock.AcquireProjectLocks` from docs commands and never run preflight. Resolve locale directly via `i18n.ResolveLocale(flagLang, cfgLang, sysLang)` — NOT `rflags.Locale` (clamped to YAML store; wrong namespace for markdown). See § Core — Docs.
- **Two i18n namespaces** — `workspace/i18n/<lang>.yml` (YAML, command/UI strings — validated by `i18n/` validator domain) vs `docs/i18n/<lang>/reference/...` + `docs/i18n/<lang>/internals/...` (markdown, long-form docs — no validator). Different loaders, no merge. See § `internal/shared/i18n/`.
- **Local compose overlays** — `compose.extra` (project-wide) and `services.<name>.compose.extra` (per-service) are valid **only** in `workspace/local.yml`; all other layers (`workspace.yml`, `defaults.yml`, `service.yml`) hard-error with a pointer to `local.yml`. Both fields are `yaml:"-"` on the typed structs (`ComposeConfig.Extra`, `ServiceConfig.LocalComposeExtra`) and are **never** decoded via YAML — they are populated by post-decode injection from the local.yml raw map inside `LoadConfig`. Injection runs **before** `ResolveServiceExtends`. Do NOT add either field to `allowedFieldsFor()` or `servicesAllowedFields` — the strict decoder would treat them as structural service fields. See § Core — Foundation (`project/config/`).
- **Config render + generated-once values** — service configs materialize via the **render** subsystem (`internal/core/execution/templates/config/` `RenderConfigs` / `HarvestGenerated`), NOT the legacy copy mechanism (`service_configs_copy`, now deprecation-warned). Four load-bearing contracts: (1) **`${...}` substrate** — config templates render through `tpl.CompileVarSyntax`+`RenderContext` (the `${X}` shorthand, NOT `packcommon.TemplateData`/raw-`{{ }}` used by ide/ai/git); `${generated.<name>}` routes to `case "generated"` → `resolveGenerated .Generated` (lenient, absent→`""` like every other `${...}` resolver), `${services.<name>...}` exposes only the **curated `injectServicesIntoRaw` subset**. (2) **Render check-pairing** — pairing `service_configs_render_check` as the render step's `check:` forces it to re-run every deploy via the `hasCheck → Run` lever in `journal/decision.go` (template edits / store clears always apply); mirrors `service_configs_copy`+`service_configs_check`. (3) **Harvest not mint** — the engine is hermetic, so the *service* generates secrets (e.g. `php artisan key:generate`) and DWE reads them back via `pattern` (regex, capture group 1) into the `generatedstore` leaf (`.dwe/generated.yml`, mirrors `promptcache`), `SetIfAbsent` (write-if-absent); the `generated-missing <svc> <field>` predicate (re-splits its own two args — see § condition) gates the generate step. (4) **Run-render ordering IS the safety argument** — `renderConfigsForRun` runs only AFTER the deploy gate AND post-pull reload but BEFORE phases; `missingGeneratedKeys` skips a service's render (with a `dwe deploy run` hint) when any declared key is absent from the store, so a `reset --clear-generated` + `dwe run` never blanks secrets. `sharesExtendsParentHub` silently skips an `extends` child that inherited its hub dir from its parent — it is a byte-identical render alias whose generated values are minted under the PARENT's store key (no own `deploy.yml`/harvest), so the parent renders the shared hub and the alias must not be rendered separately (else a false missing-key skip warning fires); a child with its OWN `dir` still renders. `reset --clear-generated` clears the store only after the FULL reset succeeds **including** journal cleanup. New top-level `generated:` field needs BOTH allowlists; `render.config` is struct-enforced (no allowlist). See § Core — Execution (`templates/config/`), § `internal/shared/generatedstore/`, and § Core — Foundation (`project/config/`).
- **Diagnostic trace routing (`-v` / `--debug`)** — all diagnostic echo goes through the `internal/shared/trace` leaf (`trace.Command`/`Decision`/`Debugf`), **stderr only** — stdout (incl. `--output json`) stays clean. `trace` is a leaf imported by `docker`/`git`/the execution engine/preflight; only `cli/` calls `trace.Configure` + installs the slog handler (`installSlogHandler`, **only** at `LevelDebug` — `-v` never touches slog). Output destination resolves by a **three-level precedence at each emit**: (1) ctx-carried printer (`trace.WithLinePrinter`) set per parallel sub-step for correct attribution, beats (2) global active printer (`trace.SetPrinter` → restore stack) set by `PlainReporter.StartPipeline` to wrap `r.live.PrintlnDiag` — frames the line above the footer via `termOut` but writes the line **text to the diagnostics writer = `os.Stderr`** (set via `LiveLine.SetDiagWriter` in `NewPlainReporter`), NOT `r.live.Println` (which writes the screen/stdout). This keeps in-pipeline `-v`/`--debug` echoes off stdout, so `dwe run --debug 2>debug.log` actually captures them. Beats (3) the `Configure` fallback writer (`os.Stderr`, used outside any pipeline + in JSON mode). `LevelOff` is a zero-alloc early return → no overhead with no flags. Level: `--debug` OR truthy `DWE_DEBUG` → Debug; else `--verbose` → Verbose; **flag beats env** (`DWE_DEBUG` in `{"","0","false","no","off"}` is off). Verbose = command echoes + pipeline decisions; Debug adds read-only docker probes, timings/exit codes, compose env, and `slog.Debug` records (read-only `ps` probes are **Debug-only** — keep `dwe status -v` quiet). `trace.FormatCommand` is the single quoting source (lifted from the old `docker/compose.go` `formatCommand`/`quoteArg`) — compose error-wrap goldens must stay byte-identical to it. See § `internal/shared/trace/`.
- **Host bridge env contract & container command policy** — the bridge daemon force-sets `DWE_INVOKED_FROM=container` + `DWE_NONINTERACTIVE=1` on every forked `dwe` (client-sent values are stripped — these two are host-controlled only, which is what makes the policy unspoofable; `DWE_INVOKED_FROM` must NOT affect `--output json` shape). The daemon ALSO strips execution-hijacking variables from the client env before forking — the dynamic-loader families (`LD_*`, `DYLD_*`), shell-startup hooks (`BASH_ENV`, `ENV`, `SHELLOPTS`, `BASHOPTS`), `IFS`, and `PATH` — then force-sets `PATH` to the **daemon's own** PATH (`subprocessEnv` / `dangerousEnvNames` + `dangerousEnvPrefixes` in `internal/core/bridge/session.go`), and **replaces the host-identity set with the daemon's own values** — `HOME`, `USER`, `LOGNAME`, `TMPDIR`, `SSH_AUTH_SOCK` plus the `DOCKER_*` / `COMPOSE_*` / `XDG_*` families (`hostIdentityEnvNames` / `hostIdentityEnvPrefixes`; `daemonEnviron` is the test seam): a container `HOME` would otherwise break host docker-context resolution (CLI falls back to `/var/run/docker.sock`, absent on Docker Desktop / OrbStack macs). This is load-bearing: the forked host `dwe` resolves `docker`/`git`/`sh` by bare name, so a container-controlled `PATH`/`LD_PRELOAD` would otherwise be host code execution across the trust boundary — the command-policy allowlist restricts WHICH commands run, this env hardening keeps the allowlisted ones from running attacker binaries. Before exempting any var a bridged command needs forwarded, confirm it cannot influence process spawning. The container surface is **allowlist, default-deny** over top-level command names (`bridgeAllowedTopLevel` in `internal/cli/bridgepolicy.go`, single nested exception `bridge status`), gated inside the EXISTING root `PersistentPreRunE` — a NEW top-level command stays container-blocked (and hidden from help/completion in container context) until explicitly allowlisted. Inside the allowlisted `commands` subtree, USER commands are additionally **opt-in per command**: only a `bridge:` block (`enabled: true`, optional `services:` list of workspace service keys — matched through the caller's service-level `extends:` chain, children inherit the parent's rights; valid on the command or its file `group:` header, field-wise inheritance) makes one container-reachable — `registry.ApplyVisibility` resolves `CommandDef.BridgeHidden` from `DWE_INVOKED_FROM` + `DWE_BRIDGE_SERVICE` (overlay-injected per service, value = the workspace KEY; deliberately NOT in the strip set, container-reported hence advisory), `registry.list` filters it unconditionally, and `bridgeGuard` (`cli/command/bridgegate.go`) rejects direct invocation/inspect with `command_not_bridged`. The workflow runner NEVER consults `BridgeHidden` — bridged workflows execute non-bridged sub-commands host-side. `bridgeclient.StripEnv` is the single strip-set source — the shim and the daemon both filter through it. The overlay `.dwe/compose.bridge.yml` is dwe-owned machine state: regenerated (atomic, write-if-changed) by the `bridge.Prepare` hook on EVERY compose-up command and DELETED when no enabled service has bridge enabled — the overlay step ALWAYS runs; `composeFiles()` inserts it after app overlays, BEFORE local.yml (local keeps the last word), and stats it at CALL time. So a scenario runs alongside the working environment (and other projects holding those ports) with NO port config: `ports_free` preflight reads `services.<name>.ports` literally, and a project sourcing its compose host bindings from the same field (directly or via an `exports.env` `from: services.<name>.ports.<x>`) binds from it too — preflight and bind move together. Host ports + any `env.vars: auto` ports come from ONE `AllocatePorts` batch. `env.vars: auto` is now only the residual path for a compose port routed through a var NOT declared under `services.<name>.ports` (a `${vars.x}` in a service `ports:` is rejected at config load — the preflight reads a strict int). The one deploy retry (`hasAllocatedPorts`) re-allocates every port. **Stage 2** (`envtest/report.go` + `envtest/clean.go` + `internal/cli/test/clean.go`) added three more contracts worth trapping: (1) **reports are failure-only, before-teardown, fresh-ctx** — `Runner.collectReport` fires in `finish` only when `!req.Keep && status != StatusPassed` (a passed or kept run leaves no report), strictly BEFORE `teardown()` so containers are still alive and the pipeline log still on disk, under its own fresh `context.WithTimeout(context.Background(), reportTimeout)` — never the scenario's (possibly expired) deadline, mirroring teardown's own fresh-context rule. Collection is best-effort throughout (`os.RemoveAll`+`os.MkdirAll` the report dir for an honest overwrite, then `pipeline.log`/`compose-ps.txt`/`container-logs.txt` each independently warn-and-continue on failure) and never changes the scenario's pass/fail outcome. (2) **both captures (`compose ps` / `compose logs`) must use `BuildInternalArgs`, never `BuildArgs`; `ps` additionally passes `--all`** — plain `compose ps` is running-only and would drop exactly the crashed service a failure report exists to surface; `BuildArgs` would inject global ANSI flags plus the matching per-command `docker.yml` policy (`args.ps` for the ps capture — must not reshape a machine-readable table; `args.logs` for the logs capture, where a user `-f` would make report collection follow logs forever instead of capturing a bounded 200-line tail). Both captures read **combined stdout+stderr** (`captureCmdReal` uses `CombinedOutput`) — `docker logs` writes a non-TTY container's stderr to its own stderr, so an stdout-only capture would drop exactly the crash output. (3) **`dwe test clean` is strictly manifest-driven and never destroys by name pattern** — it per-scenario flock-guards live runs (`*lock.HeldError` → skip, teardown not attempted) and reuses stage-1 `Teardown` verbatim for the actual sweep; the `com.docker.compose.project` label scan for the `<base>-t-` prefix is report-only (surfaces `Orphans` with a "remove manually" note) and MUST NOT be wired to any destructive path — a `Teardown` failure during a sweep is recorded as `Failed` (not `Swept`) and drives a non-zero CLI exit, since a partial teardown masquerading as success would strand Docker state for the next `dwe test run` to trip over. Before any destructive sweep, `validateManifestIdentity` re-derives every path teardown touches from `(baseDir, scenario, runID)` — `copy_path == RunDir`, `bridge_dir == DefaultBridgeDir(copy)`, on-disk filename `== <scenario>-<runID>.yml`, `copy_path` lexically contained under `.dwe/tests/runs/` AND symlink-free via `pathsafe.CheckNoSymlinks` (a planted symlink parent would otherwise let `os.RemoveAll(copy_path)` escape the test root) — and pins `compose_project`: it must ALWAYS carry the normalised `-t-<scenario>-<runID>` infix (a floor the real dev env `<base>` never has), and when the disposable copy still loads it must EXACTLY equal the copy's OWN stamped docker identity (`copyComposeIdentity` = `config.ComposeProjectName` over the copy's `docker.yml`/`docker.local.yml`, the same value the copy's `compose down` resolves). The identity check is deliberately pinned to the COPY, **not** re-derived from the current root config: a run kept/failed before a `project.name`/`project.prefix` rename is still recoverable, since the copy carries the exact identity teardown uses — re-deriving from the changed root config would wrongly mark it `invalid manifest` and strand the copy + Docker resources. A gone/unloadable copy degrades to the infix floor alone. **Stage 3a** (per-step timeout + `workspace/tests/` validator + compose isolation scanner) added three more contracts worth trapping: (1) **per-step `timeout:` is general, opt-in, and body-only** — `config.DeployStep.Timeout` (string, parsed via `time.ParseDuration` at resolve time into `pipeline.ResolvedStep.Timeout time.Duration`; `< 0` is a resolve error, `0`/absent leaves the step byte-identically unbounded) is enforced in `executeStepBody` by wrapping ONLY the step body's `ExecAction` call in `context.WithTimeout` — the `check:` action stays on the shared, unwrapped `ctx` since it is a fast skip-predicate, not the work being bounded. A non-nil body error is relabelled `step %q timed out after %s` only when `ctx.Err() == nil && errors.Is(stepCtx.Err(), context.DeadlineExceeded)`, so an outer Ctrl+C cancellation is never mislabelled a timeout. The contract is honestly scoped to **ctx-honoring bodies**: `shell`/`dwe` subprocesses terminate via the existing `bindCancelTerm` SIGTERM+`WaitDelay` path and ctx-aware builtins return on deadline, but a body blocked on interactive input (e.g. `confirm` awaiting stdin) is NOT force-interrupted — the deadline fires but the goroutine stays blocked until input arrives (accepted, documented limitation). Parallel substeps need no extra plumbing — each substep is its own `ResolvedStep` flowing through the same `executeStepBody` path. (2) **compose isolation scanner is a policy-light leaf** — `config.ScanComposeIsolation(cfg, projectRoot) []IsolationFinding` (`internal/core/project/config/compose_scan.go`) parses `cfg.ComposeFiles()` with a narrow YAML struct (no `diag`/`validate` import) and flags constructs that bypass Docker-Compose project-name scoping. Each `IsolationFinding` carries an intrinsic `Blocking bool` — `true` for `KindContainerName`/`KindRawHostPort` (real collisions with the working environment; port detection covers short+long compose syntax, single literal or literal range host ports matching `^\d+(-\d+)?$`, strips a `/tcp`|`/udp` suffix, ignores `${...}`-interpolated tokens, and explicitly does NOT flag IPv6 bracketed hosts `[::1]:8080:80`), `false` for `KindNamed*`/`KindExternal*` (shared-resource hazards) — severity policy lives entirely in the two callers, not the scanner; an unreadable/malformed compose file is skipped silently (advisory only, real parse errors surface via `dwe validate`/`docker compose`). (3) **`internal/core/validate/tests/` is validate-only, never preflight** — `dwe validate tests` (`Domain()=="tests"`, `ID()=="scenarios"`) reuses `envtest.LoadScenario` (covers name normalisation for free via `ValidateScenarioName`) then renders + resolves ALL of a scenario's steps **once** as a single synthetic `config.DeployPhase{Name:"tests"}` via `pipeline.ResolvePhaseSteps` — matching runtime's `runSteps` exactly, so it catches duplicate top-level step names (`checkUniqueStepNames`) that a per-step validation pass would miss. The render context substitutes any `env.vars` entry whose value is the literal `auto` with a placeholder host port (the only magic value in the schema) so a templated strict-int param renders validly WITHOUT masking a genuinely-bad concrete param elsewhere — deliberately not a blanket `${...}`-in-raw downgrade heuristic. Isolation findings from `ScanComposeIsolation` always surface as `SeverityWarning` here (the runner is the tier that treats `Blocking` as fatal). The runner's own gate (`envtest` prepare phase, before the `dwe validate` subprocess spawns) fails a scenario on any `Blocking` finding via `finish()` (teardown still runs, no deploy subprocess spawned) unless `--skip-isolation-check` downgrades everything to warnings. **Stage 3b** (parallel scenarios + aggregated live reporter) added four contracts worth trapping: (1) **the `Progress` seam is UI-free and nil-guarded** — `RunRequest.Progress func(phase envtest.ProgressPhase)` (nil → no-op, guarded at the top of `RunScenario` exactly like `Warn`) fires a coarse typed-string phase enum (`PhasePreparing`/`PhaseValidating`/`PhaseDeploying`/`PhaseDeployRetry`/`PhaseRunningSteps`/`PhaseCollectingReport`/`PhaseTearingDown`) at each phase's natural start; `PhaseCollectingReport` fires ONLY inside the `collectReport != nil && !req.Keep && status != StatusPassed` branch and `PhaseTearingDown` ONLY when teardown actually runs (not under `--keep`). `envtest` stays UI-free (layering preserved) — the CLI owns the phase→label mapping. (2) **the port lease set is process-lifetime by design** — `ports.go` holds a package-level `leaseMu sync.Mutex` + `leasedPorts map[int]struct{}` of every port ever returned by `AllocatePorts`; a harvested port already leased is skipped (close listener, listen again) and every returned port is registered, closing the intra-process TOCTOU two concurrent batches otherwise hit. Leases are **never released** (`dwe test` is short-lived, dozens of ports max); a bounded attempt count (`allocateAttemptsPerBatch = 100 + 20*n`) guards a pathological loop with an exhaustion error. The one deploy retry gets fresh ports for free (the failed attempt's ports stay leased). Cross-process TOCTOU stays covered by the copy's `ports_free` preflight + the retry. `resetLeases()` is the test-only isolation helper (`t.Cleanup(resetLeases)`). (3) **parallel goroutines MUST never return errors into the errgroup** — orchestration lives in the CLI (`internal/cli/test/run.go`, plain `errgroup.Group` + `SetLimit(effective)`, NOT `WithContext` — sibling scenarios must not cancel each other); each goroutine writes `slots[i]` in original index order and ALWAYS returns nil (a `RunScenario` error is a per-scenario `StatusError` outcome, exactly as the sequential path does), so a failing scenario never cancels its siblings. First statement per goroutine is `if ctx.Err() != nil { return nil }` (matching the sequential `break` on Ctrl+C); nil slots (never-started) are compacted after `Wait`, keeping text/JSON output deterministic regardless of completion order. (4) **the aggregated display engages ONLY at effective N>1 — N=1 stays byte-identical** — `effective = min(parallel, len(names))`; `effective <= 1` runs the existing sequential streaming loop untouched (exact full-match output goldens pin this). At `effective > 1` in text mode a `runLiveStatus` (`internal/cli/test/livestatus.go`) wraps one `liveui.LiveLine` block (one sticky row per scenario via `SetBlockRowPending`/`SetBlockRowRunning`/`SetBlockRowFinal`, `visibleRows = max(1, min(len(names), termHeight−3))`, overflow scenarios report via framed `Println`); non-TTY mode branches EXPLICITLY on disabled state in `Started`/`Finished` for EVERY scenario (the block methods are silent no-ops when disabled, so a piped/CI run would otherwise show nothing until the final report). `jsonReporterFactory` was renamed **`silentReporterFactory`** and now serves BOTH JSON mode and the parallel text path (per-scenario deploy/pipeline output → copy run log only); JSON mode NEVER builds a display and keeps warnings suppressed. Per-scenario warnings at N>1 route `[<scenario>] warning: …` through the display's `PrintlnDiag` (bytes land on stderr).
