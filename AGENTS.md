# Repository Guidelines

## Project Status & Compatibility Policy

**Devbox is in active pre-release development.** There are no external users, no released versions, and no third-party projects depending on `schema_version`, command names, config keys, dot-path templates, file layouts, or any other surface. Backwards compatibility is **not** a constraint when choosing a design.

What this means in practice when proposing or evaluating changes:

- Pick the design that will be the most flexible and practical **after the first release**. The goal is to avoid breaking changes later, not to avoid breaking changes now.
- Do not introduce `schema_version` bumps, deprecation paths, version gates, dual-loader fallbacks, alias shims, or `migrate-from-X` flags. There is nothing to migrate from.
- Do not preserve legacy field names "just in case." Rename freely. Restructure freely. Delete freely.
- Do not write back-compat code paths in loaders, validators, or template resolvers. One canonical form per concept.
- Internal call-site cascades from a rename or restructure are fine — fix them all in one PR. Mechanical refactors are cheap; carrying two parallel models is expensive.
- Live user projects sitting alongside this CLI in the monorepo are updated alongside CLI changes. Treat them as fixtures, not as compatibility constraints.
- The only exception: do not silently change behavior of an existing config in a way that produces *wrong* results without an error. If a config shape becomes invalid, the loader/validator must reject it with a clear message — not interpret it differently.

When in doubt: choose the shape that will be correct in the long run and update the world to match. Don't preserve the past.

## Project Structure & Module Organization

This is a Go CLI project named `devbox`. Devbox is a developer tool for local development environments running on Docker. Typical flow: a developer installs Devbox locally, enters a project with Devbox configuration, runs `devbox`, and the CLI detects the current directory as a Devbox project. From there it automates deploy/setup steps, orchestrates Docker services, and runs project commands.

`AGENTS.md` is the canonical file; `CLAUDE.md` is a symlink to it. Edit `AGENTS.md` — overwriting `CLAUDE.md` will break the symlink.

The executable entrypoint lives in `cmd/devbox`; most code is under `internal/`. Tests sit next to code as `*_test.go`; fixtures live in package-local `testdata/`.

`internal/` is organized in three layers (layering rules — `depguard` activation pending):

- **`internal/cli/`** — cobra command tree. Composition root in `cli/root.go`; no domain logic. One subpackage per command subtree, each exporting `NewCmd(groupID, flags)`.
- **`internal/core/`** — domain logic, subclustered into `project/` (what is a Devbox project), `execution/` (pipeline engine), `workflow/` (deploy / lifecycle / reset / snapshot / setup), `usercommands/` (declarative command system), `validate/` (static project validation), `docs/` (embedded docs subsystem), `ui/` (domain-aware renderers — sink layer, imported only by `cli/`), and `notify/` (desktop notifications).
- **`internal/shared/`** — leaf infrastructure (`docker/`, `git/`, `daemon/`, `lock/`, `pathsafe/`, `envfile/`, `render/`, `liveui/`, `tpl/`, `i18n/`, `version/`, `prompt/`).

**Per-package responsibilities, invariants, and cross-package contracts live in [`docs/internals/packages.md`](docs/internals/packages.md).** Read the relevant section there before modifying any package — it captures non-obvious load-bearing details (sequencing, sentinels, allowlists, render ordering, cross-cutting CLI patterns like JSON output mode and display-string localization) that are expensive to re-derive from the code.

## Configuration Documentation

Keep behavior and docs aligned. Devbox configuration documentation lives in `docs/reference/`:

- `docs/reference/config/` — project config files (`devbox.md`, `services.md`, `docker.md`, `info.md`, `styles.md`), pipelines (`deploy.md`, `lifecycle.md`, `reset.md`, `conditions.md`, `state.md`), user commands (`commands.md`), user-level notifications and i18n (`notifications.md`, `i18n.md`), snapshot workflows (`snapshot.md`), project readiness checks (`validate.md`), setup wizard (`setup.md`), and command browser settings (`ui.md`).
- `docs/reference/render/` — render subcommands (env / ide / ai / git) and template-pack mechanics (manifest schema, local overrides, collision policies).
- `docs/reference/cli/` — auto-generated CLI reference (regenerated by `devbox docs generate`).

Update these when changing schemas, commands, service toggles, deploys, or hooks.

For AI agent orientation, `devbox docs llms-txt` emits a compact llms.txt index (project context, services, commands, and docs pointers) designed for AI agents to load once and navigate the project — run it inside a project for a project-aware snapshot, or outside one for a generic devbox reference.

## Build, Test, and Development Commands

- `make build` runs `go mod tidy`, syncs `docs/` into `internal/core/docs/embedded/` (via `scripts/sync-embedded-docs.sh`), regenerates `internal/core/docs/content_hashes_gen.go` (via `scripts/gen-docs-content-hashes.sh`), builds `./cmd/devbox`, and writes `bin/devbox`. Run `make build` (not `go build`) after editing docs under `docs/reference/`, `docs/internals/`, or `docs/i18n/` — otherwise the embedded docs in the binary will be stale.
- `make test` / `make test-v` / `make test-race` run the test suite. They depend on `embedded-docs`, so the sync runs before tests every time. **Always use `make test*` — `go test ./...` directly will see an empty `internal/core/docs/embedded/` tree on a fresh checkout (it is gitignored and generated) and the docs-subsystem tests will fail.**
- `make lint` installs `golangci-lint` if missing, then runs checks.
- `make tidy` updates `go.mod` and `go.sum`.
- `make clean` removes the built binary from `bin/`.

For focused work prefer `make embedded-docs` once, then `go test ./internal/cli` or `go test ./internal/core/usercommands/... -run TestName` directly — the sync is idempotent and the embedded tree persists until the next `docs/` edit.

## Coding Style & Naming Conventions

Follow `.editorconfig`: Go files use tabs with width 4; YAML, JSON, and shell files use two spaces. Run `gofmt` and `goimports`; `golangci-lint` enforces `errcheck`, `govet`, `staticcheck`, `revive`, `gocritic`, and `modernize`.

## Testing Guidelines

Prefer table-driven tests for command parsing, config resolution, Docker orchestration, and runner behavior. Keep fixtures in `testdata/` and avoid developer-specific Docker state unless the package isolates it. Every behavior change should update nearby `*_test.go` coverage. Run `make test` before opening a PR.

## Commit & Pull Request Guidelines

Recent history uses conventional-style commits such as `feat(commands): ...`, `fix(commands): ...`, `docs(config): ...`, and `refactor(commands)!: ...`. Keep the scope tied to the package or user-facing area, and use `!` only for breaking changes. Pull requests should include a summary, verification commands, linked issues when applicable, and screenshots or terminal output when changing CLI presentation.

## Critical Patterns

Recurring traps and load-bearing contracts. Each pattern has a full write-up in `docs/internals/packages.md` — read it before touching the relevant area.

- **JSON output mode (`--output json`, `--pretty`)** — every read-only command must route through `cmdctx.WriteData[T]` / `cmdctx.WriteError`; typed errors (`cmdctx.Err`, `cmdctx.ErrWrap`) carry exit codes and serialize to a `{"error":{…}}` envelope on stderr. Diagnostic commands (`validate`) are the exception — they emit diagnostics-as-data even at severity=error. See § CLI cross-cutting behaviors.
- **Display-string localization** — never read `def.Description` directly in display code; thread `rflags.I18n` (or `i18n.TranslatorOrNop` on completion paths) and use the typed `store.*` helpers. Storage/hashing sites stay English. See § CLI cross-cutting behaviors.
- **Binary accessors** — never read `cfg.Binaries.*` fields directly. Always use nil-safe accessors `config.DevboxBin / DockerBin / ShellBin / GitBin / MmdcBin`. Deploy/condition step `when:` predicates intentionally use hardcoded `sh` for portability. See § Core — Foundation (`project/config/`).
- **YAML loader strictness** — deploy / reset / lifecycle / command-file / manifest loaders use `yaml.Decoder.KnownFields(true)` (unknown fields are hard errors). Info / styles / docker / localconfig / topology loaders use lenient `yaml.Unmarshal`. Match the surface when adding loaders. See § Core — Foundation.
- **Validation framework** — per-domain validators register via `All()` functions and run independently per-file; `env/` + `checks/` also participate in preflight, others only in `devbox validate`. Severity-gated exit codes. See § Core — Validation.
- **Preflight + locks ordering** — lifecycle commands (`deploy run` / `run` / `stop` / `restart` / `reset run`) MUST call `preflight.Run` BEFORE any side effect, then call `lock.AcquireProjectLocks(baseDir)` for project mutations (acquires `deploy.lock` then `snapshot.lock` alphabetically; releases in reverse). Never call `lock.Acquire` directly on either lock file. Docs subsystem and `devbox logs` are read-only — no preflight, no locks. See § `preflight/` and § `shared/lock/`.
- **Grouped commands: no child `PersistentPreRunE`** — cobra does NOT chain `PersistentPreRunE`; a child's hook *replaces* the parent's. For grouped subtrees needing shared setup, use a per-`RunE` loader helper (see `loadStatusContext` in `cli/status/`). See § `internal/cli/status/`.
- **Completion path safety** — cobra's hidden `__complete` path bypasses `PersistentPreRunE`. `ValidArgsFunction` callbacks must call `cmdctx.CompletionConfigPath(flags, cmd)` before any config-dependent work; on any error return empty completions + `cobra.ShellCompDirectiveNoFileComp` silently. See § `cmdctx/`.
- **Section renderer signature contract** — `internal/core/project/stack/` collectors and `internal/core/ui/render/` renderers return strings (and per-row errors where applicable); `internal/cli/` is the single writer to stdout/stderr. Do not pass `io.Writer` into `stack/` or `ui/render/`. See § `internal/core/ui/render/`.
- **Pipeline defaults** — `devbox/deploy.yml`, `devbox/reset.yml`, and each section of `devbox/lifecycle.yml` are optional. Each has paired `Default*Config()` + `Ensure*Config(loaded) (cfg, defaulted bool)` constructors. The bool drives `cmdctx.EmitDefaultNotice` (suppressed in JSON mode). Composition is full-replacement, **except** `EnsureStopConfig` which always prepends `autoReapPhase()`. See § Core — Workflow.
- **Single-block → multi-command sugar** — declarative command types like `type: daemon` expand at registry-load time into N virtual `CommandDef`s. Pattern: source command dropped from `byID`, synthetic group node `ensureGroup`'d, each synthetic carries `DerivedFrom*` + a `Source*Spec` pointer (`yaml:"-"`) for inspect. Registry expansion is config-blind. See § Core — User Commands.
- **`info.yml` auto-blocks** — `type: auto-urls` and `type: auto-hosts` items expand at *render* time, not load time. **Service iteration in renderers MUST go through `config.DeployOrder(...)` — never `range cfg.Services` directly** (map iteration is randomized → flaky golden tests). Adding new top-level fields to `service.yml` requires updating BOTH `allowedFieldsFor` in `internal/core/project/config/devbox.go` AND `servicesAllowedFields` in `internal/core/validate/config/devbox.go` — `service.yml` uses `KnownFields(true)` strict decode. See § `internal/core/ui/render/`.
- **Pending-state lifecycle** — `devbox services enable/disable` (without `--apply`) writes `local.yml` immediately and tracks deferred work in `state.Services.pending`. Toggle executor must use `ClearPendingOps` with a contributor-derived `clears` slice — NEVER `ClearPending` (would erase unrelated pending from other sessions). See § `workflow/deploy/journal/`.
- **Compose-bypass for per-service stop/reset** — `devbox stop <name>` stops via `docker stop <containerName>` directly (compose overlay is filtered out for disabled services). `devbox reset run --service <name>` drives stop+remove through a synthetic `docker_stop_remove_container` builtin (NOT `stopServiceLocked`). Volume cleanup is opt-in via `docker_remove_project_volumes`. See § `internal/cli/lifecycle/`.
- **Per-service folder symmetry** — every service lives in `devbox/services/<name>/`; folder name = map key (no `name:` field). `service.yml` is required; `deploy.yml` / `reset.yml` are optional pipeline declarations valid for any service type. When adding a new file type to a service folder, add it to the `services_folder` validator in `internal/core/validate/config/`. See § `project/config/`.
- **Snapshot template scope gate** — `${snapshot.*}` resolves only inside snapshot workflow blocks. Three scope values (`SnapshotScopeNone`, `SnapshotScopeCreate`, `SnapshotScopeRestoreOrRemove`); `tpl.RenderCommand` calls `validateSnapshotScope` before `CompileVarSyntax`. Never add scope logic to `CompileVarSyntax` — it must stay pure-syntactic with no error path. See § `internal/shared/tpl/`.
- **Live view & state pointers** — the pipeline live view uses `bubbles/v2` models directly via `Model.View()` — never `tea.NewProgram`, `term.MakeRaw`, or terminal capability queries. Nine non-negotiable invariants are documented in `internal/shared/liveui/liveline.go`. See § `internal/shared/liveui/`.
- **Prompt hot path** — `devbox prompt` and `devbox prompt --check` bypass cobra entirely via an early dispatch in `cmd/devbox/main.go`. `internal/shared/prompt` deliberately does NOT use lipgloss (auto-downgrades to no-color when stdout is piped). See § `internal/shared/prompt/`.
- **Docs subsystem read-only** — never call `lock.AcquireProjectLocks` from docs commands and never run preflight. Resolve locale directly via `i18n.ResolveLocale(flagLang, cfgLang, sysLang)` — NOT `rflags.Locale` (clamped to YAML store; wrong namespace for markdown). See § Core — Docs.
- **Two i18n namespaces** — `devbox/i18n/<lang>.yml` (YAML, command/UI strings — validated by `i18n/` validator domain) vs `docs/i18n/<lang>/reference/...` + `docs/i18n/<lang>/internals/...` (markdown, long-form docs — no validator). Different loaders, no merge. See § `internal/shared/i18n/`.

## Agent-Specific Instructions

Do not overwrite unrelated local changes. Keep command examples current with the `Makefile`. When changing CLI behavior, update tests and config docs.
