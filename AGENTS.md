# Repository Guidelines

## Project Status & Compatibility Policy

**Devbox is in active pre-release development.** There are no external users, no released versions, and no third-party projects depending on `schema_version`, command names, config keys, dot-path templates, file layouts, or any other surface. Backwards compatibility is **not** a constraint when choosing a design.

What this means in practice when proposing or evaluating changes:

- Pick the design that will be the most flexible and practical **after the first release**. The goal is to avoid breaking changes later, not to avoid breaking changes now.
- Do not introduce `schema_version` bumps, deprecation paths, version gates, dual-loader fallbacks, alias shims, or `migrate-from-X` flags. There is nothing to migrate from.
- Do not preserve legacy field names "just in case." Rename freely. Restructure freely. Delete freely.
- Do not write back-compat code paths in loaders, validators, or template resolvers. One canonical form per concept.
- Internal call-site cascades from a rename or restructure are fine — fix them all in one PR. Mechanical refactors are cheap; carrying two parallel models is expensive.
- Live user projects sitting alongside this CLI in the monorepo are updated alongside CLI changes. Treat them as fixtures, not as compatibility constraints.
- The only exception: do not silently change behavior of an existing config in a way that produces *wrong* results without an error. If a config shape becomes invalid, the loader/validator must reject it with a clear message — not interpret it differently.

When in doubt: choose the shape that will be correct in the long run and update the world to match. Don't preserve the past.

## Project Structure & Module Organization

This is a Go CLI project named `devbox`. Devbox is a developer tool for local development environments running on Docker. Typical flow: a developer installs Devbox locally, enters a project with Devbox configuration, runs `devbox`, and the CLI detects the current directory as a Devbox project. From there it automates deploy/setup steps, orchestrates Docker services, and runs project commands.

`AGENTS.md` is the canonical file; `CLAUDE.md` is a symlink to it. Edit `AGENTS.md` — overwriting `CLAUDE.md` will break the symlink.

The executable entrypoint lives in `cmd/devbox`; most code is under `internal/`. Tests sit next to code as `*_test.go`; fixtures live in package-local `testdata/`.

**Per-package responsibilities, invariants, and cross-package contracts live in [`docs/internals/packages.md`](docs/internals/packages.md).** Read the relevant section there before modifying any package — it captures non-obvious load-bearing details (sequencing, sentinels, allowlists, render ordering) that are expensive to re-derive from the code.

`internal/` is organized in three layers (layering rules — `depguard` activation pending; see `docs/internals/packages.md` § Dependency Rules):

- **`internal/cli/`** — cobra command tree. Composition root in `cli/root.go`; no domain logic. 17 subpackages: `cmdctx/` (shared `RootFlags` bundle); per-command-subtree packages `command/`, `completion/`, `compose/`, `deploy/`, `docker/`, `docs/`, `info/`, `prompt/`, `render/`, `service/`, `shell/`, `snapshot/`, `status/`, `validate/`, `version/`; `lifecycle/` (multi-export Go-domain grouping for `run`/`stop`/`restart`/`reset`, sharing a `preflightRun` test seam). Each subpackage exports a single `NewCmd(groupID, flags)` (or the `lifecycle.NewRunCmd`/`NewStopCmd`/`NewRestartCmd`/`NewResetCmd` set, or `completion.AttachInstallUninstall(parent, flags)`); siblings primarily communicate via `cmdctx/`; two documented pre-existing exceptions (`cli/service/` → `cli/deploy.RunHelper`, `cli/lifecycle/{run,restart}.go` → `cli/info.Run`) are tracked in `docs/internals/packages.md`.
- **`internal/core/`** — domain logic, subclustered:
  - **`core/project/`**: `project/`, `config/`, `user/` (imported as `userpkg`), `local/` (imported as `localpkg`), `services/`, `stack/`
  - **`core/execution/`**: `pipeline/`, `condition/`, `filesgate/`, `builtin/`, `templates/`, `preflight/`
  - **`core/workflow/`**: `deploy/`, `lifecycle/`, `reset/`, `snapshot/`, `setup/`
  - **`core/usercommands/`**: `model/`, `loader/`, `registry/`, `resolve/`, `runtime/`
  - **`core/validate/`**: framework + subdomains (`config/`, `templates/`, `commands/`, `env/`, `checks/`, `linters/`, `i18n/`, `snapshot/`, `setup/`, `diag/`)
  - **`core/docs/`**: embedded docs subsystem (embed, render, mermaid, tui, export)
  - **`core/ui/`**: domain-aware renderers (`ui/`, `ui/ask/`, `ui/cmdbrowser/`, `statusview/`, `statustui/`) — sink layer, imported only by `cli/`
  - **`core/notify/`**: desktop notifications + hookpoints in `cli/deploy`, `workflow/lifecycle/RunRun`, `usercommands/runtime/RunCommand`
- **`internal/shared/`** — leaf infrastructure: `docker/`, `git/`, `daemon/`, `lock/`, `pathsafe/`, `envfile/`, `render/`, `liveui/`, `tpl/`, `i18n/`, `version/`, `prompt/`

## Configuration Documentation

Keep behavior and docs aligned. Devbox configuration documentation lives in `docs/reference/`:

- `docs/reference/config/` — project config files (`devbox.md`, `services.md`, `docker.md`, `info.md`, `styles.md`), pipelines (`deploy.md`, `lifecycle.md`, `conditions.md`, `state.md`), user commands (`commands.md`), user-level notifications config (`notifications.md`), snapshot workflows (`snapshot.md`), project readiness checks (`validate.md`), and command browser settings (`ui.md`).
- `docs/reference/render/` — render subcommands (env / ide / ai / git) and template-pack mechanics (manifest schema, local overrides, collision policies).
- `docs/reference/cli/` — auto-generated CLI reference (regenerated by `devbox docs generate`).

Update these when changing schemas, commands, service toggles, deploys, or hooks.

For AI agent orientation, `devbox docs llms-txt` emits a compact llms.txt index (project context, services, commands, and docs pointers) designed for AI agents to load once and navigate the project — run it inside a project for a project-aware snapshot, or outside one for a generic devbox reference.

## Build, Test, and Development Commands

- `make build` runs `go mod tidy`, syncs `docs/` into `internal/core/docs/embedded/` (via `scripts/sync-embedded-docs.sh`), regenerates `internal/core/docs/content_hashes_gen.go` (via `scripts/gen-docs-content-hashes.sh`), builds `./cmd/devbox`, and writes `bin/devbox`. Run `make build` (not `go build`) after editing docs under `docs/reference/`, `docs/internals/`, or `docs/i18n/` — otherwise the embedded docs in the binary will be stale.
- `make test` / `make test-v` / `make test-race` run the test suite. They depend on `embedded-docs`, so the sync runs before tests every time. **Always use `make test*` — `go test ./...` directly will see an empty `internal/core/docs/embedded/` tree on a fresh checkout (it is gitignored and generated) and the docs-subsystem tests will fail.**
- `make lint` installs `golangci-lint` if missing, then runs checks.
- `make tidy` updates `go.mod` and `go.sum`.
- `make clean` removes the built binary from `bin/`.

For focused work prefer `make embedded-docs` once, then `go test ./internal/cli` or `go test ./internal/core/usercommands/... -run TestName` directly — the sync is idempotent and the embedded tree persists until the next `docs/` edit.

## Coding Style & Naming Conventions

Follow `.editorconfig`: Go files use tabs with width 4; YAML, JSON, and shell files use two spaces. Run `gofmt` and `goimports`; `golangci-lint` enforces `errcheck`, `govet`, `staticcheck`, `revive`, `gocritic`, and `modernize`.

## Testing Guidelines

Prefer table-driven tests for command parsing, config resolution, Docker orchestration, and runner behavior. Keep fixtures in `testdata/` and avoid developer-specific Docker state unless the package isolates it. Every behavior change should update nearby `*_test.go` coverage. Run `make test` before opening a PR.

## Commit & Pull Request Guidelines

Recent history uses conventional-style commits such as `feat(commands): ...`, `fix(commands): ...`, `docs(config): ...`, and `refactor(commands)!: ...`. Keep the scope tied to the package or user-facing area, and use `!` only for breaking changes. Pull requests should include a summary, verification commands, linked issues when applicable, and screenshots or terminal output when changing CLI presentation.

## Key Patterns

- **JSON output mode (`--output json`)**: The global `--output text|json` and `--pretty` flags live on `cmdctx.RootFlags`. Every read-only command emits naked data on stdout; errors (when `--output json`) go as a JSON envelope on stderr via `cmdctx.WriteError`. Use the generic `cmdctx.WriteData[T](flags, cmd, data, textFn)` helper — it dispatches to compact/pretty JSON or calls `textFn(data)` for text. Return typed errors with `cmdctx.Err(code, msg)` / `cmdctx.ErrWrap(code, err)` and chain `.WithHint(...)` / `.WithDetail(key, val)` — `WriteError` will serialize them into `{"error":{"code":…,"message":…,"hint":…,"details":{…}}}`. JSON mode side-effects (set in `PersistentPreRunE`): `NO_COLOR=1`, `SilenceErrors=true`, `SilenceUsage=true`. `runRoot` (no subcommand) checks `flags.Output == "json"` at entry and delegates to `runRootJSON` — never emits brand header, help text, or pending banner in JSON mode. DTO convention: snake_case field names, RFC3339 timestamps, durations in seconds and sizes in bytes as numbers; wrap top-level arrays in a keyed object (`{"apps":[...]}`, `{"snapshots":[...]}`); use `omitempty` on optional inner fields but NOT on the wrapper key (always present). Stderr in JSON mode is reserved for the JSON error envelope — gate any informational `warning:` writes behind `flags.Output != "json"`. Diagnostic commands (`validate` and its subdomains) are the exception to the envelope rule: they always emit diagnostics-as-data on stdout, even at severity=error; the exit code conveys severity (0 ok/info, 1 error or warning+`--strict`), and `validationFailedError` carries `ExitCode()` so `main.go` short-circuits the envelope path. TUI-capable commands (`status`, future `cmdbrowser`) must force TUI off when `flags.Output == "json"`. Exit codes via `cmdctx.ExitCodeFor(err)`: 0 success, 1 runtime, 2 usage (e.g. `invalid_output`, `--pretty` without `--output json`). Use `cli.NewRootCmdWithFlags()` (not `NewRootCmd()`) when you need the `*RootFlags` pointer; the no-flags constructor exists for the 14+ legacy test call sites only.
- **Completion helpers**: Cobra's hidden `__complete` path bypasses `PersistentPreRunE`, so `ValidArgsFunction` callbacks cannot rely on the project being resolved. All such callbacks must call `cmdctx.CompletionConfigPath(flags, cmd)` (in `internal/cli/cmdctx/completion.go`) before any config-dependent work. On any error (`ErrNotFound`, schema, bad `-c` path) return empty completions and `cobra.ShellCompDirectiveNoFileComp` silently.
- **Binary accessors**: Never read `cfg.Binaries.*` fields directly (they were removed in favor of user-config). Always use nil-safe accessors: `config.DevboxBin(cfg)`, `config.DockerBin(cfg)`, `config.ShellBin(cfg)`, `config.GitBin(cfg)`, `config.MmdcBin(cfg)`. These accessors check `cfg.userConfig.BinaryOverride(name)` first (loaded via `userpkg.Load()` at `LoadConfig` time); fallback to PATH default if nil or override not found. Deploy/condition step `when:` predicates intentionally use hardcoded `sh` (not `ShellBin`) for portability. `internal/shared/git` (probe/pull) and `internal/core/project/stack.CollectGitWorkspace` both take the binary as a parameter so callers thread `config.GitBin(cfg)` explicitly.
- **YAML loader strictness**: Deploy / reset / lifecycle loaders (`LoadDeployConfig`, `LoadResetConfig`, `LoadLifecycleConfig`), the command-file parser (`model.ParseCommandFile`), and template manifest loaders (via shared `manifest.Load()`) use `yaml.Decoder.KnownFields(true)` — unknown fields are hard errors. Other loaders (info, styles, docker, localconfig, topology) use lenient `yaml.Unmarshal`. When adding loaders, match the surface: strict for user-edited pipeline / command / manifest YAML; lenient for internal or non-step config. For command files, `loader.LoadCommandFile` (parse + validate) is the runtime entry point; `loader.ParseCommandFile` is for validators that want categorised diagnostics — never use it at runtime.
- **Validation framework**: `internal/core/validate` defines `Validator`, `Diagnostic`, and `Registry` for static project validation. Validators run independently per-file to surface all issues regardless of main-config load success. Registry dispatches by scope (domain + optional ID); diagnostics are sorted deterministically and rendered via `RenderDiagnosticsTable`. Exit code is severity-gated: errors → 1, warnings with `--strict` → 1, otherwise 0. Per-domain validators live in `internal/core/validate/{config,templates,commands,env,checks,linters,snapshot,setup}` and register via `All()` functions (no `init()` side effects). `env/` and `checks/` also participate in preflight; `snapshot/` is only assembled by the `validate snapshot` subcommand and `devbox validate`. `setup/` uses a function-arg form — `valsetup.All(setupCfg, setupErr, setupPath)` — to avoid an import cycle (`internal/core/workflow/setup` imports `internal/core/validate/env`); it is assembled by `runDeployMenu` and `runValidate` before displaying the deploy menu or running full validation.
- **Live view & state pointers**: The pipeline live view (`internal/shared/liveui` + `internal/core/execution/pipeline/plain.go`) uses `bubbles/v2` models directly via `Model.View()` — never `tea.NewProgram`, `term.MakeRaw`, or terminal capability queries. Nine non-negotiable invariants enforced by `LiveLine` / `LiveBlock` are documented in `internal/shared/liveui/liveline.go`; read them before touching the live view. Deploy lock and state-journal invariants (atomic write-temp + rename, stale-PID reclaim, config-hash invalidation before skip decisions) are documented in `docs/reference/config/state.md`.
- **Grouped commands: no child `PersistentPreRunE`**. Cobra does NOT chain `PersistentPreRunE` — a child's hook *replaces* the parent's entirely, silently dropping the root's project resolution and schema validation. For grouped subtrees (e.g. `status apps` / `status tools` / `status infra` / `status deploy`) that need shared setup beyond what root provides, use a per-`RunE` loader helper instead. The `status` group uses `loadStatusContext(flags, errW)` (`internal/cli/status/status.go`) as the canonical example: called once from each subcommand's `RunE` to load cfg/journal/tracked/topology on demand. Same constraint applies to any new command group added on top of the root.
- **Section renderer signature contract**: `internal/core/project/stack/` section renderers return strings (and per-row errors where applicable) rather than writing to `*render.Writer`. The `internal/cli` layer is the single writer of stdout/stderr (`cmd.OutOrStdout()` / `cmd.ErrOrStderr()`), so `internal/core/ui/` stays format-agnostic and `internal/core/project/stack/` stays output-agnostic. When adding a new status section: collector in `stack/` returns data, `ui.Render*` returns a string, command layer composes and writes. Do not pass `io.Writer` into `stack` or `ui` render functions.
- **Single-block → multi-command sugar**: a declarative command type (e.g. `type: daemon`) can expand at registry-load time into N virtual `CommandDef`s. Pattern: the source command is **dropped** from `byID` (not runnable), a synthetic group node is `ensureGroup`'d so the tree renders, each synthetic carries `DerivedFromDaemon = <base>` (or analogous field) plus a `Source*Spec` pointer (yaml:"-") with the original block's structural fields for inspect. Inspect renders a `derived from: <kind> <base>` line + a typed subsection from the `Source*Spec` so users see the source without runtime round-tripping `with:`. Registry expansion is config-blind (`LoadRegistry(baseDir)` has no `*config.DevboxConfig`) — anything config-derived resolves at builtin runtime via `ectx.Config`; anything param-derived is expressed as `${param.<name>}` template literals so `renderBuiltinWith` resolves at command dispatch.
- **Pipeline defaults**: `devbox/deploy.yml`, `devbox/reset.yml`, and both sections of `devbox/lifecycle.yml` are optional. Each has a paired `Default*Config()` Go constructor (returns a freshly-allocated struct — callers may mutate safely) and an `Ensure*Config(loaded) (cfg, defaulted bool)` wrapper: when the file or section is absent, `Ensure*` returns the default + `true`; when present, it returns the user config + `false`. The bool is the sole signal for whether the CLI should emit the info line (`cmdctx.EmitDefaultNotice(cmd, flags, pipeline, file)`) — the notice is suppressed in `--output json` mode. Composition model: the returned config fully replaces the absent user config (no partial merge). Exception: `EnsureStopConfig` always prepends `autoReapPhase()` to the returned phases regardless of defaulting — the `_auto_reap_daemons` phase is a system invariant, not part of the default content. The lifecycle package uses `lifecycle.DefaultedPipeline` (typed string enum: `DefaultedRun`, `DefaultedStop`) and `RunContext.OnDefaultUsed` / `StopContext.OnDefaultUsed` callbacks so the workflow layer stays free of cobra imports; `RunRestart` propagates `ctx.OnDefaultUsed` into `stopCtx` so restart fires the callback for both legs. The CLI deploy entrypoint overwrites `cfg.Deploy` with the Ensure result so downstream resolvers always see a non-nil config when the default fires.
- **Project-lock seam**: All project-mutating commands — lifecycle (`deploy run` / `run` / `stop` / `restart` / `reset`) and all snapshot subcommands (`create` / `restore` / `rollback` / `remove` / `pack` / `unpack`) — must call `lock.AcquireProjectLocks(baseDir)` from `internal/shared/lock/project.go`, never `lock.Acquire` directly on either lock file. The helper acquires `deploy.lock` first then `snapshot.lock` (alphabetical) and releases in reverse order; violating this order risks deadlock. Lifecycle commands acquire the locks *after* preflight so `type: command` checks do not run under operation locks.
- **Snapshot template scope gate**: `${snapshot.*}` resolves only inside snapshot workflow blocks. The gate is enforced by `validateSnapshotScope(expr, scope)` in `internal/shared/tpl/render_command.go`, called from `RenderCommand` before `CompileVarSyntax`. `CompileVarSyntax` has no error path and must stay pure-syntactic — never add scope logic there. Three scope values: `SnapshotScopeNone` (zero value, default — compile error on any `${snapshot.*}`), `SnapshotScopeCreate` (all keys except `created_at`), `SnapshotScopeRestoreOrRemove` (all keys). Use `snapshot.BuildSnapshotVars(...)` to build the map; inject via `RunContext.Render.Snapshot` + `.SnapshotScope`.
- **Linters domain (`linters.*`)**: external linters (`shellcheck`, `hadolint`, plus `type: generic`) live in `internal/core/validate/linters/` and run **only** in `devbox validate`, never in preflight (preflight answers "can we run?", not "is the code clean?"). Per-adapter autodetect: when no entry exists for a known built-in, synthesize one with defaults; missing default `bin:` on PATH → silent skip; explicit `bin:` missing → Warning. `bin:` is load-time enforced as a bare command name (no path separators) — `validate.yml` ships with the repo, so absolute/relative paths in `bin:` would be a code-execution vector. Built-in adapters declare `ReservedFlags()` for parser-load-bearing flags (`--format` / `-f`); user `flags:` are rejected at load time across **every** argv form (`--format=gcc`, `["--format", "gcc"]`, `-f tty`, **`-fgcc` short-attached**). Linters use `GroupValidator` for parallel fan-out: `sync.WaitGroup` + buffered-channel semaphore (NOT `errgroup.WithContext` — one linter's failure must not cancel siblings); per-goroutine `recover()` converts panics to Error; concurrency capped at `MaxLinterConcurrency = runtime.NumCPU()`. Two diagnostic buckets per linter — `operationalDiags` (timeout, truncation, parse failure, missing-path, panic) is **never** clamped; `findings` is clamped from above by `entry.Severity` — so `severity: info` cannot silence runtime failure signals. Per-linter bounds: `DefaultLinterTimeout = 5m`, `MaxLinterOutputBytes = 50 MB` (combined stdout+stderr via `boundedWriter`). All three bounds + concurrency cap are package-level `var` (test-seamed). Missing **default** paths drop silently; missing **user-configured** paths emit a Warning.
- **Preflight + env/checks domains**: lifecycle commands (`deploy run`, `run`, `stop`, `restart`, `reset run`) invoke `preflight.Run(ctx, cfg, cmdRegistry, baseDir, stage, skip, errOut)` BEFORE any side effect on Docker, git, or the filesystem — including `lock.Acquire`, git probe/pull, and container stops. cfg and `loadCommandRegistry` are hoisted above the preflight call; registry-load failure is tolerated (nil registry → unknown-command diagnostics). Two new validate domains back this: `env.*` (seven hardcoded probes in `internal/core/validate/env/`: docker_bin / docker_daemon / docker_compose / git_bin / shell_bin / project_perms / ports_free — config-blind beyond the nil-safe `config.{Docker,Git,Shell}Bin` accessors; `ports_free` additionally reads `cfg.Services[*].Ports` for declared host ports and queries `docker ps` once to distinguish our compose containers from foreign conflicts, and self-skips on `Stage == "stop"`) and `checks.*` (declarative entries from `devbox/validate.yml`, loaded by `config.LoadValidateConfig` strict-decode, dispatched via `internal/core/validate/checks/`). Single parse point: the caller (`runValidate` or `preflight.Run`) calls `LoadValidateConfig` once and threads the result into `validate.Context.{ValidateCfg, ValidateCfgWarnings, ValidateCfgLoadErr}`; the `config.validate` validator is the SOLE emitter of load-error diagnostics (silent on `os.ErrNotExist`, one error diagnostic otherwise). Stage filtering happens at *assembly time* via `checks.AllForStage` — `validate.Registry` only filters via `MatchScope` (domain / domain+id). `--skip-preflight` (local flag on the four lifecycle commands; NOT on `rootFlags`) is a true bypass: prints the skip notice and runs NO validators, because `type: command` checks invoke arbitrary user scripts. `type: command` checks are restricted at load time to user commands of `type: shell` or `type: script`, and are run with `SkipConfirm=true` / `NonInteractive=true` / `SkipNotify=true` / discarded stdout / captured stderr.
- **Per-service folder symmetry**: Every service lives in `devbox/services/<name>/`. The `service.yml` file is the declaration (required). The `deploy.yml` and `reset.yml` files are optional pipeline declarations (any service type may have them). The folder name is the service key — there is no `name:` field inside the files. `LoadServices(baseDir)` enumerates `devbox/services/*/` and uses the folder name as the map key. `LoadServiceFolder(baseDir, name)` loads a single folder. A missing `devbox/services/` directory returns an empty map (not an error). When adding a new file type to a service folder, add it to the `services_folder` validator in `internal/core/validate/config/` or it will surface as a "unknown file in service folder" warning.
- **Pending-state lifecycle**: `devbox services enable/disable` (without `--apply`) writes `local.yml` immediately but defers the apply step. The deferred work is tracked in `state.Services.pending` as a list of `PendingOp{Kind, Services}` entries. Journal helpers: `AddPendingOps` (atomic batch write), `ClearPendingOps` (atomic batch clear), `ClearPendingForKind`, `ClearPendingForServices`, `ReplaceServiceWithPending` (atomic clear-deployed + write-pending for per-service reset). Clear rules: `devbox restart` clears the `restart` op only; `devbox deploy run` (full) clears the `deploy` op only; `devbox deploy run --service <name>` removes `<name>` from the deploy op's service list; `devbox reset run` (full) calls `journal.Remove` (entire state file deleted — reset means nothing is deployed). The toggle executor must use `ClearPendingOps` with a contributor-derived `clears` slice — NEVER `ClearPending` (it would erase unrelated pending from other sessions). The status banner is rendered by `ui.RenderPendingBanner(p *journal.PendingApply)`.
- **Compose-bypass for per-service stop/reset**: `devbox stop <name>` stops a service container via `docker stop <containerName>` directly (`docker.StopContainer`), bypassing compose. This is required because after a service is disabled, its compose overlay is filtered out of the rendered project, so `docker compose stop <name>` would fail. The container name is resolved via `daemon.ResolveContainerName`. The compose-bypass stop is safe as long as the container name is stable — it is, because `container:` in `service.yml` is the canonical name. `StopService(ctx, StopServiceDeps, name)` is the public entry point (runs preflight + acquires lock); `stopServiceLocked(ctx, StopServiceDeps, name)` is the lock-already-held variant. The per-service reset path (`devbox reset run --service <name>`) does NOT call `stopServiceLocked` — it drives stop **and removal** through a synthetic `container` phase backed by the `docker_stop_remove_container` engine builtin (`internal/core/execution/builtin/containers_stop_remove.go`) so the operation flows through the standard `pipeline.RunWithOptions` reporter, log handling, and `ErrSilent` path. The reset path additionally appends a synthetic `files` phase (`remove_paths` builtin) when the service declares `dir:` and the directory exists, then the user's `services/<name>/reset.yml` phases. Both synthetic phases are `Untracked: true` so they don't appear in `[N/M]` counters or journal entries; the builtins emit their own success lines. Volume cleanup is NOT automatic — users opt in via `docker_remove_project_volumes` in their per-service `reset.yml`. `devbox stop <name>` intentionally only stops (no removal) — stop semantics differ from reset semantics.
- **Runtime log inspection**: `devbox logs <service>` is the canonical entry point for inspecting container logs by service name — use it instead of `docker logs <container>` directly, since it handles container-name resolution via `daemon.ResolveContainerName`. Supports `--tail N`, `--since DUR|TS`, `--follow`, and `--output json` (NDJSON, one `{"ts","stream","msg"}` per line). Read-only: no lock, no preflight. Implementation: `internal/cli/logs/`.
- **Prompt hot path**: `devbox prompt` and `devbox prompt --check` bypass cobra entirely via an early dispatch in `cmd/devbox/main.go` to keep per-shell-prompt cost minimal. The `internal/shared/prompt` package duplicates the accent-color resolution from `internal/core/ui/styles.go` deliberately — it cannot use lipgloss because lipgloss auto-downgrades to no-color when stdout is piped (which it is, when starship invokes `devbox prompt`). A cobra `prompt` command exists in `internal/cli/prompt/prompt.go` for `--help` discoverability only — its RunE is unreachable in normal startup.
- **`info.yml` auto-blocks**: `type: auto-urls` and `type: auto-hosts` items expand at *render* time inside `renderInfoItem` (`internal/core/ui/info.go`), not at load time. The `InfoItem` carries a `Source*Spec` pointer per the daemon-style sugar pattern (yaml:"-", populated by `InfoItem.UnmarshalYAML` dispatching on `type:` and using a `type alias InfoItem` shadow to avoid infinite recursion on the flat-field decode pass). `LoadInfoConfig` stays config-blind; `RenderInfo` does NOT take a topology parameter — auto-block renderers call `config.DeployOrder(cfg, types)` directly (folder-key space; `ParseTopologyFromFiles` is intentionally unused because it returns compose-name space). `stack.DeployOrder` is a thin shim over `config.DeployOrder`; `ui` cannot import `stack` because `stack` imports `ui`. When `devbox/info.yml` is missing, `LoadInfoConfig` returns `DefaultInfoConfig()` — a synthesized config with a urls section + hosts section, both with `Source*Spec` pointers populated directly (UnmarshalYAML does not run on Go-constructed configs). Service `icon`, `info.title`, `info.primary_host`, `info.primary_port`, and `info.paths` are display-only fields read by these renderers (and by status/cmdbrowser for `icon` in a planned follow-up). **Service iteration in renderers MUST go through `config.DeployOrder(...)` — never `range cfg.Services` directly**, because Go map iteration is randomized and would produce flaky golden tests. **`renderBlock` in `internal/core/ui/info.go` was tightened to drop empty `renderInfoItem` output from `contentCount`** so `hide_on_empty` sections collapse correctly when their auto-block renders to `""`. **Adding new top-level fields to `service.yml` requires updating BOTH `allowedFieldsFor` in `internal/core/project/config/devbox.go:607` AND `servicesAllowedFields` in `internal/core/validate/config/devbox.go:112`** — service.yml uses `KnownFields(true)` strict decode.
- **Display-string localization**: Every call site that renders user-command descriptions, parameter descriptions, group names, or doc-generator section headers to stdout must use the `i18n.Translator` interface (via `rflags.I18n` in command context). Thread the translator and locale explicitly to renderer functions; never read `def.Description` directly in display code. Use typed helpers: `store.CommandDescription(locale, id, fallback)`, `store.ParamDescription(locale, id, paramName, fallback)`, `store.GroupTitle/Description(locale, id, fallback)`, `store.T(locale, uiKey, fallback)`. Completion-path safety: `__complete` paths bypass `PersistentPreRunE`, so wrap via `i18n.TranslatorOrNop(rflags.I18n)` before helper calls. Storage/hashing sites (journal, deploy steps, phase definitions) stay English — never introduce locale to `internal/core/workflow/deploy/journal/hash.go` or to any persistence layer.
- **Docs subsystem read-only**: `internal/core/docs/` (embed, render, mermaid, tui, export) are all read-only operations. Never call `lock.AcquireProjectLocks` from docs commands and never run preflight (read-only commands don't need preconditions). Docs work without `devbox.yml` (project root detection is optional). Docs commands resolve locale **directly** via `i18n.ResolveLocale(flagLang, cfgLang, sysLang)` — do NOT use `rflags.Locale` (clamped to YAML store; wrong namespace for markdown translations).
- **Two i18n namespaces**: `devbox/i18n/<lang>.yml` (YAML, command/UI strings — existing, validated by `i18n/` domain) vs `docs/i18n/<lang>/reference/...` + `docs/i18n/<lang>/internals/...` (markdown, long-form docs — new, no validator yet). Different loaders, different namespace prefixes (no merge). Docs content-hash header format: first line matching `^>\s*Translated from:\s*\S+\s*@\s*([0-9a-f]{12,64})\s*$` contains the hash of the English source file (computed at build time by `gen-docs-content-hashes.sh`, 12-char `sha256` prefix). Staleness check compares manifest hash against header hash; manifest absence → no banner.
- **Mermaid chain composition**: Mermaid rendering is a **three-stage fallback chain** built via `mermaid.Chain(FileCache, MmdcRenderer, Disabled{})`. `cfg.Docs.Mermaid ∈ {"auto", "mmdc", "off"}` determines which renderers to include: `off` → `Disabled{}`; `auto` → full chain with silent skip of missing mmdc; `mmdc` → full chain with error-placeholder on missing mmdc. Cache wraps underlying renderer: writes `<key>.png` (key includes source + theme + width + mmdc version), does LRU eviction on mtime, deduplicates concurrent same-key misses via singleflight. Timeout is per-render (10s), not cumulative. Text-level mermaid preprocess replaces ` ```mermaid ` blocks with placeholder text BEFORE glamour invocation (glamour has no extender hook).
- **Content-hash manifest fallback**: The generated `internal/core/docs/content_hashes_gen.go` file is **committed** (not gitignored) so fresh checkouts get a real manifest. If the map is empty or an entry is absent, the staleness check returns `false` (no banner) — this is the safety net for tests that `go test` without `make build`, and for historical snapshots. Manifest values are `sha256(en-file bytes)[:12]` (content-based, NOT git commit SHA — stable across rebases and checkouts). Build-time generator: `make build` runs `scripts/gen-docs-content-hashes.sh` which walks `docs/reference/` and `docs/internals/`, computes hashes with `sha256sum`/`shasum -a 256` + `cut`, outputs sorted Go map literal, pipes through `gofmt -s`. CI guard: `git diff --exit-code internal/core/docs/content_hashes_gen.go` after `make build` rejects PRs where regeneration was skipped. (The `internal/core/docs/embedded/` tree is gitignored and regenerated on every `make build`/`make test*`, so it is not part of the diff guard.)

## Agent-Specific Instructions

Do not overwrite unrelated local changes. Keep command examples current with the `Makefile`. When changing CLI behavior, update tests and config docs.
