# Repository Guidelines

## Project Structure & Module Organization

This is a Go CLI project named `dwe` (Dev Workspace Engine). DWE is a developer tool for local development environments running on Docker. Typical flow: a developer installs DWE locally, enters a project with DWE configuration, runs `dwe`, and the CLI detects the current directory as a DWE project. From there it automates deploy/setup steps, orchestrates Docker services, and runs project commands.

`AGENTS.md` is the canonical file; `CLAUDE.md` is a symlink to it. Edit `AGENTS.md` — overwriting `CLAUDE.md` will break the symlink.

The executable entrypoint lives in `cmd/dwe`; most code is under `internal/`. Tests sit next to code as `*_test.go`; fixtures live in package-local `testdata/`.

`internal/` is organized in three layers (layering rules — `depguard` activation pending):

- **`internal/cli/`** — cobra command tree. Composition root in `cli/root.go`; no domain logic. One subpackage per command subtree, each exporting `NewCmd(groupID, flags)`.
- **`internal/core/`** — domain logic, subclustered into `project/` (what is a DWE project), `execution/` (pipeline engine), `workflow/` (deploy / lifecycle / reset / snapshot / setup), `usercommands/` (declarative command system), `validate/` (static project validation), `docs/` (embedded docs subsystem), `ui/` (domain-aware renderers — sink layer, imported only by `cli/`), and `notify/` (desktop notifications).
- **`internal/shared/`** — leaf infrastructure (`docker/`, `git/`, `daemon/`, `lock/`, `pathsafe/`, `envfile/`, `render/`, `liveui/`, `tpl/`, `i18n/`, `version/`, `prompt/`, `promptcache/`).

**Per-package responsibilities, invariants, and cross-package contracts live in [`docs/internals/packages.md`](docs/internals/packages.md).** Read the relevant section there before modifying any package — it captures non-obvious load-bearing details (sequencing, sentinels, allowlists, render ordering, cross-cutting CLI patterns like JSON output mode and display-string localization) that are expensive to re-derive from the code.

## Configuration Documentation

Keep behavior and docs aligned. DWE user-facing documentation lives in `docs/reference/` (schemas) and `docs/guides/` (task-oriented recipes):

- `docs/reference/config/` — project config files (`workspace.md`, `services.md`, `docker.md`, `info.md`, `styles.md`), pipelines (`deploy.md`, `lifecycle.md`, `reset.md`, `conditions.md`, `state.md`), user commands (`commands/`), user-level notifications and i18n (`notifications.md`, `i18n.md`), snapshot workflows (`snapshot.md`), project readiness checks (`validate.md`), setup wizard (`setup.md`), and command browser settings (`ui.md`).
- `docs/reference/render/` — render subcommands (env / ide / ai / git) and template-pack mechanics (manifest schema, local overrides, collision policies).
- `docs/guides/` — task-oriented recipes and integrations (e.g. Starship prompt). Each page solves a concrete user-facing problem that cuts across the reference. Translations live in `docs/i18n/<lang>/guides/`.

The live CLI surface (flag list, subcommand tree) is `dwe --help`; no per-command markdown files are kept in the repo.

Update these when changing schemas, commands, service toggles, deploys, or hooks.

For AI agent orientation, `dwe docs llms-txt` emits a compact llms.txt index (project context, services, commands, and docs pointers) designed for AI agents to load once and navigate the project — run it inside a project for a project-aware snapshot, or outside one for a generic dwe reference.

## Build, Test, and Development Commands

- `make build` runs `go mod tidy`, syncs `docs/` into `internal/core/docs/embedded/` (via `scripts/sync-embedded-docs.sh`), regenerates `internal/core/docs/content_hashes_gen.go` (via `scripts/gen-docs-content-hashes.sh`), builds `./cmd/dwe`, and writes `bin/dwe`. Run `make build` (not `go build`) after editing docs under `docs/reference/`, `docs/guides/`, `docs/internals/`, or `docs/i18n/` — otherwise the embedded docs in the binary will be stale.
- `make test` / `make test-v` / `make test-race` run the test suite. They depend on `embedded-docs`, so the sync runs before tests every time. **Always use `make test*` — `go test ./...` directly will see an empty `internal/core/docs/embedded/` tree on a fresh checkout (it is gitignored and generated) and the docs-subsystem tests will fail.**
- `make lint` runs `golangci-lint` checks.
- `make tidy` updates `go.mod` and `go.sum`.
- `make clean` removes the built binary from `bin/`.

For focused work prefer `make embedded-docs` once, then `go test ./internal/cli` or `go test ./internal/core/usercommands/... -run TestName` directly — the sync is idempotent and the embedded tree persists until the next `docs/` edit.

## Coding Style & Naming Conventions

Follow `.editorconfig`: Go files use tabs with width 4; YAML, JSON, and shell files use two spaces. Run `gofmt` and `goimports`; `golangci-lint` enforces `errcheck`, `govet`, `staticcheck`, `revive`, `gocritic`, and `modernize`.

## Testing Guidelines

Prefer table-driven tests for command parsing, config resolution, Docker orchestration, and runner behavior. Keep fixtures in `testdata/` and avoid developer-specific Docker state unless the package isolates it. Every behavior change should update nearby `*_test.go` coverage. Run `make test` before opening a PR.

## Commit & Pull Request Guidelines

Recent history uses conventional-style commits such as `feat(commands): ...`, `fix(commands): ...`, `docs(config): ...`, and `refactor(commands)!: ...`. Keep the scope tied to the package or user-facing area, and use `!` only for breaking changes. Pull requests should include a summary, verification commands, linked issues when applicable, and screenshots or terminal output when changing CLI presentation.

## Critical Patterns

Recurring traps and load-bearing contracts. Each pattern has a full write-up in `docs/internals/packages.md` — read it before touching the relevant area.

- **JSON output mode (`--output json`, `--pretty`)** — every read-only command must route through `cmdctx.WriteData[T]` / `cmdctx.WriteError`; typed errors (`cmdctx.Err`, `cmdctx.ErrWrap`) carry exit codes and serialize to a `{"error":{…}}` envelope on stderr. Diagnostic commands (`validate`) are the exception — they emit diagnostics-as-data even at severity=error. See § CLI cross-cutting behaviors.
- **Display-string localization** — never read `def.Description` directly in display code; thread `rflags.I18n` (or `i18n.TranslatorOrNop` on completion paths) and use the typed `store.*` helpers. Storage/hashing sites stay English. See § CLI cross-cutting behaviors.
- **Binary accessors** — never read `cfg.Binaries.*` fields directly. Always use nil-safe accessors `config.DweBin / DockerBin / ShellBin / GitBin / MmdcBin`. Deploy/condition step `when:` predicates intentionally use hardcoded `sh` for portability. See § Core — Foundation (`project/config/`).
- **YAML loader strictness** — deploy / reset / lifecycle / command-file / manifest loaders use `yaml.Decoder.KnownFields(true)` (unknown fields are hard errors). Info / styles / docker / localconfig / topology loaders use lenient `yaml.Unmarshal`. Match the surface when adding loaders. Exception: the four strict pipeline loaders (`LoadLifecycleConfig`, `loadProjectDeployConfigDecode`, `loadServiceDeployConfigDecode`, `loadDeployConfigDecode`) also tolerate `io.EOF` from an all-comment/empty file — empty doc is treated as absent, so the built-in default applies unchanged. This was introduced to support `dwe init`'s inert scaffold overrides. Mirror this pattern when adding new strict pipeline loaders. See § Core — Foundation.
- **Validation framework** — per-domain validators register via `All()` functions and run independently per-file; `env/` + `checks/` also participate in preflight, others only in `dwe validate`. Severity-gated exit codes. See § Core — Validation.
- **Preflight + locks ordering** — lifecycle commands (`deploy run` / `run` / `stop` / `restart` / `reset run`) MUST call `preflight.Run` BEFORE any side effect, then call `lock.AcquireProjectLocks(baseDir)` for project mutations (acquires `deploy.lock` then `snapshot.lock` alphabetically; releases in reverse). Never call `lock.Acquire` directly on either lock file. CLI command sites should acquire via `cmdctx.AcquireProjectLocksOrReport(baseDir, w)` — it wraps `lock.AcquireProjectLocks`, prints `*lock.ProjectLockHeldError` via the writer and returns it unchanged (preserving exit code 2), and wraps any other error as `acquiring project locks: %w`. Do not re-roll the 9-line acquire-and-report block. Docs subsystem and `dwe logs` are read-only — no preflight, no locks. See § `preflight/` and § `shared/lock/`.
- **Config-load helpers** — after `config.LoadConfig`, the plain `loading config: %w` wrap is centralized in `config.LoadConfigOrWrap(workspacePath)` (reachable from both `cli/` and `core/workflow/`); use it instead of re-wrapping. The typed `cmdctx.ErrWrap("project_invalid_config")` contract is a **separate** path — do not collapse it into `LoadConfigOrWrap`. For the docker-config load-or-empty idiom (`os.ErrNotExist` → `&DockerConfig{}`, else `loading docker config: %w`), use `config.LoadDockerConfigOrEmpty(baseDir, cfg)`. See § Core — Foundation (`project/config/`).
- **Grouped commands: no child `PersistentPreRunE`** — cobra does NOT chain `PersistentPreRunE`; a child's hook *replaces* the parent's. For grouped subtrees needing shared setup, use a per-`RunE` loader helper (see `loadStatusContext` in `cli/status/`). See § `internal/cli/status/`.
- **Completion path safety** — cobra's hidden `__complete` path bypasses `PersistentPreRunE`. `ValidArgsFunction` callbacks must call `cmdctx.CompletionConfigPath(flags, cmd)` before any config-dependent work; on any error return empty completions + `cobra.ShellCompDirectiveNoFileComp` silently. See § `cmdctx/`.
- **Section renderer signature contract** — `internal/core/project/stack/` collectors and `internal/core/ui/render/` renderers return strings (and per-row errors where applicable); `internal/cli/` is the single writer to stdout/stderr. Do not pass `io.Writer` into `stack/` or `ui/render/`. See § `internal/core/ui/render/`.
- **Pipeline defaults** — `workspace/deploy.yml`, `workspace/reset.yml`, and each section of `workspace/lifecycle.yml` are optional. Each has paired `Default*Config()` + `Ensure*Config(loaded) (cfg, defaulted bool)` constructors. The bool drives `cmdctx.EmitDefaultNotice` (suppressed in JSON mode). Composition is full-replacement, **except** `EnsureStopConfig` which always prepends `autoReapPhase()`. See § Core — Workflow.
- **Single-block → multi-command sugar** — declarative command types like `type: daemon` expand at registry-load time into N virtual `CommandDef`s. Pattern: source command dropped from `byID`, synthetic group node `ensureGroup`'d, each synthetic carries `DerivedFrom*` + a `Source*Spec` pointer (`yaml:"-"`) for inspect. Registry expansion is config-blind. See § Core — User Commands.
- **`info.yml` auto-blocks** — `type: auto-urls` and `type: auto-hosts` items expand at *render* time, not load time. **Service iteration in renderers MUST go through `config.DeployOrder(...)` — never `range cfg.Services` directly** (map iteration is randomized → flaky golden tests). Adding new top-level fields to `service.yml` requires updating BOTH `allowedFieldsFor` in `internal/core/project/config/workspace.go` AND `servicesAllowedFields` in `internal/core/validate/config/workspace.go` — `service.yml` uses `KnownFields(true)` strict decode. See § `internal/core/ui/render/`.
- **Pending-state lifecycle** — `dwe services enable/disable` (without `--apply`) writes `local.yml` immediately and tracks deferred work in `state.Services.pending`. Pending writes are gated on `journalSnapshot.everDeployed` (see `loadJournalSnapshot` in `internal/cli/service/service_toggle.go`): any prior deploy attempt counts (StatusDeployed / StatusFailed / StatusInProgress / StatusPartial on any service, OR `state.Project.LastRun != nil`, OR `state.Project.Status != "" && != StatusNotDeployed`). Journal load errors default to `everDeployed = true` to avoid silently swallowing pending on a corrupt file — `AddPendingOps` then either repairs the file or hard-fails. The gate is closed only when there has been NO deploy attempt at all: in that case both the pending write and the "stack not running" banner are skipped (silent `local.yml`/`.env` update plus a one-line `run dwe deploy` hint after the plan). With `--apply` the docker probe still runs even when never-deployed, so a broken docker setup surfaces an early diagnostic. Toggle executor must use `ClearPendingOps` with a contributor-derived `clears` slice — NEVER `ClearPending` (would erase unrelated pending from other sessions). See § `workflow/deploy/journal/`.
- **Compose-bypass for per-service stop/reset/restart** — `dwe stop <name>` stops via `docker stop <containerName>` directly (compose overlay is filtered out for disabled services). `dwe restart <name>` restarts via `docker restart <containerName>` directly (also bypasses compose and lifecycle hooks; runs NO preflight, acquires NO project locks — lighter than the full-lifecycle restart; `ErrNoSuchContainer` surfaces as a user-facing "run `dwe deploy run` first" hint). `dwe reset run --service <name>` drives stop+remove through a synthetic `docker_stop_remove_container` builtin (NOT `stopServiceLocked`). Volume cleanup is opt-in via `docker_remove_project_volumes`. See § `internal/cli/lifecycle/`.
- **Per-service folder symmetry** — every service lives in `workspace/services/<name>/`; folder name = map key (no `name:` field). `service.yml` is required; `deploy.yml` / `reset.yml` are optional pipeline declarations valid for any service type. When adding a new file type to a service folder, add it to the `services_folder` validator in `internal/core/validate/config/`. See § `project/config/`.
- **Snapshot template scope gate** — `${snapshot.*}` resolves only inside snapshot workflow blocks. Three scope values (`SnapshotScopeNone`, `SnapshotScopeCreate`, `SnapshotScopeRestoreOrRemove`); `tpl.RenderCommand` calls `validateSnapshotScope` before `CompileVarSyntax`. Never add scope logic to `CompileVarSyntax` — it must stay pure-syntactic with no error path. See § `internal/shared/tpl/`.
- **Live view & state pointers** — the pipeline live view uses `bubbles/v2` models directly via `Model.View()` — never `tea.NewProgram`, `term.MakeRaw`, or terminal capability queries. Nine non-negotiable invariants are documented in `internal/shared/liveui/liveline.go`. See § `internal/shared/liveui/`.
- **Prompt hot path** — `dwe prompt` and `dwe prompt --check` bypass cobra entirely via an early dispatch in `cmd/dwe/main.go`. `internal/shared/prompt` deliberately does NOT use lipgloss (auto-downgrades to no-color when stdout is piped). The cobra command is `Hidden: true` (still works with `--help`/completion, just dropped from listings). See § `internal/shared/prompt/`.
- **Prompt cache contract** — `.dwe/prompt-cache.yml` (TTL 2 min) backs the prompt's stack-state icon. Authoritative writers: `dwe run` / `restart` (no arg) / `services …--apply` write `running`; `dwe stop` / `reset run` (no arg) write `stopped`; top-level `dwe status` writes the exact aggregated `stack.HealthState(h)`. Scoped mutations (`--service`, snapshot restore/rollback, `dwe deploy run`) **invalidate** via `promptcache.Remove`. `dwe prompt`'s own refresh only ever writes `running` — **never `stopped`** (no-downgrade rule: zero-result from `docker ps` is indistinguishable from a wrong-label filter). Layering: `shared/promptcache` is leaf (string in/out); `core/project/stack.HealthState(Health) string` does the enum→string mapping in `core/`. Cache writes are best-effort everywhere (`_ = promptcache.Write(...)`). See § `internal/shared/promptcache/`.
- **Docs subsystem read-only** — never call `lock.AcquireProjectLocks` from docs commands and never run preflight. Resolve locale directly via `i18n.ResolveLocale(flagLang, cfgLang, sysLang)` — NOT `rflags.Locale` (clamped to YAML store; wrong namespace for markdown). See § Core — Docs.
- **Two i18n namespaces** — `workspace/i18n/<lang>.yml` (YAML, command/UI strings — validated by `i18n/` validator domain) vs `docs/i18n/<lang>/reference/...` + `docs/i18n/<lang>/internals/...` (markdown, long-form docs — no validator). Different loaders, no merge. See § `internal/shared/i18n/`.
- **Local compose overlays** — `compose.extra` (project-wide) and `services.<name>.compose.extra` (per-service) are valid **only** in `workspace/local.yml`; all other layers (`workspace.yml`, `defaults.yml`, `service.yml`) hard-error with a pointer to `local.yml`. Both fields are `yaml:"-"` on the typed structs (`ComposeConfig.Extra`, `ServiceConfig.LocalComposeExtra`) and are **never** decoded via YAML — they are populated by post-decode injection from the local.yml raw map inside `LoadConfig`. Injection runs **before** `ResolveServiceExtends`. Do NOT add either field to `allowedFieldsFor()` or `servicesAllowedFields` — the strict decoder would treat them as structural service fields. See § Core — Foundation (`project/config/`).
- **Config render + generated-once values** — service configs materialize via the **render** subsystem (`internal/core/execution/templates/config/` `RenderConfigs` / `HarvestGenerated`), NOT the legacy copy mechanism (`service_configs_copy`, now deprecation-warned). Four load-bearing contracts: (1) **`${...}` substrate** — config templates render through `tpl.CompileVarSyntax`+`RenderContext` (the `${X}` shorthand, NOT `packcommon.TemplateData`/raw-`{{ }}` used by ide/ai/git); `${generated.<name>}` routes to `case "generated"` → `resolveGenerated .Generated` (lenient, absent→`""` like every other `${...}` resolver), `${services.<name>...}` exposes only the **curated `injectServicesIntoRaw` subset**. (2) **Render check-pairing** — pairing `service_configs_render_check` as the render step's `check:` forces it to re-run every deploy via the `hasCheck → Run` lever in `journal/decision.go` (template edits / store clears always apply); mirrors `service_configs_copy`+`service_configs_check`. (3) **Harvest not mint** — the engine is hermetic, so the *service* generates secrets (e.g. `php artisan key:generate`) and DWE reads them back via `pattern` (regex, capture group 1) into the `generatedstore` leaf (`.dwe/generated.yml`, mirrors `promptcache`), `SetIfAbsent` (write-if-absent); the `generated-missing <svc> <field>` predicate (re-splits its own two args — see § condition) gates the generate step. (4) **Run-render ordering IS the safety argument** — `renderConfigsForRun` runs only AFTER the deploy gate AND post-pull reload but BEFORE phases; `missingGeneratedKeys` skips a service's render (with a `dwe deploy run` hint) when any declared key is absent from the store, so a `reset --clear-generated` + `dwe run` never blanks secrets. `reset --clear-generated` clears the store only after the FULL reset succeeds **including** journal cleanup. New top-level `generated:` field needs BOTH allowlists; `render.config` is struct-enforced (no allowlist). See § Core — Execution (`templates/config/`), § `internal/shared/generatedstore/`, and § Core — Foundation (`project/config/`).
- **Diagnostic trace routing (`-v` / `--debug`)** — all diagnostic echo goes through the `internal/shared/trace` leaf (`trace.Command`/`Decision`/`Debugf`), **stderr only** — stdout (incl. `--output json`) stays clean. `trace` is a leaf imported by `docker`/`git`/the execution engine/preflight; only `cli/` calls `trace.Configure` + installs the slog handler (`installSlogHandler`, **only** at `LevelDebug` — `-v` never touches slog). Output destination resolves by a **three-level precedence at each emit**: (1) ctx-carried printer (`trace.WithLinePrinter`) set per parallel sub-step for correct attribution, beats (2) global active printer (`trace.SetPrinter` → restore stack) set by `PlainReporter.StartPipeline` to wrap `r.live.Println` (the live-view-safe screen path, framed above the footer), beats (3) the `Configure` fallback writer (`os.Stderr`, used outside any pipeline + in JSON mode). `LevelOff` is a zero-alloc early return → no overhead with no flags. Level: `--debug` OR truthy `DWE_DEBUG` → Debug; else `--verbose` → Verbose; **flag beats env** (`DWE_DEBUG` in `{"","0","false","no","off"}` is off). Verbose = command echoes + pipeline decisions; Debug adds read-only docker probes, timings/exit codes, compose env, and `slog.Debug` records (read-only `ps` probes are **Debug-only** — keep `dwe status -v` quiet). `trace.FormatCommand` is the single quoting source (lifted from the old `docker/compose.go` `formatCommand`/`quoteArg`) — compose error-wrap goldens must stay byte-identical to it. See § `internal/shared/trace/`.

## Agent-Specific Instructions

Do not overwrite unrelated local changes. Keep command examples current with the `Makefile`. When changing CLI behavior, update tests and config docs.
