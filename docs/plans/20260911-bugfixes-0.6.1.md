# 0.6.1 bug fixes: stopped stack, interpolated test ports, runner tail

## Overview

Three independent bugs found while testing 0.6.0 on live projects. They ship on
one branch (`fix/0.6.1-bugfixes`, cut from `release/0.6.1`) as three separate
commits, one PR into `release/0.6.1` (milestone 0.6.1). Commits go smallest
first:

**Fix A — the workflow runner drops the un-terminated last line of a parallel
sub-step.** A sub-step whose final output has no trailing newline
(`printf 'error: x'; exit 1`) loses that line from BOTH the failure dump and the
per-sub-step log file. In CI the dump is the only output channel, so the line
that explains the failure is exactly the one that disappears.

**Fix B — `dwe test` silently does not remap host ports interpolated through
`vars:`.** A compose port such as `"${VALKEY_PORT:-6379}:6379"`, where
`VALKEY_PORT` is an `exports.env` rule `from: vars.ports.valkey`, is not
remapped in the test copy and collides with the live stack at bind time. This is
a documented boundary (the fix is `env.vars: { ports.valkey: auto }`), not a
regression — the defect is that nothing warns. Fix B adds a non-blocking
isolation-scanner finding that carries the ready-made fix line.

**Fix C — the built-in deploy pipeline does not bring a stopped stack back
up.** `dwe deploy run` prints `Phase: start`, finishes `✓ Done (0s)`, and the
stack stays down. The built-in `up` step has no `check:`, so the journal records
it `ok` with a matching action hash and skips it on every later deploy; the step
is `untracked`, so even the skip line is hidden. The docs promise the opposite
("Start containers and wait for health").

All three are user-observable → each commit carries its own `CHANGELOG.md`
`## [Unreleased]` entry and its own EN + RU docs. `[Unreleased]` currently has
only `### Changed`; the first commit creates `### Fixed`.

### Non-goals

Decided during design; do not re-litigate during implementation:

- **Fix A does not touch the pipeline.** The pipeline's parallel branch still
  drops the tail from the per-sub-step file; it keeps it in the global
  `.dwe/logs/<pipeline>.log` through `commitTrailingTail`. `flushTee` is called
  early in several places there (`executor.go:998-1001`), so the same flag does
  not port over trivially.
- **Fix B does not remap anything.** Automatic remapping of interpolated ports
  and `ports_free` coverage for them are separate, larger work. Fix B only
  warns.
- **Fix C adds no schema field and does not avoid the one-time project-hash
  change** (see Solution Overview). Post-deploy `info`/`success` stay
  journal-skippable, and untracked steps still print no skip line.

## Solution Overview

### Fix A — close the tee at EOF

A local `atEOF bool` next to the tee. The callback keeps its early return for
`!final` frames only while `!atEOF`. After `runCommandStep` returns, set
`atEOF = true`, then call `tee.Flush()`: the tail now goes to `buf` and to the
per-sub-step file (stripped, with a newline, like any final frame). A tail whose
ANSI-stripped form is blank (`strings.TrimSpace` empty) is dropped entirely — the check comes BEFORE
`SetBlockRowRunning`, so it does not redraw the row either; a real tail still
updates the row right before `SetBlockRowFinal`.

No synchronisation is needed (see Context). No frame is held, so this is not
the "composite flush hook" the liveui paragraph warns about.

### Fix B — trace interpolated ports through `exports.env`

The scanner learns to read `${…}` host-port tokens and to follow the variable to
its export rule:

| rule for `VAR` | result |
|---|---|
| active rule, `from:` is exactly `services.<n>.ports.<p>`, `<p>` declared in `cfg.Services[n].Ports` with a port in 1..65535 | finding with `SourceService=<n>` — dropped by the consumer when the runner actually remaps `<n>`'s ports |
| active rule, `from: services.…` that does not meet the above (`.port` sub-path — `Raw` stores the port as a bare int, so it never resolves; undeclared or out-of-range port) | generic finding — the export falls back to its `default:` |
| active rule, `from: vars.<path>` | finding, `VarPath=<path>`, message carries `env.vars: { <path>: auto }` |
| no rule, or the rule's `when:` is falsy (host env, user `.env`, default only) | finding, no `VarPath`/`SourceService`, generic message |

"Active" means `when:` is empty or resolves truthy on `cfg.Raw`, evaluated
exactly as `envfile.Render` does. The scanner never decides whether a port is
remapped: that differs per scenario, so it only records `SourceService`.

**The question is "is this port remapped", not "is the service enabled".** The
single answer is membership in the set the runner's remap actually covers —
`enabledHostPortKeys(cfg, scn)`, exposed as a thin helper
`envtest.RemappedHostPortServices(cfg, scn) map[string]bool` with
`enabledHostPortKeys` built on it. The two differ for a `required: true`
service a scenario lists under `env.services.disable`: the loader keeps it
`Enabled`, but the remap skips it, so its port collides. Filtering on
`Enabled` would silently drop exactly that finding.

The finding is a new kind, `interpolated_host_port`, `Blocking: false`. The
scanner stays scenario-blind; each consumer filters by its own view:

- runner gate: drop the finding when `SourceService` is in
  `RemappedHostPortServices(origCfg, scn)` (the same inputs `writeCopyLocalYAML`
  uses), or when the scenario sets `VarPath` to `auto`;
- cost profile: the same two rules with `RemappedHostPortServices(p.cfg, scn)`;
  its per-scenario `view` additionally gets `Raw["services"][n]["enabled"]`
  patched from `view.Services` (loader semantics, required wins) — that patch
  only serves `when:` evaluation, never the remap filter;
- `dwe validate` (`tests` domain): drop a `SourceService` finding when it is in
  `RemappedHostPortServices(ctx.Cfg, scn)` for every scenario; drop a `VarPath`
  finding when every scenario sets the path to `auto`; an unloadable scenario
  counts as not covering; the warning names the scenarios that still lack the
  fix. `when:` is
  evaluated on the project `Raw` here — a rule gated on a service that is off by
  default but on in every scenario still warns; documented approximation.
  Because the runner runs `dwe validate` in the copy, `dwe test run A` on a
  fixed A still streams this warning while scenario B lacks the fix —
  documented, non-blocking.

This keeps a correctly fixed project green under `dwe validate --strict`, which
is the same reason `shared: true` volumes are already suppressed.

### Fix C — an honest post-condition on the built-in `up`

The built-in `up` step gets `check: {type: builtin, cmd: containers_running}`
with no `with:`. Because the step now has a `check:`, the journal never skips it,
and `compose up --wait` is idempotent, so a stopped stack comes back up and a
running one is a no-op plus a probe.

`containers_running` gains the whole-project mode for an absent/empty
`services`, aligned with `docker_wait_healthy`. Semantics: **every non-one-off
container of the compose project is running, or exited with code 0** (a
finished init/migrate one-shot) — **restricted to containers of services active
in the current compose config**. The expected set is the project's existing
containers, not the config's service list, so `scale: 0` / `replicas: 0`
services (no containers) never fail it, and a service that could not even be
created has already failed `up --wait` (the body) before the check runs. The
active-service filter is needed because `up --remove-orphans` does NOT remove
containers of inactive-profile services: a profile service started once with
`--profile x` and then stopped (Exited 143) would otherwise fail every later
deploy (reproduced on Compose v5.5.1). An empty set after a successful
`up` (every service at scale 0) passes: there is nothing that should be
running.

**Accepted consequence — one-time project-hash change.** `check:` is part of
`ProjectConfigHash`, so the first deploy after upgrading sees "config changed"
once (interactive selector; default "Apply changes" does the right thing;
non-interactive applies silently) and re-runs the project-level steps once.
Avoiding it would mean excluding `check:` from the project hash, which changes
hashing semantics for every pipeline — rejected. Documented in Upgrading and
CHANGELOG instead.

## Technical Details

### Fix B — tokenizer

- Split the short syntax on `:` only outside `${…}` (track brace depth; `$$` is
  compose's escaped dollar and is not an interpolation).
- A host-port token is interpolated when it is exactly one of: `${VAR}`,
  `${VAR:-d}`, `${VAR-d}`, `${VAR:?e}`, `${VAR?e}`, `$VAR`, where `VAR` matches
  `[A-Za-z_][A-Za-z0-9_]*`. Anything mixed (`${A}${B}`, `80${X}`) is ignored —
  advisory scanner, no false positives.
- `/tcp` / `/udp` stripping, the IPv6 `[` bail-out and every literal result stay
  byte-identical.
- Long syntax already routes `published:` through `publishedNodeToken` →
  `scanPublishedToken`; the interpolation branch lives in `scanPublishedToken`
  so both syntaxes share it.
- `IsolationFinding` gains `EnvVar`, `VarPath` and `SourceService` strings (all
  empty for every other kind). The collapse switch must route the new kind into
  `portIdx` alongside `KindRawHostPort`, or it falls into the last-wins map.
- Rule lookup: build a `Name → ExportRule` index of **active** rules once per
  `ScanComposeIsolation` call (skip reserved names; evaluate `when:` via
  `ResolvePath(cfg.Raw, rule.When)` + `isTruthy`) and pass it down to
  `scanPublishedToken`. The declared-port check reads `cfg.Services[n].Ports`
  regardless of `Enabled`.
- Consumer filtering lives next to each consumer, and all three ask the same
  helper, `envtest.RemappedHostPortServices(cfg, scn)`, built from the existing
  `enabledHostPortKeys` loop (no second derivation, no behaviour change to the
  remap — it deliberately does not honour `required`). No import cycle:
  `validate/tests` and `cli/test` already import `envtest`.

### Fix C — whole-project mode of `containers_running`

**Project name.** Use `compose.ProjectName`. When it is empty, read the
effective top-level `name` from `compose config --format json` (internal args,
same call shape as `DeriveBuildBases`). Still empty or the call fails → error
`containers_running: cannot determine the compose project name — set
project.name or docker.yml project_name`.

**Label mode.** One probe decides whether this backend stamps the oneoff label:
`ps -a` + project label + key-only `label=com.docker.compose.oneoff`. If it
returns containers → filter every query below with `oneoff=False`. If it
returns nothing → query without the oneoff filter (podman-compose without the
label; accepted edge: a stopped `compose run` container is then evaluated too).

**Queries** — portable `{{.Names}}` against the project label, compose bin and
process env so the probe hits the same daemon:

1. `all` — `ps -a`;
2. `running` — `ps` + `status=running`;
3. `done` — `ps -a` + `exited=0`.

Run them in this order (all → running → done) so a container that appears
between queries is simply not evaluated, never misclassified.

`candidates = all − running − done` (by container name). Empty → pass (the
common case; `all` empty also passes — nothing should be running).

**Slow path — only when candidates exist.** Keep only candidates that belong to
a service active in the current config: `compose config --services`
(internal args), then for each active service one `ps -a` + project label +
`label=com.docker.compose.service=<s>` (+ the label-mode oneoff filter) query;
`failed = candidates ∩ names of active-service containers`. Non-empty →
`containers not running: a, b`; otherwise pass (the leftovers were
inactive-profile or orphan containers).

The transient-probe retry (`runningServicesWithRetry` semantics) wraps the probe
set: a query that fails to run is retried; a successful answer is never
re-polled.

Placement: one query helper in `internal/shared/docker/labels.go` beside
`serviceContainerPSArgs` (`projectContainerNames(ctx, bin, env, project, filters…)`
or similar) plus a `Compose.ConfigProjectName(ctx)` for the name fallback; both
echo the command through `trace.Command` at Debug only, like `RunningServices`.
The builtin orchestrates behind package-level function vars so tests drive every
branch without a daemon. `Describe` for the empty mode:
`check that every compose container is running (or exited 0)`.

`Validate`: absent or empty `services` is valid; an empty-string element and any
unknown key remain errors.

Known edges (documented, not handled): on podman-compose without the oneoff
label, a stopped daemon container of an active service can be reported as not
running; a podman-compose build without `config --format json` / `config
--services` support hits the error-with-hint path when the name is unset or a
candidate exists; `BuildInternalArgs` drops `args.global`, so a project whose
`args.global` carries `--project-directory` / `--env-file` can resolve a
different fallback name than `up` used, and a `--profile` there makes that
profile's services look inactive to the slow path (a false pass on a crashed
profile service, never a false failure). A project that overrides `args.up`
without `--remove-orphans` is covered by the slow path: orphans are not in
`config --services`.
