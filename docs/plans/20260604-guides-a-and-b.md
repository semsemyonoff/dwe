# User-facing guides (A: project consumers, B: project maintainers)

## Overview

Fill out `docs/guides/` (currently 2 pages: `index.md`, `starship.md`) with 12 new task-oriented user guides that solve concrete cross-reference problems:

- **A. Project consumer guides** (4 pages) — for developers who join an existing DWE project and use it day-to-day.
- **B. Project maintainer guides** (8 pages) — for developers who *write* DWE config (author services, commands, daemons, snapshot workflows, theming, localization, IDE template packs, preflight checks).

Each EN page has a parallel Russian translation under `docs/i18n/ru/guides/<name>.md` with a `> Translated from: guides/<name>.md @ <hash>` staleness header. Both indexes (`docs/guides/index.md` and `docs/i18n/ru/guides/index.md`) are restructured to group pages by audience.

Guides are NOT reference: they do not duplicate schemas, do not link to internal code, and do not describe DWE internals. They stitch reference pages together under one concrete user task ("I joined a project, what now?", "I want to add a worker service", "everything is broken, where do I look").

## Context (from discovery)

- **Project**: DWE CLI (Go, cobra-based). Docker-based dev environment manager.
- **Existing docs layout**: `docs/reference/` (schemas + concepts + render + docs subsystem + templates) is comprehensive but reference-shaped; `docs/guides/` currently has only `starship.md` (one integration recipe). `docs/i18n/ru/` mirrors `docs/reference/` and `docs/guides/` with translations.
- **Style anchor**: `docs/guides/starship.md` and `docs/i18n/ru/guides/starship.md`. Short intro → sections with code blocks, tables, mermaid where useful. Reference links use `../reference/...` (EN) and `../reference/...` (RU mirror — Russian guide links to Russian reference).
- **Translation header format**: `> Translated from: guides/<name>.md @ <8–12 char hash>` — the hash comes from `internal/core/docs/content_hashes_gen.go`, regenerated by `make build` (via `scripts/gen-docs-content-hashes.sh`).
- **Build pipeline**: `make build` runs `scripts/sync-embedded-docs.sh` (syncs `docs/` → `internal/core/docs/embedded/`) and regenerates `content_hashes_gen.go`. Required after every docs/ edit; tests touching the docs subsystem won't see new files otherwise.
- **Validation**: `dwe validate translations` checks `workspace/i18n/` shape (project-level, not relevant to our docs i18n which is markdown), but the docs subsystem has its own content-hash staleness check that surfaces in `dwe docs` when a translation's hash doesn't match the EN source.

## Development Approach

- **Testing approach**: Regular (write content, then verify via `make build` + `dwe docs show` rendering + `dwe docs list --lang ru`).
- Documentation work — the "tests" for docs are:
  - `make build` succeeds (embedded docs + content hashes regenerate cleanly).
  - `dwe docs list` and `dwe docs list --lang ru` show every new page.
  - `dwe docs show guides/<name>` renders each EN page; `dwe docs show guides/<name> --lang ru` renders each RU page.
  - `dwe docs search` finds substrings from each new page (basic smoke check).
  - No translation staleness warnings on `dwe docs`.
- Each task = one guide page (or one structural change). Tasks are independently shippable.
- **CRITICAL**: do not duplicate reference content. If a section would just restate a reference page, link to it and move on.
- **CRITICAL**: keep guides user-facing — no internal code references, no Go type names, no internal package paths.
- **CRITICAL**: every EN page must have a parallel RU page with a correct content-hash header before the plan is considered done.

## Testing Strategy

- **Unit-test analogue for each guide**: after writing the EN page, run `make build` and verify it appears in `dwe docs list`. After writing the RU page, run `make build` again and verify `dwe docs list --lang ru` includes it and no staleness warning fires.
- **End-of-plan verification** (Task 17): full `make build`, `dwe validate` clean, `dwe docs list` + `dwe docs list --lang ru` both show all 13 guides (12 new + `starship.md`), spot-check rendering for 3 random pages.

## Solution Overview

13 markdown writes (12 EN + 12 RU + 2 index updates), bracketed by 2 `make build` runs (first to mint content hashes, second to embed final state with correct translation headers).

**Why two `make build` cycles**: translation headers reference the EN source's content hash. The hash for a brand-new EN file only exists after the first `make build` regenerates `content_hashes_gen.go`. So:

1. Write all EN files + EN index.
2. `make build` → mints hashes for new files (and re-mints the modified EN index).
3. Read hashes out of `internal/core/docs/content_hashes_gen.go`.
4. Write all RU files + RU index with the freshly minted hashes in the `Translated from:` header.
5. `make build` again → embedded tree now contains both languages, all hashes consistent.

**Note on staleness check**: the `> Translated from: ... @ <hash>` header in an RU file references the **EN source's** hash, not the RU file's own. RU files themselves get separate hashes minted in `content_hashes_gen.go` after step 5 — those exist only for the embedded-tree integrity check and are unrelated to the staleness mechanism. If anyone later edits an EN file, its hash changes and `dwe docs` flags the RU translation as stale; editing the RU file does not trigger staleness on itself.

### Style invariants for every guide

- One H1 = page title.
- Short opening paragraph naming the user problem the page solves.
- `## Sections` with H2 — table-of-contents pattern from starship.md is optional, only include if the page is long enough to benefit.
- Concrete commands with `dwe ...` and YAML blocks. Prefer shell + yaml fences (not generic `text`).
- Link to reference using relative paths: `../reference/config/<file>.md`.
- Russian translations link to Russian reference: same relative path resolves under `docs/i18n/ru/`.
- No internal code references, no Go type names.

### Translation workflow

For each EN file `docs/guides/<name>.md`:

1. After EN files are written, run `make build` to mint hashes.
2. Open `internal/core/docs/content_hashes_gen.go` — find the entry for `guides/<name>.md` (the key matches the docs-tree path).
3. Use the first 8–12 characters of that hash in the RU header: `> Translated from: guides/<name>.md @ <hash>`.
4. Translate body with Russian terms matching the existing `docs/i18n/ru/guides/starship.md` style.
5. Run `make build` after writing RU files — the staleness check should pass.

### Content-overlap rule

Several guides touch the same commands (`dwe logs`, `dwe status`, `dwe info`). To avoid duplication:

- The guide that solves the **user goal** owns the full treatment.
- Other guides referencing the same command get a one-line cross-link.
- Example: `daily-workflow.md` owns the `dwe logs` walkthrough; `troubleshooting.md` references it via "see [daily-workflow → viewing logs](daily-workflow.md#viewing-logs)" rather than restating it.
