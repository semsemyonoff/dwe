# Devbox Branding & Styling Refactor

## Overview

Implement the design-locked Devbox branding & styling specification:

1. Collapse the 25-token `StylesColors` surface to **7 semantic tokens** (`accent`, `success`, `warning`, `danger`, `muted`, `border`, `text`) with separate light / dark hex defaults, resolved once at `ApplyStyles` time via `lipgloss.HasDarkBackground()` and stored as raw hex strings (required for the v1/v2 + Fang bridge — see Technical Details).
2. Rework the CLI header: remove `header.color`, add `header.tagline`, introduce branded line `{▪} Devbox · <project> · <version>`.
3. Introduce reusable `LogoMark()` / `LogoMarkPlain()` helpers and embed the logomark in cmd-browser, root header, info header, version output, status section titles, docs generator.
4. Fix cmd-browser visual bugs: torn right border (overflowing descriptions), title/help bars not full-width.
5. Brand desktop notifications: `beeep.AppName = "Devbox"`, embedded `icon.png`, project name in title, simplified body.

Delivered as a single coherent change. Tasks are ordered by dependency: styles foundation → header → logo → cmd-browser fixes → notifications.

Related patterns:

- `ApplyStyles` rebuilds package-level style vars from config; empty strings preserve defaults — this seam stays, only the field set changes.
- `lipgloss.AdaptiveColor{Light, Dark}` is the standard idiom for adaptive styling, but unsuitable here because the `Color*()` accessors must return **raw hex strings** for the v1/v2/Fang bridge. Resolution happens once at `ApplyStyles` time via `lipgloss.HasDarkBackground()`.
- `validate/config` validators emit warning diagnostics for unknown keys with hints — surface for old-token rename warnings.
- `notify` already uses `beeep.Notify`; `beeep.AppName` is a package var (no API change required).

### Task 2: Rebuild `ApplyStyles` with light/dark hex defaults and semantic accessors

The package mixes v1 lipgloss (`internal/ui/`) and v2 lipgloss (`internal/ui/cmdbrowser/`). The existing **string-typed `Color*()` accessors are the only sanctioned bridge** between them ([docs/internals/packages.md:56](../../docs/internals/packages.md#L56)). This shape must be preserved.

- [x] in `internal/ui/styles.go`, define 7 light/dark hex pairs as package-level `struct { Light, Dark string }` values per spec §1.2 (accent `#2EC3EB`/`#0EA5E9`, success `#22C55E`/`#16A34A`, warning `#F59E0B`/`#D97706`, danger `#EF4444`/`#DC2626`, muted `#9AA3BB`/`#64748B`, border `#334155`/`#CBD5E1`, text empty/empty). These are plain hex defaults, **not** `lipgloss.AdaptiveColor` — see the Light/dark resolution strategy in Technical Details for why.
- [x] rewrite `ApplyStyles` to:

For a non-empty hex, build with `lipgloss.NewStyle().Foreground(lipgloss.Color(<hex>))`. For an empty hex (the `text` zero-value default), build with `lipgloss.NewStyle().Foreground(lipgloss.NoColor{})` (or skip the `Foreground` call entirely) — explicit `NoColor` avoids any reliance on `lipgloss.Color("")` behavior and keeps the terminal default text color for `styleText`. User-set `text:` overrides this with a real foreground.

### Task 4: Update `config.styles` validator for the new surface

**Scope contract**: old-key diagnostics are emitted **only via `devbox validate`** (the `config.styles` validator). Normal command startup (`devbox`, `devbox cmd`, `devbox run …`, etc.) loads styles silently — only actual parse / read errors from `LoadStylesConfig` may surface to stderr, never rename warnings. ## Technical Details

- **Color palette source**: Tailwind-compatible hex values; verified contrast on common dark + light backgrounds.
- **Light/dark resolution strategy**: spec §1.2 defines a `{Light, Dark}` hex pair per token. Implementation does **not** use `lipgloss.AdaptiveColor` directly because the package-level `Color*()` accessors must return raw hex strings (they bridge v1 lipgloss inside `internal/ui/`, v2 lipgloss inside `internal/ui/cmdbrowser/`, and Fang's `ColorScheme` which takes hex strings). Instead, `ApplyStyles` calls `lipgloss.HasDarkBackground()` once and stores the chosen hex per token. User overrides apply identically to both modes. Re-running `ApplyStyles` after a profile change is the supported way to retheme.
- **Snapshot scope**: this work touches static styles and notification format only; no snapshot template scope changes.
- **Lock ordering**: no project-mutating commands touched.
- **Cobra completion safety**: no command-tree changes; completion remains config-blind through `completionConfigPath`.
- **Strictness**: `LoadStylesConfig` is lenient (`yaml.Unmarshal`, no `KnownFields`) and stays that way — unknown keys do not break the run. The validator (Task 4) is the loud surface for rename warnings via its own raw-YAML traversal of `colors:` (including the nested `colors.help:` sub-tree from the old schema) and `header:`. **There is no top-level `help:` key** — the old Fang scheme lived under `colors.help` ([internal/config/styles.go:55-56](../../internal/config/styles.go#L55)). This matches the existing pattern of lenient loaders + opt-in validators in `internal/validate/config/`.
