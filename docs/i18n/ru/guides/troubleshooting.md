# Диагностика проблем

Ваш стек перестал работать, деплой завис или `dwe status` светит красным там, где раньше был зелёный. Это руководство — карта триажа: куда смотреть первым делом, какая команда отвечает на какой вопрос и какие аварийные люки есть, когда обычный путь забит.

## Первый осмотр

Три команды покрывают девяносто процентов картины и ни одна не меняет состояние:

```shell
dwe validate
dwe status
dwe logs <сервис>
```

- `dwe validate` агрегирует все статические проверки — env-пробы, схему конфига, переводы и проектные preflight-проверки. Запускайте её первой; если красное — чините сначала это.
- `dwe status` сообщает здоровье контейнеров, состояние деплоя, состояние git-рабочей копии и любые отложенные переключения сервисов, ждущие деплоя. См. [`daily-workflow.md`](daily-workflow.md#быстрый-статус) о флагах секций и шорткатах.
- `dwe logs <сервис>` тянет docker-логи одного контейнера. См. [`daily-workflow.md`](daily-workflow.md#просмотр-логов).

Если `dwe validate` зелёный, а `dwe status` показывает конкретный сбой — переходите к соответствующей секции ниже.

## «Порт уже занят»

Host-порт, который DWE хочет опубликовать, занят другим процессом — другим проектом DWE, локальным dev-сервером, чем угодно, что привязано к этому порту.

Сначала диагностика:

```shell
dwe validate env
```

Проба `env.ports_free` перечисляет каждый конфликт с указанием номера занятого порта. Чтобы переназначить, переопределите порт в `workspace/local.yml` (машинно-локальный, gitignored). Оверлей делает глубокий мерж по записи, так что переписывайте только те порты, которые меняете:

```yaml
# workspace/local.yml
services:
  main:
    ports:
      http: 18080   # было 8080
```

Затем пере-деплой (или `dwe deploy run --service main`), чтобы изменение проехало через compose и обновило `dwe info`. Справочник: [`../reference/config/services/fields.md`](../reference/config/services/fields.md).

## «Docker не запущен»

`dwe validate env` снова первая остановка. Тут важны две пробы:

- `env.docker_bin` — бинарь `docker` не в `PATH` или нечитаем.
- `env.docker_daemon` — бинарь есть, но `docker info` не достучится до демона (Docker Desktop не запущен, права на сокет, недоступный remote-контекст).

Запустите Docker Desktop (или `systemctl start docker`, в зависимости от платформы), потом перезапустите `dwe validate env`. Если демон на нестандартном сокете, задайте `DOCKER_HOST` в шелле или через `workspace/local.yml`. Справочник: [`../reference/config/validate.md`](../reference/config/validate.md).

## «Контейнер не поднимается»

Деплой завершился, но сервис в нездоровом состоянии или перезагружается. Три команды сужают круг:

```shell
dwe logs <сервис>             # что контейнер реально говорит
dwe compose argv up <сервис>  # точная compose-argv, которую DWE собирает
dwe compose files             # список активных compose-файлов (с оверлеями)
```

Логи отвечают на «почему процесс упал?». Две `compose`-диагностики отвечают на «правильную ли compose-конфигурацию собрал DWE?» — удобно, когда локальный оверлей или неожиданный `extends:`-предок молча меняют то, что видит Docker. Справочник: [`../reference/config/docker.md`](../reference/config/docker.md).

## «Деплой постоянно падает»

Три подвопроса — три команды:

```shell
dwe deploy plan               # разрешённый список шагов для текущего состояния
dwe deploy state show         # журнал: что прошло, что упало и когда
dwe deploy state clear        # сбросить журнал и форсировать полный прогон
```

`dwe deploy plan` показывает деплой, который DWE сейчас реально запустит, включая шаги, которые будут пропущены из-за совпадений `config_hash` или неизменных входов. Если ожидаемый шаг пропускается — журнал объясняет, почему.

`dwe deploy state show` печатает зафиксированный результат последней попытки — статус по шагам, выдержки из ошибок и записанный `config_hash`. `dwe deploy state clear` удаляет `.dwe/deploy/state.yml`, чтобы следующий `dwe deploy` перепрогнал все шаги. Полезно, когда подозреваете, что неправ сам журнал, а не проект. Справочник: [`../reference/config/state/management.md`](../reference/config/state/management.md), [`../reference/config/state/hashing.md`](../reference/config/state/hashing.md).

## «Подтянул ветку коллеги — деплой говорит изменений нет, но сервис сломан»

Симптом: вы чек-аутнули ветку, которая меняет шаги деплоя, прогнали `dwe deploy`, и DWE пропустил почти всё, ссылаясь на отсутствие изменений. Или прогнал, но работающий контейнер всё ещё ведёт себя как до переключения.

Причина почти всегда — устаревший журнал деплоя: `.dwe/deploy/state.yml` хранит `config_hash`, который совпал с предыдущим чек-аутом, и пропускатель ему доверяет. Фикс — сбросить журнал и пере-деплоить:

```shell
dwe deploy state clear
dwe deploy
```

Если дело в одном сервисе — сузьте прогон:

```shell
dwe deploy run --service <имя>
```

Это же лечит случай, когда вы прыгали между ветками, переключающими разные опциональные сервисы — журнал не знает, что ваш `local.yml` под ним сдвинулся.

## «Ядерный вариант»

Когда стек залип настолько, что пошаговый разбор обходится дороже, чем начать заново:

```shell
dwe reset run
```

`dwe reset run` останавливает все контейнеры, удаляет их и прогоняет проектный reset-пайплайн (`workspace/reset.yml`). Что переживёт сброс — определяется проектом: обычно дерево `volumes/` с базами и кэшами остаётся, журнал и runtime-состояние — нет. Перед предположениями прочтите проектный `reset.yml` (и `dwe reset plan` для разрешённого списка шагов).

Если нужно стереть stateful-данные — соглашайтесь явно. Проектный reset-пайплайн может выставить шаг `docker_remove_project_volumes` — проверьте `dwe reset plan` — или удалите `volumes/` руками после чистой остановки.

**Перед любым деструктивным reset делайте снапшот.** Даже одной строкой `dwe snapshot create pre-reset` вы получаете откат, если reset окажется агрессивнее ожидаемого. См. [`switching-tasks-with-snapshots.md`](switching-tasks-with-snapshots.md) о поверхности снапшотов.

Справочник: [`../reference/config/reset.md`](../reference/config/reset.md).

## Аварийный люк: `dwe compose raw`

Когда обёртка DWE мешает — нужен флаг, который DWE не пробрасывает, или хочется проверить, проблема в DWE или в самом compose:

```shell
dwe compose raw -- ps -a
dwe compose raw -- exec main env
dwe compose raw -- config
```

`dwe compose raw` — низкоуровневый сквозной проброс: DWE разрешает список compose-файлов и имя проекта, а остальную argv передаёт `docker compose` как есть. Никаких policy-аргументов, никаких оверлеев сверх тех, что уже на диске. Используйте как диагностику, не как повседневный инструмент — высокоуровневые команды `dwe` существуют не зря — но это правильный инструмент, когда вы дебажите сам DWE или воспроизводите проблему напрямую через compose CLI. Справочник: [`../reference/config/docker.md`](../reference/config/docker.md).
