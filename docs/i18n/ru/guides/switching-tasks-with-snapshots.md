# Переключение задач через снапшоты

Вы посередине фичи: накат миграций наполовину, наседаны тестовые данные — и тут на `main` падает хотфикс. Нужен чистый стек, чтобы воспроизвести баг, пофиксить его и вернуться ровно туда, где вы были: те же строки в БД, тот же индекс поиска, тот же `local.yml`. Это руководство — поваренная книга для такого сценария.

Снапшоты — это механизм чек-пойнтов DWE. Они захватывают изменяемые данные проекта (БД, поисковые индексы, журнал деплоя, `workspace/local.yml`) в именованный каталог под `./snapshots/<имя>/` и позволяют восстановить их позже как мягкую операцию — без `reset`, без пересоздания контейнеров, без перепрогона деплоя.

## Шаблон `baseline`

Выберите один снапшот на стабильную стартовую точку и держите его. Распространённая форма:

- `baseline` — known-good почти пустое состояние, в которое всегда можно откатиться (чистые seed-данные, никаких незавершённых миграций).
- `wip-<branch>` — per-task чек-пойнт, который вы создаёте, когда надо переключиться с in-progress работы.

`baseline` — это просто обычное имя снапшота. Зарезервированного в нём ничего нет — конвенция окупается тем, что каждое руководство и каждая привычка может ссылаться на «восстановить baseline» однозначно.

Создайте один раз, сразу после чистого деплоя:

```shell
dwe snapshot create baseline -d "чистое состояние после деплоя"
```

## Полный цикл «фича на паузе из-за хотфикса»

```shell
# 1. чек-пойнт in-flight работы по фиче
dwe snapshot create wip-feature-x -d "WIP: фича X, миграции применены"

# 2. чистая база под хотфикс
dwe snapshot restore baseline

# 3. ... воспроизвести, пофиксить, запушить, смерджить хотфикс ...

# 4. вернуться туда, где были
dwe snapshot restore wip-feature-x
```

Restore — это по конвенции **drop + restore**: проектная команда `db.restore` обычно дропает целевую базу и перезаливает её из `${snapshot.path}/db/main.sql.gz`. Контейнеры не пересоздаются, шаги деплоя не выполняются — меняются только данные и файлы workspace.

`workspace/local.yml` входит в снапшот, но всё, объявленное под `local_yml.preserve_keys` в `workspace/snapshot.yml` (порты, хосты, пути — см. [`write-snapshot-workflows.md`](write-snapshot-workflows.md)), вшивается обратно из вашей текущей копии, так что машинно-локальные оверрайды переживают свап.

## Откат одной командой через `rollback_target`

Если вы часто переключаетесь на `baseline` (или другой «безопасный» снапшот), объявите его как rollback-цель в `workspace/snapshot.yml`:

```yaml
# workspace/snapshot.yml
rollback_target: baseline
```

Тогда `dwe snapshot rollback` — это шорткат для `dwe snapshot restore baseline` — полезно в мышечной памяти и в скриптах. Команда явно падает, если целевого снапшота нет. Справочник: [`../reference/config/snapshot.md`](../reference/config/snapshot.md).

## Изучение того, что есть

```shell
dwe snapshot list                  # всё под ./snapshots/
dwe snapshot current               # что создано или восстановлено последним
dwe snapshot inspect wip-feature-x # содержимое манифеста: описание, артефакты, набор сервисов, config_hash
```

`inspect` — это то, к чему обращаются, когда не уверены, что снапшот ещё актуален: он показывает зафиксированный набор сервисов, `config_hash` на момент создания, размеры и sha256 каждого артефакта.

## Передача снапшота коллеге

Снапшоты — локальные файлы, но они аккуратно пакуются и распаковываются:

```shell
# производитель
dwe snapshot pack wip-feature-x
# → ./snapshots/wip-feature-x.tar.gz

# потребитель
dwe snapshot unpack ./snapshots/wip-feature-x.tar.gz
dwe snapshot restore wip-feature-x
```

`pack` пишет один `.tar.gz` (никакого сайдкар-чексумм-файла). `unpack` верифицирует каждый артефакт архива против записанного в манифесте sha256, прежде чем переместить дерево в `./snapshots/`. Если что-то не прошло верификацию — будет промт перед тем, как снапшот ляжет; отказ оставляет рабочее дерево нетронутым.

Когда эффективный набор сервисов получателя расходится с набором, записанным в снапшоте, restore поднимает диф через политику `services_mismatch` (`warn` по умолчанию, можно поднять до `block` в `workspace/snapshot.yml`). Справочник: [`../reference/config/snapshot.md`](../reference/config/snapshot.md).

## Что снапшот НЕ делает

Стоит проговорить явно, потому что каждый из этих пунктов хотя бы раз кого-то кусает:

- **Не пересоздаёт контейнеры.** Restore меняет файлы данных и конфиг workspace; работающие контейнеры продолжают работать с тем образом и конфигом, с которыми были подняты. Если снапшот делался против другого тэга образа — работающий контейнер теперь подаёт устаревший код против новых данных.
- **Не повторяет деплой.** `.dwe/deploy/state.yml` перезаписывается зафиксированным журналом снапшота, но описанные в нём шаги не выполняются заново. Если снапшот сделан до того, как в `workspace/deploy.yml` появился новый шаг — на restore этот шаг не запустится; запустит его `dwe deploy` при следующем вызове.
- **Не делает reset.** Volumes, untracked-файлы в дереве проекта и всё за пределами артефактов, которые ваш `create:` явно захватил, не трогаются. Restore аддитивен поверх того, что сейчас на диске.
- **Никакой магии на уровне данных.** Ядро снапшота не знает, что такое база. Ваши `create:` и `restore:` вызывают ваши же команды `db.dump` / `db.restore`; если они дропают и перезаливают — restore дропает и перезаливает. Если аппендят — restore аппендит.

Когда нужна по-настоящему чистая база, для этого есть `dwe reset run` — см. [`troubleshooting.md`](troubleshooting.md#ядерный-вариант). Распространённый шаблон — `snapshot create pre-reset` непосредственно перед `reset run`, чтобы был откат, если reset окажется агрессивнее ожидаемого.
