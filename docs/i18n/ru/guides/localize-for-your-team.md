# Локализация под вашу команду

Ваша команда работает по-русски, по-немецки, по-французски — на любом языке, кроме английского. DWE поставляется с английской базой для своей поверхности, но каждую пользовательскую команду, которую вы написали (`dwe db.seed`, `dwe build.docker`, …), и каждый заголовок секции в сгенерированной документации можно перевести per-project, бок о бок с английским источником.

Это руководство проходит по тому, где живут переводы, что переводится и что остаётся английским, рабочий пример и как переключать локаль без правки файлов. Полный справочник ключей — в [i18n reference](../reference/config/i18n.md).

## Разрешение локали

DWE выбирает активную локаль из четырёх источников, по убыванию приоритета:

1. **Флаг `--lang`** на любой подкоманде `dwe docs` (`show`, `list`, `search`, `export`, `generate`, `llms-txt`). Per-invocation, никогда не сохраняется.
2. **Переменная окружения `DWE_LANGUAGE`.** Перекрывает поле `language` userconfig для одного шелла или одной команды.
3. **Поле `language` в userconfig** (`~/.config/dwe/config` или `.dwe/config`). Поставьте это один раз per-developer, чтобы зафиксировать предпочтительную локаль.
4. **Системный `$LANG`** — парсится в 2-буквенный код (`ru_RU.UTF-8` → `ru`). `C` и `POSIX` игнорируются, и цепочка продолжается.
5. **Дефолт:** `en`.

Коды вида `ru-RU`, `ru_RU` или `ru_RU.UTF-8` нормализуются до `ru` на каждом слое. Пустые входы пропускаются.

На практике большинство разработчиков один раз кладут `language: ru` (или какой угодно код) в userconfig и забывают. `DWE_LANGUAGE` и `--lang` — это аварийные люки для одноразовых оверрайдов.

## Раскладка файлов

Переводы — это проектные YAML-файлы под `workspace/i18n/`. Глобальной или user-уровневой папки переводов нет — каждый проект отгружает свои.

```
workspace/
  i18n/
    ru.yml
    de.yml
    fr.yml
```

Имя файла — 2-буквенный код языка. Отсутствующая папка `workspace/i18n/` молча трактуется как «только английский» — ни ошибки, ни предупреждения.

Файлы переводов используют **строгий YAML-декод**: неизвестный ключ (`descripton:` вместо `description:`) не загрузится, и `dwe validate` выдаст чёткую ошибку. Опечатки не проскальзывают молча.

## Что переводится

YAML-стор переводов несёт три бакета строк:

| Семейство ключей | Покрывает |
|------------------|-----------|
| `commands.<id>.description` | однострочное описание, показываемое в `dwe commands list` и `dwe <id> --help` |
| `commands.<id>.confirmation_text` | промт перед запуском деструктивной команды (при `confirmation: true`) |
| `commands.<id>.messages.success` / `.error` | строки, печатаемые при успехе/провале, когда у команды задан `messages:` |
| `commands.<id>.params.<name>.description` | help-текст для каждого объявленного параметра |
| `commands.<id>.params.<name>.options.<value>` | per-value лейблы для enum-style params (например, `prod: "Production"`) |
| `groups.<id>.title` / `.description` | заголовок группы команд и её описание в TUI-браузере |
| `ui.docs.section.*` / `ui.docs.property.*` | заголовки секций и лейблы свойств, эмитимые `dwe docs generate` и таблицами свойств в `dwe commands <id>` |

ID команды в `commands.<id>` — та же точечная форма, что и в шелле: `workspace/commands/db/seed.yml` → `commands.db.seed`. ID групп следуют той же path-based конвенции.

Все поля опциональны. Опустите любой ключ — DWE фолбэкнется на английское значение из YAML-источника команды (или встроенный английский baseline для `ui.*`). Частичные переводы — нормально: переведённые и непереведённые строки сосуществуют в одном выводе без предупреждения.

## Что НЕ переводится

Вне скоупа YAML-стора:

- **Собственные Cobra-команды DWE.** `dwe deploy --help`, `dwe run --help`, `dwe docs --help` и каждая встроенная команда остаются английскими независимо от локали. Стор переводов покрывает только проектные пользовательские команды.
- **Runtime-ошибки и логи.** Они машинно-читаемые и всегда английские, чтобы их можно было грепать и копипастить в issue-трекеры без сюрпризов.
- **Длинная справочная документация** под `docs/reference/` и `docs/internals/`. Она переводится через отдельный **markdown**-неймспейс по адресам `docs/i18n/<lang>/reference/...` и `docs/i18n/<lang>/internals/...`. Другой загрузчик, другой валидатор, другой формат файлов — два неймспейса не сливаются. См. [i18n reference — long-form documentation translations](../reference/config/i18n.md#long-form-documentation-translations).

Разделение скоупов даёт каждому из них двигаться независимо: можно отгрузить русские переводы команд `dwe db.seed` команде, не дожидаясь полного перевода справочника.

## Рабочий пример

**Английский источник** — канонический YAML команды:

```yaml
# workspace/commands/db/seed.yml
- id: db.seed
  description: "Seed the database with fixture data"
  confirmation: true
  confirmation_text: "Wipe and re-seed the database?"
  messages:
    success: "Database seeded"
    error: "Seeding failed"
  params:
    - name: env
      description: "Target environment"
      options:
        - dev
        - staging
  type: service_exec
  service: db
  cmd: "/usr/local/bin/seed --env ${env}"
```

**Русский перевод** — та же форма под `commands.db.seed`:

```yaml
# workspace/i18n/ru.yml
ui:
  docs.section.parameters: "Параметры"
  docs.section.command: "Команда"
  docs.property.workdir: "Рабочая директория"

commands:
  db.seed:
    description: "Заполнить базу тестовыми данными"
    confirmation_text: "Очистить и заново заполнить базу?"
    messages:
      success: "База заполнена"
      error: "Не удалось заполнить базу"
    params:
      env:
        description: "Целевое окружение"
        options:
          dev: "Разработка"
          staging: "Стейджинг"

groups:
  db:
    title: "База данных"
    description: "Команды управления базой данных"
```

Три вещи, на которые стоит обратить внимание:

- YAML-источник команды остаётся 100% английским. Авторы и переводчики работают над разными файлами и никогда не сталкиваются.
- `confirmation_text` переводится, но базовый переключатель `confirmation: true` остаётся в источнике — переводы несут *строки*, а не поведение.
- Блок `ui:` опциональный. Если его пропустить, генерируемая документация использует английские заголовки секций — частичное покрытие в норме.

После сохранения `ru.yml`, запустите:

```sh
DWE_LANGUAGE=ru dwe commands list   # → "Заполнить базу тестовыми данными"
DWE_LANGUAGE=ru dwe db.seed --help  # → переведённое описание + params
```

## Валидация

`dwe validate` проверяет каждый файл под `workspace/i18n/`. Три класса находок:

| Находка | Severity | Что значит |
|---------|----------|------------|
| ошибка парсера | error | строгий декод поймал неизвестное поле или YAML-синтаксис — починить файл |
| orphan-запись | warning | `commands.<id>` ссылается на команду, которой больше нет в `workspace/commands/` — переименовать или удалить запись |
| неизвестный UI-ключ | warning | ключ `ui.*`, которого нет в каноническом whitelist — открыть issue, если нужен новый |

Warning-и по умолчанию информативны. Чтобы они блокировали CI:

```sh
dwe validate --strict
```

Чтобы целиться только в домен i18n:

```sh
dwe validate translations
```

Валидация работает рано (preflight), так что битый файл переводов не всплывает посреди прогона деплоя.

## Переключение per-invocation

Для быстрых перепрыгов между локалями без правки конфига:

```sh
# Одна команда по-русски
DWE_LANGUAGE=ru dwe commands list

# Целая сессия шелла по-немецки
export DWE_LANGUAGE=de
dwe commands list      # немецкий
dwe db.seed --help     # немецкий

# Явный --lang на docs-подкоманде всегда побеждает
DWE_LANGUAGE=de dwe docs show config/services/fields --lang ru
# → рендерит русский перевод независимо от DWE_LANGUAGE
```

`DWE_LANGUAGE` слотится **выше** поля `language` userconfig и **ниже** флага `--lang`. Этот порядок позволяет разработчику зафиксировать дефолт в userconfig, переопределить его для одного терминала через env-переменную и всё равно получить явный `--lang ru` для одноразовой справки.
