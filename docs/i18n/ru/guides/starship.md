# Интеграция со Starship

Используйте `dwe prompt`, чтобы рендерить компактный, проектно-ориентированный сегмент внутри промта [Starship](https://starship.rs/).

## Обзор

`dwe prompt` печатает одну строку для текущего рабочего каталога шелла:

```
{▪} my-project ✓ ●
```

Полная форма вывода (каждый хвостовой сегмент независимо опционален):

```
{▪} <проект> [<сервис>] <иконка-деплоя> <иконка-стека>
```

- `{▪}` — логомарка DWE; внутренний квадрат окрашен токеном `accent` проекта из `workspace/styles.yml`.
- `<проект>` — `project.name` из `workspace.yml`, с откатом на basename каталога.
- `[<сервис>]` — присутствует, когда `cwd` находится под исходным каталогом сервиса. Для каждого `workspace/services/<name>/` поле `dir:` из `service.yml` разрешается относительно корня проекта и сопоставляется с `cwd` (выигрывает самое глубокое совпадение на вложенных раскладках; цепочка `extends:` разворачивается, когда у потомка нет собственного `dir`). Сервисы, чей `dir:` разрешается в корень проекта (`dir: .`) или за его пределы (`dir: ..`, абсолютные пути вне корня), молча пропускаются. Рамка из скобок — простая; внутреннее имя санитизируется. Один `os.ReadDir` плюс одно небольшое чтение YAML на сервис на каждый вызов промта — субмиллисекундно на типичных проектах; файлы `service.yml` крупнее 64 KB пропускаются на горячем пути.
- `<иконка-деплоя>` — `✓`/`⟳`/`⚠`/`✗`, отражает журнал состояния деплоя в `.dwe/deploy/state.yml`. Опущена, когда деплой-стейта нет.
- `<иконка-стека>` — `●`/`◐`/`○`, отражает живое состояние контейнеров. Подложкой служит `.dwe/prompt-cache.yml` (см. [Иконка стека](#стека)). Опущена, когда ни кэш, ни обновление не выдают значение.

Стабильно гарантирован только префикс `{▪} <проект>` — любой другой хвостовой сегмент может отсутствовать в зависимости от состояния проекта.

Когда шелл находится за пределами какого-либо DWE-проекта, команда завершается с кодом `1` и ничего не печатает — Starship скрывает сегмент через предикат `when =`.

`dwe prompt` — горячий путь для промта шелла: он минует cobra, валидацию конфига и lipgloss полностью. Бюджет cold-старта существенно меньше 50 мс на современной машине.

## Установка

Добавьте следующий блок в `~/.config/starship.toml`:

```toml
[custom.dwe]
command = "dwe prompt"
when    = "dwe prompt --check"
format  = "[$output]($style) "
style   = "bold"
description = "DWE project status"
```

Предикат `when = "dwe prompt --check"` — молчаливый и только по exit-коду: Starship вызывает его раз на промт, чтобы решить, показывать ли сегмент. Форма `command` делает собственно рендеринг и эмитит окрашенный сегмент в stdout.

## Кастомизация

`dwe prompt` окрашивает только логомарку и иконки — скобки, имя проекта, тег сервиса и окружающие пробелы остаются простыми. Это оставляет остальное свободным под `style` и `format` Starship — можно перестилизовать без борьбы со встроенным ANSI:

```toml
[custom.dwe]
command = "dwe prompt"
when    = "dwe prompt --check"
format  = "via [$output]($style) "
style   = "dimmed cyan"
```

Эскейпы цвета внутри сегмента используют `\x1b[39m` (только дефолтный foreground) — они не сбрасывают окружающие атрибуты.

## Иконка деплоя

Вычисляется в этом порядке приоритетов — выигрывает первое совпадение:

| Порядок | Условие | Иконка | Цветовой токен |
| --- | --- | --- | --- |
| 1 | деплой `status: failed` | `✗` | `danger` |
| 2 | деплой `status: partial` | `⚠` | `warning` |
| 3 | есть незакрытые изменения (блок `pending`) | `⟳` | `warning` |
| 4 | деплой `status: deployed` | `✓` | `success` |
| 5 | нет состояния / `not_deployed` / ошибка парсинга | _(опущена)_ | — |

Failed и partial идут впереди pending, чтобы промт первым делом сигнализировал о поломанном состоянии — нужно знать, что что-то сломано, *прежде чем* думать о применении ожидающих изменений.

## Иконка стека

Иконка стека отражает живое состояние Docker-контейнеров. Она независима от иконки деплоя — проект может показывать `✓ ○` (деплой успешен, контейнеры остановлены вручную).

| Состояние | Глиф | Цветовой токен | Смысл |
| --- | --- | --- | --- |
| running | `●` | `success` | все ожидаемые контейнеры подняты |
| partial | `◐` | `warning` | часть контейнеров поднята, часть остановлена |
| stopped | `○` | `muted` (дефолт промта `#6B7280`; переопределяется через `colors.muted` в `workspace/styles.yml`) | ни один контейнер не работает |
| _(нет)_ | — | — | нет кэша и обновление не выдало пригодного значения |

### Кэш

Состояние читается из stale-while-revalidate-кэша в `.dwe/prompt-cache.yml`:

```yaml
updated_at: 2026-06-03T12:34:56Z   # RFC3339 UTC
state: running                      # running | partial | stopped
```

- **TTL**: 2 минуты. Чтения свежего кэша — чистый файловый ввод-вывод, без `docker ps`.
- **Stale или отсутствует**: промт вызывает `docker ps -q --filter label=com.docker.compose.project=<project>` с **жёстким тайм-аутом 150 мс**. По тайм-ауту или любой ошибке запись в кэш не происходит.
- **Атомарная запись**: tmp-файл + rename в том же каталоге, поэтому конкурирующие промты не могут повредить файл.

### Карта писателей

Разные места знают про стек разное. Каждое выбирает безопасное действие — пишет, если уверено, инвалидирует, если scope ограничен, никогда не врёт:

| Место | Действие |
| --- | --- |
| `dwe run` | пишет `running` |
| `dwe restart` (без аргумента-сервиса) | пишет `running` |
| `dwe restart <service>` | инвалидирует (удаляет файл кэша) |
| `dwe stop` (без `--service`) | пишет `stopped` |
| `dwe stop --service <n>` | инвалидирует |
| `dwe deploy run` (без `--service`) | инвалидирует (deploy может стать no-op через «already up-to-date») |
| `dwe deploy run --service <n>` | инвалидирует |
| `dwe reset run` (project-wide teardown) | пишет `stopped` |
| `dwe reset run --service <n>` | инвалидирует |
| `dwe services enable/disable --apply` | пишет `running` (после того как весь план toggle, включая after-хуки, завершён) |
| `dwe status` (верхнего уровня) | пишет точный агрегированный `Health` (`running`/`partial`/`stopped`) |
| `dwe status <subcommand>` | не пишет (scope ограничен секцией) |
| `dwe snapshot restore` / `rollback` | инвалидирует (пост-restore состояние произвольное) |
| `dwe prompt` (sync refresh) | пишет `running`, если `docker ps` вернул > 0 — **никогда `stopped`** |

### Правило no-downgrade при prompt refresh

Собственный sync-refresh `dwe prompt` пишет только `running`. Нулевой результат `docker ps` неотличим между:

- по-настоящему остановленным стеком, и
- неправильным лейбл-фильтром (шаблонизированный `docker.yml.project_name` промтом не загружается — см. [Известные ограничения](#известные-ограничения)).

Разрешить prompt refresh писать `stopped` означало бы либо (а) даунгрейднуть корректный `running`, оставленный авторитетным писателем (lifecycle / status), либо (б) записать неверный `stopped` в отсутствующий кэш после инвалидации. Резервирование записи `stopped` за авторитетными писателями делает кэш честным.

Запись в кэш всюду — best-effort: ни prompt refresh, ни lifecycle-команды не падают при ошибках I/O. Кэш — это observability, а не correctness.

## Поведение в терминалах без цвета

`dwe prompt` следует [спецификации NO_COLOR](https://no-color.org/): если переменная окружения `NO_COLOR` установлена в *любое* значение (включая пустую строку), все ANSI-эскейпы подавляются и вывод состоит только из обычных рун.

```
{▪} my-project ✓ ●
```

## Известные ограничения

- **Автодетект светлой/тёмной темы**: промт всегда использует тёмный вариант палитры. Большинство терминалов тёмные; поддержка светлых терминалов может быть добавлена позже через `COLORFGBG`, если будет спрос.
- **Нет флага `-c`**: `dwe prompt` всегда поднимается вверх от `$PWD`. Это намеренно — промт шелла отражает текущий каталог шелла, а не произвольный указатель на проект.
- **Кастомный бинарь docker**: `binaries.docker: podman` (или любое не-`docker` значение) минует обновление, инициированное промтом — `shared/prompt` хардкодит `docker`, чтобы держать горячий путь свободным от конфига. Lifecycle-команды и `dwe status` всё ещё пишут кэш с правильным бинарём, так что иконка остаётся точной при активном использовании; только 2-минутное обновление в idle — no-op.
- **Шаблонизированное имя compose-проекта**: проекты, у которых `workspace/docker.yml` задаёт `project_name` шаблоном (например, `${project.prefix}_${project.name}`), увидят `docker ps` с нулём строк при prompt refresh, потому что `shared/prompt` не загружает `docker.yml`. В сочетании с правилом no-downgrade, prompt refresh просто ничего не пишет — иконка остаётся корректной, пока lifecycle-команды и `dwe status` (которые знают настоящее compose-имя) держат кэш заполненным.
- **Ручной `docker stop` вне dwe**: не детектируется prompt refresh (правило no-downgrade). Запустите `dwe status`, чтобы обновить закэшированное состояние.
- **Сервисы без `dir:`**: tool/infra-сервисы (и любое приложение без mount-а исходников) никогда не появляются как `[<сервис>]` в промте — у них нет каталога исходников, под которым может находиться `cwd`. Промт всё ещё нормально рендерит проект, деплой и стек.
- **Symlink-пути**: `dwe prompt` не вызывает `filepath.EvalSymlinks` ни для `cwd`, ни для разрешённого `dir:`. Если `cwd` достигнут через symlink, а `dir:` указывает на канонический путь (или наоборот), тег сервиса молча исчезает. Используйте настоящие пути в `service.yml`'s `dir:`, чтобы избежать сюрпризов.
- **Quoting в разных шеллах**: sh, bash и zsh принимают строки `command` / `when` как есть. Пользователям fish может потребоваться скорректировать кавычки в `starship.toml`, если конфиг Starship оборачивает команды иначе.

## До / после

Без сегмента:

```
~/code/my-project ❯
```

С сегментом (корень проекта):

```
{▪} my-project ✓ ● ~/code/my-project ❯
```

С сегментом (внутри исходного каталога сервиса `api` — при условии, что в `workspace/services/api/service.yml` задано `dir: ./services/api`):

```
{▪} my-project [api] ✓ ● ~/code/my-project/services/api ❯
```

(Логомарка DWE и иконки окрашены в реальных терминалах.)
