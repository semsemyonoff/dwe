# Создание нового проекта с `dwe init`

Вы хотите завести под DWE совершенно новый проект. `workspace.yml` ещё нет, а собирать конфигурацию файл за файлом вручную утомительно и легко ошибиться в мелочах. `dwe init` делает начальную раскладку за вас: одна команда создаёт минимальный, но полноценный проект, который при первом же запуске чисто загружается и проходит `dwe validate`.

Это зеркальное отражение [Подключения к проекту DWE](joining-a-project.md): то руководство — про репозиторий, в котором конфигурация DWE уже есть; это — про создание такой конфигурации с нуля.

## Для чего нужен `dwe init`

`dwe init` — единственная команда DWE, которая работает **вне** проекта: она его создаёт, а не действует внутри. Она:

- **С мнением, но инертна.** Создаёт реальный рабочий стартовый набор (один активный сервис `app`, встроенные пайплайны deploy/lifecycle) плюс набор закомментированных файлов-переопределений, в которые можно врастать. Ничего полунастроенного она не оставляет.
- **Идемпотентна.** Заполняет пробелы и никогда не перезаписывает существующий файл без `--force`, поэтому её безопасно перезапускать на частично настроенном каталоге.
- **Не трогает состояние машины.** Проекта ещё нет, поэтому никаких preflight-проверок и блокировок — только файловая система.

## Интерактивный запуск

В пустом каталоге просто выполните:

```shell
dwe init
```

Короткая форма спросит:

- **Имя проекта** (обязательно) — пишется в `workspace.yml` как `project.name`.
- **Префикс compose** (по умолчанию `dwe`) — `project.prefix`, который разводит ваши Docker-ресурсы по пространствам имён.
- **Брендирование** (необязательно) — заголовок, слоган и акцентный цвет, попадающие в `workspace/styles.yml`. Оставьте пустыми для обобщённого заголовка; [оформить](brand-your-project.md) можно и позже.

Вся форма собирается до записи на диск, так что `Ctrl-C` посреди формы оставит каталог нетронутым.

## Неинтерактивный запуск

`dwe init` автоматически переходит в режим, управляемый флагами, когда stdin/stdout не TTY (CI, скрипты, пайпы), либо когда передан `--yes` или `--output json`. Всё задаётся флагами:

```shell
dwe init --name my-project --prefix acme --service api
```

Либо взять все значения по умолчанию без формы:

```shell
dwe init my-project --yes
```

Позиционный `[name]` создаёт проект в `./<name>/`, а не в текущем каталоге. Приоритет разрешения имени: `--name` → позиционный `[name]` → имя текущего каталога.

### Флаги

| Флаг | По умолчанию | Эффект |
| --- | --- | --- |
| `--name` | аргумент `[name]`, иначе имя каталога | имя проекта в `workspace.yml` |
| `--prefix` | `dwe` | префикс compose/проекта |
| `--brand-title` / `--tagline` / `--accent` | пусто | брендирование `workspace/styles.yml` |
| `--service` | `app` | имя папки стартового сервиса; `""` — не создавать |
| `--force` | выкл | перезаписывать существующие файлы вместо пропуска |
| `-y, --yes` | выкл | пропустить форму, взять значения по умолчанию |
| `--output json` | текст | машиночитаемый отчёт (подразумевает неинтерактивный режим) |

С `--output json` вместо прозы вы получаете структурированный отчёт:

```json
{
  "target": "/abs/path/to/project",
  "created": ["workspace.yml", "workspace/defaults.yml", "..."],
  "skipped": [],
  "symlink_fallback": false,
  "nested_warning": false
}
```

`skipped` перечисляет уже существовавшие файлы (оставленные как есть), `symlink_fallback` равен true, когда `CLAUDE.md` пришлось записать копией вместо символической ссылки, а `nested_warning` — true, когда выше по дереву найден `workspace.yml`.

## Что появляется на диске

```
<target>/
├─ workspace.yml        project.name + project.prefix (+ закомментированные опциональные поля)
├─ compose.yaml         базовый compose-файл, на который ссылается defaults.yml
├─ .gitignore           записи DWE для runtime (дописываются, если файл уже есть)
├─ .editorconfig        соглашения репозитория (пишется только при отсутствии)
├─ AGENTS.md            краткий промпт о проекте для ИИ-агентов
├─ CLAUDE.md          → симлинк на AGENTS.md (копия там, где симлинки недоступны)
├─ .dwe/
│  └─ config            закоммиченный, полностью закомментированный шаблон пользовательской конфигурации
└─ workspace/
   ├─ defaults.yml      переключатель стартового сервиса + закомментированные примеры runtime/exports
   ├─ styles.yml        брендирование из формы + закомментированный остаток
   ├─ deploy.yml        инертная копия встроенного пайплайна deploy
   ├─ lifecycle.yml     инертная копия встроенного пайплайна lifecycle
   ├─ info.yml          инертная копия конфигурации дашборда
   ├─ docker.yml        инертная копия политики compose
   └─ services/app/
      └─ service.yml    type + container активны, остальные поля закомментированы
```

Два момента стоит понимать:

- **Файлы-переопределения специально приходят закомментированными.** Композиция пайплайнов DWE — это *полная замена*: активный `workspace/deploy.yml` заменяет весь встроенный пайплайн deploy, поэтому наполовину отредактированный файл молча теряет фазы. Поэтому `deploy.yml`, `lifecycle.yml`, `info.yml` и `docker.yml` приходят полностью закомментированными; встроенный дефолт остаётся активным, пока вы сознательно не раскомментируете и не возьмёте на себя весь пайплайн. В шапке каждого файла есть указатель на авторитетный дефолт, который он отражает.
- **`.gitignore` дополняется, а не перезаписывается.** Если в каталоге уже есть `.gitignore`, `dwe init` дописывает только недостающие строки DWE под маркером `# dwe`. Повторный запуск ничего не меняет. Runtime-подкаталоги (`.dwe/deploy/`, `.dwe/snapshots/`, `.dwe/logs/`, `.dwe/prompt-cache.yml`) игнорируются по отдельности, чтобы закоммиченный шаблон `.dwe/config` оставался под контролем git.

## После init

```shell
dwe validate     # убедиться, что свежий проект внутренне согласован
dwe deploy run   # поднять стартовый стек
```

Свежий `dwe init` рассчитан на то, чтобы немедленно проходить валидацию. Дальше — обычный путь авторства: [добавить сервис](add-a-service.md), [написать команды проекта](author-project-commands.md), [оформить дашборд](brand-your-project.md) и раскомментировать файл-переопределение, когда действительно нужно перекроить пайплайн.

## Граничные случаи

- **Существующие `.gitignore` / `.editorconfig`.** `.gitignore` дополняется; `.editorconfig` пишется только при отсутствии. Ни один не затирается.
- **Вложенные проекты.** Если в каталоге выше уже есть `workspace.yml`, `dwe init` предупреждает (`nested_warning` в JSON), но не блокирует — иногда вложенный проект и нужен.
- **Без стартового сервиса.** `--service ""` создаёт валидный проект без сервисов; сервисы добавляются позже папками под `workspace/services/`.
- **Симлинки в Windows.** Там, где `CLAUDE.md` нельзя сделать символической ссылкой на `AGENTS.md`, он записывается копией, и запуск отмечает этот fallback.
