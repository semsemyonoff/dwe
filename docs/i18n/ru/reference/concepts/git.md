## Два сервиса имеют рабочее дерево

Проект DWE имеет *собственный* Git-репозиторий в корне проекта — тот, что отслеживает `workspace.yml`, дерево конфигурации `workspace/` и оверлеи `compose/`. Большинство проектов также несут один или несколько прикладных сервисов, исходный код которых живёт под `<svc.Dir>/src/`. По конвенции каждый такой сервис владеет отдельным Git-выгрузкой в `<svc.Dir>/src/.git/`.

DWE обращается с этими двумя слоями одинаково: он никогда не предполагает, что в корне проекта живёт конкретная VCS, и никогда не лезет в репозиторий одного сервиса, чтобы узнать о другом. Каждая Git-операция либо нацелена на корень проекта (проба обновления), либо нацелена ровно на один `<svc.Dir>/src/` (рендеринг хуков, проба рабочего пространства). Глобальной поверхности «забрать всё» нет.

CLI шеллит в хостовый бинарник `git`. Путь бинарника разрешается через стандартный аксессор (`config.GitBin(cfg)`), так что проект может закрепить конкретную версию через `binaries.git` в `workspace.yml` при необходимости. Пусто означает «искать `git` в `$PATH`».

## Рендеринг хуков

`dwe render git` рендерит shell-хуки в директорию `<svc.Dir>/src/.git/hooks/` каждого включённого сервиса из template-пака под `workspace/templates/git/`.

Механизм такой же, как у `render ide` и `render ai` — та же модель выбора, та же цепочка разрешения пака, те же защитники path-safety, та же схема манифеста. Три вещи отличают рендеринг Git-хуков:

- **Назначение находится внутри `.git/`**, которое Git никогда не отслеживает. Отрендеренные файлы не коммитятся; повторный рендеринг — источник истины. Ручное редактирование `src/.git/hooks/pre-commit` с расчётом, что изменения переживут, — категориальная ошибка.
- **Манифестный `to` ограничен basename'ами**, потому что Git не рекурсирует в поддиректории `hooks/`. Манифестная строка вида `to: subdir/pre-commit` отвергается на загрузке.
- **Дефолт активации совпадает с `render ide`**: только сервисы `type: app` рендерят хуки по умолчанию. Tool и infra сервисы явно соглашаются через `services.<name>.render.git.enabled: true`.

Сквозной поток на сервис:

1. **Гейт активации.** Оба `services.<name>.enabled` и `services.<name>.render.git.enabled` должны быть true (политический дефолт зависит от типа сервиса).
2. **Преflight хаба.** `<svc.Dir>` должен разрешиться внутрь корня проекта и не достигаться через симлинк.
3. **Проба директории git.** `<svc.Dir>/src/.git` должен быть директорией. Обычный файл (указатель `gitdir:` от `git worktree` или субмодуль) приводит к пропуску сервиса с предупреждением — см. [Worktrees and submodules](../render/git.md#worktrees-and-submodules) в справочнике команд. Отсутствующий `.git/` тоже пропускается с предупреждением.
4. **Разрешение коллизий.** Когда два сервиса делят один `<svc.Dir>` (обычно базовый `main` и `extends:`-потомок `main-debug`), побеждает самый глубокий extender.
5. **Разрешение пака.** `render.git.template` закрепляет пак; иначе цепочка пробует `workspace/templates/git/<service-name>/`, затем `workspace/templates/git/default/`.
6. **Per-file рендер.** Каждая запись в `manifest.yml` пака читается, вычисляется как [строгий Go text template](../templates.md), пишется в `<svc.Dir>/src/.git/hooks/<basename>` и получает `chmod 0755` на каждом запуске.

Полный справочник по полям и проработанные примеры живут в [`dwe render git`](../render/git.md). Справочник блока активации (`services.<name>.render.git`) — в [`config/services/fields.md`](../config/services/fields.md#rendergit-block).

### Наследование шаблонов хуков

Пак — это просто директория. Композиция происходит через два механизма:

- **Оверлей `<pack>.local/`.** Для любого пака под `workspace/templates/git/<pack>/` соседняя директория `workspace/templates/git/<pack>.local/` может затенять отдельные файлы по относительному пути. Резолвер packroot пробует `<pack>.local/<rel>` первым и проваливается на `<pack>/<rel>`. Это шов кастомизации на разработчика — `.local/` обычно gitignored.
- **`extends:` сервиса.** Когда `service-b` расширяет `service-a`, и у `service-b` нет своего `render.git.template`, он наследует значение родителя. Правило коллизии deepest-extends затем разрешает, какой сервис побеждает для общего `<svc.Dir>`. Шаблонная переменная `.Resolved` именует рендерящий сервис (самый глубокий extender — его оверлей решает container/dir), а `.Service` именует канонический корень конфигурации (используйте его, чтобы посмотреть сырую конфигурацию по имени сервиса).

Сам пак не поддерживает директиву наследования «из другого пака». Если два пака делят содержимое, выносите общие части в тело шаблона через `{{ template "name" . }}` или дублируйте их. DWE не вводит языка композиции паков; модель файлового оверлея — единственная поверхность кастомизации.

## Проба рабочего пространства (`dwe status git`)

`dwe status` и `dwe status git` рендерят по одной строке на каждый сервис, у которого есть рабочее дерево в `<svc.Dir>/src/`. Проба только читает, параллельна и никогда не модифицирует репозиторий.

```mermaid
flowchart TD
  CFG["Загрузить смерженный конфиг"] --> ITER["Для каждого сервиса<br/>с выставленным svc.Dir"]
  ITER --> ABS["Разрешить <abs>/src"]
  ABS --> EX{"<abs>/src<br/>директория?"}
  EX -- нет --> SKIP["Пропустить строку"]
  EX -- да --> DEDUP["Сгруппировать по probe dir<br/>(потомки extends схлопываются)"]
  DEDUP --> PICK["Выбрать корень цепочки<br/>(минимальная глубина)"]
  PICK --> OWNGIT{"<abs>/src/.git<br/>существует?"}
  OWNGIT -- нет --> BLANK["Строка с пустыми ячейками"]
  OWNGIT -- да --> SHELL["git -C <abs>/src status -b --porcelain=v2"]
  SHELL --> PARSE["Распарсить branch + oid + ahead/behind + dirty"]
  PARSE --> ROW["Эмитировать строку"]
```

Особенности на границе:

- **Нет собственного `.git/` → пустые ячейки, не ошибка.** Сервис, у которого `<svc.Dir>/src/` существует, но нет своего `.git/`, получает строку с пустыми branch/SHA/ahead-behind. Проба намеренно коротит до любого шеллаута — `git -C` иначе пошёл бы вверх к ближайшему охватывающему репозиторию (часто корень проекта), и репортить его как статус сервиса было бы неверно.
- **Отсутствующий `src/` → вообще без строки.** Сервисы без рабочего дерева полностью опускаются из вывода. Нет флага отказа от секции workspace помимо отсутствия директории `src/`.
- **Потомки extends дедуплицируются.** Когда два сервиса делят один `<svc.Dir>` через `extends:`, они пробуют то же дерево. Коллектор группирует кандидатов по probe-директории и оставляет корень цепочки extends (минимальная глубина, ничьи разрешаются алфавитно). Sidecar-варианты вроде `main-debug` не дают дублирующих строк.
- **Параллельный шеллаут, ограниченный.** Пробы запускаются внутри `errgroup`, ограниченного 8 одновременными вызовами. Каждая горутина пишет в предзаранее аллоцированный слот строки, так что падения на строку изолированы и никогда не отменяют соседей.
- **Отображаемый путь.** Пробуемая директория, показанная в таблице статуса, относительна корню проекта с префиксом `…/` (`…/services/main/src`). Сама проба использует абсолютные пути.

Проба никогда не делает fetch. Branch / OID / ahead-behind / dirty приходят из одного вызова `git status -b --porcelain=v2`. Актуальность относительно удалённого репозитория требует отдельной пробы обновления, описанной ниже.

## Проба обновления (`dwe run`)

Пайплайн `run:` в `workspace/lifecycle.yml` может объявить блок `update:`. Когда он присутствует, `dwe run` пробует репозиторий корня проекта до выполнения любой фазы:

```yaml
# workspace/lifecycle.yml
run:
  update:
    mode: on   # on | off
```

Два режима:

| Режим | Fetch | Pull |
|------|---------|-------|
| `on` | да | с согласия (TTY-промпт; не-TTY понижается до check-семантики) |
| `off` | нет | нет — проба отключена |

Проба запускается на корне проекта, никогда на `src/` сервиса. Она зовёт `git fetch --quiet <remote>` (таймаут 15 с), затем `git rev-list --left-right --count`, чтобы вывести `behind` / `ahead`. Грязное дерево, отсутствующий upstream или провал fetch предупреждают и продолжают — пайплайн run никогда не блокируется.

Когда режим `on`, и рабочее дерево чистое, behind > 0, ahead = 0, и сессия интерактивна, DWE запрашивает подтверждение перед запуском `git pull --ff-only` (таймаут 2 мин). Успешный pull перезагружает `DweConfig`, `LifecycleConfig` и реестр команд in-process до выполнения фаз, так что остаток `dwe run` видит post-update состояние.

Runtime-приоритет: флаг `--no-update` > флаг `--update <mode>` > YAML `update.mode`. Справочник по полю: [`config/lifecycle.md`](../config/lifecycle.md#runupdate).

## Конвенции `.gitignore`

Типичный `.gitignore` проекта исключает три DWE-владеющих дерева:

```text
# DWE runtime artifacts
/.dwe/

# Container bind-mount targets
/volumes/

# Unpacked snapshot stash
/snapshots/
```

Обоснование, по папкам:

- **`.dwe/`** содержит журнал деплоя (`state.yml`), блокировки проекта (`deploy.lock`, `snapshot.lock`), логи команд (`logs/`) и проектные оверрайды user-config. Всё в нём перегенерируется из дерева конфигурации и запущенных контейнеров. Отслеживание его лишь связало бы историю коммитов с локальным таймингом.
- **`volumes/`** содержит цели bind-mount, в которые пишут контейнеры (директории данных БД, кэши сборки, сгенерированные артефакты). Отслеживание его связало бы репозиторий с выводом контейнеров.
- **`snapshots/`** содержит распакованную рабочую копию активного снапшота. Сами snapshot-архивы живут там, куда их кладёт snapshot-workflow — обычно отдельный путь или общий том. Runtime-стэш не должен отслеживаться.

Две связанные конвенции живут в других местах:

- **Per-service `<svc.Dir>/src/`** — это нормальный вложенный репозиторий (или worktree). Его `.gitignore` — забота приложения, а не DWE.
- **Директории `workspace/templates/<kind>.local/`** конвенционально gitignored. Резолвер packroot ищет их первыми и проваливается на канонический пак — это шов оверрайдов на разработчика для шаблонов IDE, AI и Git.

## Никакого checkout, fetch или push

DWE не выполняет Git-операций, о которых пользователь не просил:

- Он никогда не запускает `git checkout`, `git switch`, `git reset --hard`, `git stash` или что-либо ещё, что могло бы потерять работу.
- Он запускает только `git fetch` и `git pull --ff-only` из пробы обновления, и только когда сконфигурирован `update.mode: on` (или передан `--update on`), и рабочее дерево чистое.
- Он никогда не делает push. Единственные пути, которые могут делать push, — это написанные пользователем Git-хуки, которые пользователь занёс в template-пак — хуки являются пользовательским кодом, запускаемым Git, а не DWE.
- Проба рабочего пространства строго read-only — `git status --porcelain=v2` без флагов, которые могли бы мутировать индекс.

В сочетании с принципом отсутствия сети ([Архитектура → Без сети на штатном пути](architecture.md#без-сети-на-штатном-пути)) это означает, что вызов `dwe`, отличный от `dwe run` с `update.mode: on`, не выполняет вообще никаких удалённых Git-операций.
