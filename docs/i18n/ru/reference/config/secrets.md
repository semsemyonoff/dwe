# `dwe secrets` — зашифрованные значения, закоммиченные в репозиторий

`vars:` — дом для произвольных значений проекта, но у него нет ответа на
значение, которое разделяет вся команда и которое не должно лежать в git
открытым: токен тестового Telegram-бота, JSON сервис-аккаунта Google.
`workspace/local.yml` в gitignore, поэтому такие значения передают из рук в руки
и они расходятся между машинами.

`dwe secrets` закрывает этот пробел: значения **шифруются at rest и
коммитятся**, расшифровываются в памяти при загрузке конфига и никогда не
записываются обратно в отслеживаемый файл в открытом виде.

## Модель

Одна пара ключей **X25519 age на проект**:

- **Публичный recipient** (`age1…`) коммитится в `workspace.yml` под
  `secrets.recipient`. Для шифрования больше ничего не нужно, поэтому **любой,
  у кого есть репозиторий, может добавить секрет**.
- **Приватный identity** (`AGE-SECRET-KEY-1…`) никогда не попадает в git. Он
  живёт в `~/.config/dwe/keys/<recipient>.key` либо в `DWE_AGE_KEY` /
  `DWE_AGE_KEY_FILE` для CI. **Прочитать** секрет могут только держатели
  identity.

Расшифровка происходит один раз — в загрузчике конфига. `${vars.*}`,
`exports.env`, `dwe vars`, хеш деплоя и любой другой потребитель объединённого
конфига видят открытый текст и вообще ничего не знают о шифровании.

Формат — [age](https://age-encryption.org), стандартный проаудированный формат
файлов. Payload маркера — это age-файл, обёрнутый в base64, поэтому CLI `age`
открывает его напрямую; см. [Совместимость с CLI `age`](#совместимость-с-cli-age).

## Две формы: скаляры и целые файлы

**Скалярные значения.** Любая строка в любом слое конфига (`workspace.yml`,
`workspace/defaults.yml`, `workspace/local.yml`) может быть маркером
`ENC[age:…]`:

```yaml
# workspace/defaults.yml — отслеживается git
vars:
  telegram:
    token: ENC[age:YWdlLWVuY3J5cHRpb24ub3JnL3YxCi0+IFgyNTUx…]
```

Грамматика маркера строгая: `ENC[age:<base64>]`, **весь скаляр целиком или
ничего**. Строка, которая просто *содержит* `ENC[` — строка лога, регулярка,
комментарий — это обычные данные, её не трогают.

Проход расшифровки не зависит от пути (маркер работает где угодно в дереве), но
`dwe secrets set` пишет только под `vars.`: это единственная свободная песочница
в схеме со строгим корнем и единственное место, где валидатор оверлеев
разрешает произвольное значение. См.
[`workspace.md` → Строгий корень + песочница `vars:`](workspace.md#strict-root--the-vars-sandbox).

**Целые файлы.** Источник конфиг-пака, чей `from:` заканчивается на `.age`, —
это нативный зашифрованный age-файл. `render config` расшифровывает его перед
обычным рендером `${...}` в hub-директорию сервиса:

```yaml
# workspace/templates/config/bot/manifest.yml
render:
  - from: google-credentials.json.age
    to: config/google-credentials.json
```

Путь `to:` **никогда** не выводится из источника — называйте вывод так, как
ожидает сервис. См. [`render config`](../render/config.md).

## Блок `secrets:`

```yaml
# workspace.yml — только слой 1
secrets:
  recipient: age1qyqszqgpqyqszqgpqyqszqgpqyqszqgpqyqszqgpqyqszqgpqyqs3fgh2p
```

| Поле | Тип | Описание |
|------|-----|----------|
| `secrets.recipient` | string | Публичный age-recipient проекта (`age1…`). Коммитится. |

`secrets:` входит в allowlist строгого корня, но в отличие от всех остальных
формализованных блоков он легален **только в `workspace.yml`**. Объявление его в
`workspace/defaults.yml` или `workspace/local.yml` — жёсткая ошибка загрузки с
именем файла: recipient «на разработчика» молча разбил бы команду на группы,
которые не могут читать секреты друг друга. (`compose.extra` — существующий
прецедент ключа, легального ровно в одном слое.)

Некорректный `recipient` или значение `secrets:`, не являющееся мапой, — тоже
ошибка загрузки с именем файла. Та же валидация выполняется для послойного
резолва `dwe vars inspect`, поэтому два загрузчика не могут разойтись.

## Ключи: где живёт identity

`dwe` ищет приватный identity в этом порядке и использует **первый найденный
источник**:

| Порядок | Источник | Значение |
|---------|----------|----------|
| 1 | `DWE_AGE_KEY` | Сам текст identity (`AGE-SECRET-KEY-1…`) |
| 2 | `DWE_AGE_KEY_FILE` | Путь к файлу с текстом identity |
| 3 | `~/.config/dwe/keys/<recipient>.key` | Keyfile проекта, `0600` |

Первый найденный источник **обязан** совпасть с настроенным recipient.
Несовпадение — это `wrong_identity` с именем источника; переход к следующему
источнику **не происходит**, потому что молчаливое игнорирование явно
выставленного `DWE_AGE_KEY` — ровно тот путь, на котором CI-джоба сообщает «нет
ключа», хотя на деле ключ не тот.

Директория ключей создаётся с правами `0700` (существующая более свободная
ужимается), каждый keyfile пишется с `0600` и `O_CREATE|O_EXCL` — DWE никогда не
перезаписывает файл identity.

Identity читается как **первый токен `AGE-SECRET-KEY-1…` в строке, не
являющейся комментарием `#`**, поэтому keyfile от CLI `age` (в котором есть
заголовок `# public key:`) используется как есть, а файл, где живой ключ лежит
под закомментированным старым, разрешается в живой ключ — тот же, который взял
бы сам `age`. Более поздний токен игнорируется, а не считается ошибкой:
multi-identity `DWE_AGE_KEY_FILE` — документированная форма `age`. Если *все*
токены лежат внутри комментариев — форма, которую даёт вставка, склеившая
заголовок keyfile и ключ в одну строку, — сканируется весь текст целиком, так
что такая вставка по-прежнему разбирается. Этот повторный скан не выполняется,
если в строке-не-комментарии есть `AGE-SECRET-KEY-1…`, который слишком короток
или испорчен: дотянуться через повреждённый живой ключ до закомментированного
старого означало бы объявить файл *чужим* identity вместо некорректного.

## С чего начать

```bash
# Один раз на проект, на одной машине:
dwe secrets init                                  # сгенерировать пару ключей
git add workspace.yml && git commit               # закоммитить recipient

# Добавить секрет (нужен только закоммиченный recipient):
pbpaste | dwe secrets set vars.telegram.token --stdin
git add workspace/defaults.yml && git commit

# Онбординг коллеги — identity передаётся вне репозитория:
dwe secrets key export                            # → менеджер паролей
# …на другой машине:
dwe secrets key import                            # скрытый ввод: вставить ключ
dwe secrets key import --file identity.txt        # …или прочитать из файла
```

После этого `${vars.telegram.token}` везде резолвится в открытый текст, а
`dwe vars get vars.telegram.token` его печатает.

## Новый разработчик / новая машина

Клон несёт публичный recipient; приватный identity вместе с ним не едет. Пока
identity нет на этой машине, любое зашифрованное значение читается как
`<encrypted>`, а любая lifecycle-команда упирается в `secrets.unresolved`.

Мест ровно три — [порядок поиска выше](#ключи-где-живёт-identity):
`DWE_AGE_KEY`, `DWE_AGE_KEY_FILE` или keyfile проекта, который пишет
`dwe secrets key import`. **Первый найденный источник обязан совпасть с
recipient**; перехода к следующему не происходит.

### Интерактивный импорт

В терминале, без `--file` и без пайпа, `import` спрашивает ключ сам:

```
$ dwe secrets key import
Private identity for age1qyqs…
Paste the AGE-SECRET-KEY-… line, or the whole keyfile; the typed characters are not echoed.
> ••••••••••••

identity for age1qyqs… stored at /home/dev/.config/dwe/keys/age1qyqs….key
2 encrypted value(s) and 1 .age file(s) are now readable
```

Поле скрытое, и принимается keyfile целиком — вместе с заголовком-комментарием
и даже когда вставка приехала одной склеенной строкой. Проверка идёт **внутри
формы**: ключ, который не парсится, или ключ от другого проекта показываются без
закрытия формы, поэтому опечатку исправляют, а не начинают заново. `Esc`
отменяет с `secrets_import_cancelled` и без keyfile.

Вторая строка — ради чего всё и затевалось: это тот же скан, что рендерит
[`dwe secrets status`](#dwe-secrets-status), поэтому импорт заканчивается
отчётом о том, что ключ реально открыл, а не оставляет проверять это вручную.

### Предложение в `dwe deploy`, `dwe run` и `dwe restart`

Знать команду импорта наизусть не обязательно. Когда в проекте есть
зашифрованные данные, пригодного identity нет, а за терминалом сидит человек,
интерактивные точки входа предлагают ввести ключ прямо здесь:

```
Enter the private identity now?
This project has encrypted values that need the age identity for age1qyqs…, and
this machine does not have it. run 'dwe secrets key import' to store the identity
at /home/dev/.config/dwe/keys/age1qyqs….key, or set DWE_AGE_KEY / DWE_AGE_KEY_FILE
  [ Enter key ]   [ Abort ]
```

`Enter key` открывает тот же скрытый ввод; сохранённый identity проверяется
настоящим поиском, и команда **продолжается в том же запуске** — предложение
работает на сырых слоях *до* загрузки конфига, поэтому конфиг читается один раз
и уже расшифрованным. `Abort` (или `Esc`) завершает команду подсказкой и ничего
не записывает — в меню `dwe deploy` это типизированный `secrets_no_identity`,
в `dwe run` / `dwe restart` — та же фраза.

Три детали:

- **`dwe restart` предлагает до того, как что-то остановит.** Отказ оставляет
  стек работающим, а не роняет его, чтобы потом не суметь поднять. Речь про
  рестарт всего стека: `dwe restart <сервис>` идёт сразу в `docker restart` и не
  запускает ни предложение, ни preflight.
- **В `dwe deploy` предложение стоит на входе в меню**, поэтому покрывает и
  `Plan`, а не только `Run` и мастера: план, построенный без ключа, печатал бы
  команды, выведенные из `<encrypted>`.
- **Неинтерактивные точки входа сохраняют сегодняшнюю жёсткую ошибку**:
  `dwe deploy run`, `dwe reset`, `dwe render env` и `dwe render config` падают с
  теми же сообщением и подсказкой. Это предложение там, где человек уже ждёт, а
  не глобальный хук.

### Что видят CI и скрипты

Предложение не открывается, когда отвечать на него некому: stdin не терминал,
`--yes` (его определяют только `dwe run` и `dwe restart` — у `dwe deploy` такого
флага нет), `--output json` или `DWE_NONINTERACTIVE=1`. В каждом из этих случаев
остаётся прежнее поведение — стена preflight `secrets.unresolved` для
lifecycle-команд, — так что вывод и код возврата пайплайна не меняются.
`key import` тоже не изменился: identity из пайпа читается как раньше, а на
терминале `--output json` и `DWE_NONINTERACTIVE=1` вместо запроса отказывают с
`secrets_identity_source_required`.

### Сломанный источник сообщают, а не предлагают починить вводом

Раз побеждает первый найденный источник и перехода к следующему нет, заданный
`DWE_AGE_KEY`, который не содержит identity этого проекта, **импортом ключа не
чинится**: свежий keyfile просто не будет прочитан. Поэтому вместо формы, чей
результат нельзя использовать, гейт называет источник:

```
$DWE_AGE_KEY is set but does not hold the identity for age1qyqs…;
unset it or fix it — a keyfile is not consulted while it is set
```

Уже существующий keyfile с чужим ключом отклоняется так же — с указанием на
[`dwe secrets key remove`](#dwe-secrets-key-remove): запись идёт с `O_EXCL` и
его бы не заменила. Оба отказа срабатывают в **любом** режиме, интерактивном или
нет: они точнее общего «нет identity», и ни один из них не вопрос.

## Подкоманды

Все пишущие команды берут локи проекта (`deploy.lock` → `snapshot.lock`) и
**не запускают preflight** — это правки конфига, а не мутации стека. `status`,
`get` и `key export` вообще ничего не пишут. `decrypt` тоже не берёт локи — он
не трогает конфиг, — но он пишет файл с открытым текстом (см. ниже).

**`init`, `set` и `rekey` правят файл слоя, заменяя отдельные строки.** Они не
переэнкодят документ, поэтому отступы, пустые строки, комментарии, якоря,
merge-ключи `<<:`, стиль кавычек и переводы строк остаются побайтово теми же:
один `dwe secrets set` в размеченный `defaults.yml` на несколько сотен строк
даёт диф в одну строку. Новый ключ вставляется, а не заменяется — в конец файла
для нового верхнеуровневого блока, иначе после конца ближайшего существующего
маппинга.

Плата за это — несколько форм, которые нельзя отредактировать на месте: они
**отклоняются, а файл остаётся нетронутым** (`secrets_write_unsupported`), с
указанием пути и способа починки:

| Отклонённая форма | Что сделать |
|-------------------|-------------|
| Литеральный или свёрнутый блочный скаляр, либо plain/quoted скаляр, перенесённый на несколько строк | Записать значение в одну строку |
| Цель внутри flow-коллекции (`{a: 1}`, `[x, y]`) | Записать её как блочную коллекцию |
| Родитель, который является `null` (`vars:` без вложенных ключей), последовательностью или скаляром | Материализовать родителя как блочный маппинг |
| Родитель, достижимый через YAML-алиас (`vars: *common`), или ключ, который может наследоваться через merge-ключ `<<:` | Записать ключ в этом маппинге явно |

Перед записью склеенные байты перечитываются, и значение читается обратно по
своему пути; расхождение тоже отклоняется, и ничего не пишется.

### `dwe secrets init`

```
dwe secrets init
```

Генерирует пару ключей X25519, пишет identity в
`~/.config/dwe/keys/<recipient>.key` и вклеивает `secrets.recipient` в
`workspace.yml` (проект, где ещё нет блока `secrets:`, получает этот блок в
конец файла; остальной файл не трогается и сохраняет свои права).

Keyfile пишется **первым**: закоммиченный recipient без читаемого identity
закрыл бы проекту доступ к собственным секретам. Если запись в `workspace.yml`
затем упадёт, keyfile удаляется обратно, чтобы повторный запуск не упёрся в
запрет перезаписи.

Отказывается работать, если `secrets.recipient` уже выставлен — замена живой
пары ключей — это [`rekey`](#dwe-secrets-rekey), который перешифровывает
существующие значения вместо того, чтобы осиротить их.

### `dwe secrets status`

```
dwe secrets status
```

Отчёт, который запускают, чтобы понять, почему что-то заблокировано. Сам он
никогда ничего не блокирует: **ни одно зашифрованное значение не может его
уронить** — даже когда ключа нет и ни одно значение не читается, он завершается
с кодом 0 и показывает каждое строкой. (Конфиг, который вообще не грузится, —
по-прежнему ошибка: инвентаризировать было бы нечего.)

Показывает настроенный recipient, identity, который есть на этой машине (а
когда его нет — где именно искали), и две инвентаризации:

- **Маркеры** — каждый скаляр `ENC[age:…]` во всех трёх файлах слоёв, как
  `layer` / `path` / `state`.
- **Зашифрованные файлы** — каждый `*.age` под
  `workspace/templates/config/**`.

Каждая запись **реально расшифровывается**, поэтому отчёт различает три
причины, а не сваливает их в кучу:

| Состояние | Значение |
|-----------|----------|
| `decrypted` / `decryptable` | Настроенный identity его читает |
| `decrypted: stale_key` / `decryptable: stale_key` | Здесь читается, но только *старым* keyfile — настроенный identity его не открывает |
| `unresolved: no_identity` | На этой машине нет identity для этого recipient |
| `unresolved: wrong_identity` | Identity найден, но это значение он не открывает |
| `unresolved: invalid_identity` | Источник identity задан, но не содержит ключа age — например, обрезанный `DWE_AGE_KEY`. Чинить нужно сам источник: пока задана env-переменная, keyfile не читается |
| `unresolved: corrupt` | Payload повреждён — проблема не в ключе |

`corrupt` определяется без ключа (форма маркера, base64, заголовок age), поэтому
разработчика без ключа никогда не отправляют искать ключ, который всё равно бы
не помог.

Наполовину перекеенное дерево описывается **по каждому значению**: сначала
пробуется настроенный identity, затем каждый другой keyfile в директории
ключей, — поэтому `status` говорит, каким значениям всё ещё нужен старый ключ,
вместо того чтобы упасть целиком. Это и есть строки `stale_key`, и они
показываются жёлтым: загрузчик конфига пробует *только* настроенный identity,
поэтому такое значение на этапе загрузки всё ещё `wrong_identity`, и
`secrets.unresolved` продолжает блокировать lifecycle-команды, пока
`dwe secrets rekey` не будет доведён до конца. Кандидат `*.age`, не прошедший
дисциплину путей (симлинк, устройство), сообщается как `not decryptable` с
причиной отказа — а не пропускается молча.

Строки отсортированы (порядок слоёв, затем путь), поэтому вывод стабилен между
запусками и его можно диффать.

Строка **Identity** описывает поиск честно: источник, который прочитали и
отвергли, никогда не выглядит как отсутствующий ключ.

| Заголовок | Значение |
|-----------|----------|
| `keyfile (…)` / `$DWE_AGE_KEY` / `$DWE_AGE_KEY_FILE` | Identity загружен из этого источника |
| `none (looked at …)` | Identity нет нигде; строка перечисляет все места, где искали |
| `invalid (…)` | Источник задан, но не содержит ключа age — строка называет источник, который нужно чинить |
| `wrong recipient (…)` | Читаемый identity, но **другого** recipient; строка называет обоих |

Если identity не загрузился, отчёт заканчивается инструкцией по починке
(`run 'dwe secrets key import' to store the identity at …, or set DWE_AGE_KEY /
DWE_AGE_KEY_FILE`) — той же фразой, что печатает `dwe validate`. В `--output
json` те же факты структурированы: `identity.source` — **прочитанный** источник
даже при неудаче, `identity.reason` — стабильное слово причины (`no_identity` /
`invalid_identity` / `wrong_identity`), `identity.error` — формулировка,
`identity.hint` — как починить. Все они написаны самим dwe: ошибка разбора от
`age` повторяет символы входа, а для сломанного источника identity это байты
приватного ключа, поэтому она не печатается никогда.

### `dwe secrets set`

```
dwe secrets set <vars.path> [value] [--file defaults|workspace] [--stdin]
```

Шифрует значение на recipient проекта и записывает его маркером в
**отслеживаемый** файл слоя. Нужен только recipient — разработчик без identity
всё равно может добавить секрет.

Значение берётся из одного из трёх источников:

- позиционный аргумент — **попадает в историю шелла**, как любой аргумент;
- `--stdin` — весь stdin, с обрезанным ровно одним завершающим переводом строки
  (и предшествующим `\r`), не более;
- ни то, ни другое, на терминале — **скрытый промпт**.

Передача и аргумента, и `--stdin` — типизированный отказ
(`secrets_value_ambiguous`), а не молчаливая победа одного из них.

Правила:

- **Префикс `vars.` обязателен**, в отличие от `dwe vars set`. Молчаливая
  переписка `project.name` в `vars.project.name` приняла бы путь, который
  пользователь имел в виду буквально, а у `secrets set` нет автодополнения,
  которое сделало бы сокращение заметным.
- **Никакого приведения типов.** Значение всегда хранится строкой, поэтому
  секрет, похожий на число (`"123"`), останется тем, что вы напечатали. Сравните
  с [`dwe vars set`](vars.md#dwe-vars-set), который разбирает аргумент как
  YAML-скаляр.
- **`--file`** выбирает `workspace/defaults.yml` (по умолчанию) или
  `workspace.yml`. `--file local` отклоняется с указанием на `dwe vars set`:
  `workspace/local.yml` — это личное состояние в gitignore, где шифрование
  ничего не даёт.
- Спуск через существующую мапу — норма; спуск через существующий
  **не-мап**-узел (`vars.db.host.port`, где `host` — скаляр) отклоняется как
  неподдерживаемая форма, файл остаётся нетронутым — как и остальные
  [отклонённые формы](#подкоманды).
- Подготовленный документ валидируется как слой конфига **до** записи, поэтому
  `set` никогда не может оставить слой незагружаемым.

Значение получают *до* взятия локов проекта — скрытый промпт может висеть
сколько угодно, а удержание пары локов всё это время блокировало бы любую другую
команду `dwe` в проекте. Recipient затем перечитывается **под локом**, поэтому
значение не может быть зашифровано на recipient, который параллельный `rekey`
успел вывести из обращения.

Запись меняет только целевую строку — комментарии, порядок ключей, пустые
строки и форматирование сохраняются побайтово; отсутствующий
`workspace/defaults.yml` создаётся с правами `0644` (отслеживаемые файлы
сохраняют обычные права — принудительно `0600` ставится только `local.yml`).

### `dwe secrets get`

```
dwe secrets get <vars.path>
```

Расшифровывает маркер по пути и печатает открытый текст. Нужен identity.

`get` читает слои **как они записаны**, поэтому сообщает сам секрет, а не
объединённое значение: когда маркер в `workspace/defaults.yml` перекрыт
открытым значением в `workspace/local.yml`, `dwe secrets get` всё равно печатает
секрет, а [`dwe vars get`](vars.md#dwe-vars-get) — переопределение, которое
реально побеждает в рантайме.

Путь без маркера — это `secrets_not_encrypted`; для открытого значения
используйте `dwe vars get`.

### `dwe secrets encrypt` / `decrypt`

```
dwe secrets encrypt <file>     [--out PATH|-] [--force]
dwe secrets decrypt <file.age> [--out PATH|-] [--force]
```

Помощники для целых файлов — под источники конфиг-паков. `encrypt` пишет
`<file>.age` рядом со входом; `decrypt` снимает суффикс `.age` (входу, который
не заканчивается на `.age`, нужен явный `--out`). Обе отказываются перезаписать
существующий выход без `--force`.

Флаг называется `--out`, а не `-o`: корневая команда владеет `-o` для
`--output`. `--out -` пишет в stdout и **отклоняет** `--output json`
(`secrets_raw_stream`) — поток байтов и JSON-конверт не могут делить stdout.

Дисциплина путей применяется к обоим концам: абсолютный путь вне проекта
легален (это файловая утилита), но **симлинк или не-обычный файл отклоняется,
где бы он ни лежал** — запись через симлинк-выход это ровно тот способ, которым
«расшифровать во временный файл» превращается в перезапись чего-то другого.
Выход, равный входу, тоже отклоняется.

Расшифрованный выход получает права `0600`, а существующий **ужимается** до
`0600` — теперь это открытый текст на диске, коммитить его нельзя.
Перезаписанный *шифротекстовый* файл сохраняет права, которые ему дал
репозиторий.

`encrypt` нужен только recipient; `decrypt` нужен identity.

### `dwe secrets key export` / `import`

```
dwe secrets key export
dwe secrets key import [--file|-f PATH]
```

Identity никогда не лежит в git — он передаётся через менеджер паролей или
другой канал вне репозитория.

`export` печатает `AGE-SECRET-KEY-1…` в stdout. Когда stdout — терминал, он
дополнительно предупреждает в stderr (только в текстовом режиме), потому что
ключ сейчас осядет в скроллбеке.

`import` читает identity из `--file`, из stdin, когда тот приходит по пайпу,
или — на терминале, когда нет ни того, ни другого — из **скрытого запроса**.
Каким бы ни был источник, он **проверяет, что recipient совпадает с
настроенным** (`secrets_identity_mismatch`), и только тогда пишет keyfile с
правами `0600`. Он тоже берёт локи проекта: импорт, гонящийся с `rekey`, иначе
установил бы выводимый из обращения identity.

Вставлять можно как строку `AGE-SECRET-KEY-1…`, так и весь keyfile целиком —
комментарий-заголовок age-keyfile игнорируется, в том числе когда вставка
склеила его строки в одну.

Запрос валидирует ввод на месте: ключ, который не разбирается, или ключ от
другого проекта показываются как ошибка, не закрывая форму, поэтому опечатку
в вставке не приходится начинать заново. `Esc` отменяет с
`secrets_import_cancelled` и без keyfile. Так как запись идёт с `O_EXCL`, уже
установленный identity сообщается **до** открытия формы, а не после того, как
ключ набран.

Запрос никогда не открывается без терминала: identity из пайпа
(`pbpaste | dwe secrets key import`, CI) читается со stdin как раньше, а пустой
stdin — это `secrets_identity_source_required`. На терминале `--output json` и
`DWE_NONINTERACTIVE=1` отказывают тем же кодом вместо запроса.

Успешный импорт заканчивается тем, что открыл ключ:

```
identity for age1… stored at ~/.config/dwe/keys/age1….key
2 encrypted value(s) and 1 .age file(s) are now readable
```

Счётчики берутся из того же скана, который печатает `dwe secrets status`, и
считаются только значения, которые открывает *настроенный* identity: значение,
оставшееся от прерванного `rekey`, — всё ещё задача, поэтому оно не в счёт.

Если этот скан вообще не отрабатывает (нечитаемый `workspace/templates/config`),
импорт всё равно **успешен** — keyfile записан, и `O_EXCL` откажет повторной
попытке, — но вторая строка становится `the readability report could not be
built: <причина>`, а в JSON вместо `markers_readable` / `files_readable`
приходит `report_error`. Нулевой счётчик здесь означал бы, что ключ ничего не
открывает, а произошло не это.

### `dwe secrets key list`

```
dwe secrets key list
```

Все identity, установленные на этой машине, отсортированные по имени файла:

```
  Directory — /home/dev/.config/dwe/keys

╭───────────┬───────────────┬────────────────────╮
│RECIPIENT  │FILE           │STATE               │
├───────────┼───────────────┼────────────────────┤
│age1broken │age1broken.key │unparsable          │
│age1current│age1current.key│ok (current project)│
│age1locked │age1locked.key │unreadable          │
│age1other  │age1other.key  │ok                  │
│age1parsed │age1stale.key  │misnamed            │
╰───────────┴───────────────┴────────────────────╯
```

Директория ключей **общемашинная, а не проектная**, и именно поэтому ничего не
удаляется автоматически: лежащий здесь ключ может принадлежать любому другому
проекту на этой машине, так что «неиспользуемый» вычислить нельзя. Единственное
отношение, которое `list` может назвать, — то, что он знает: строка текущего
проекта помечается `current project`. Вне проекта не помечается ничего, и
команда всё равно работает (она в списке команд, которым проект не нужен).
Пустая или отсутствующая директория ключей печатает `No identities in <dir>.`
и завершается с кодом 0.

| Состояние | Значение |
|-----------|----------|
| `ok` | Файл содержит тот age-identity, который заявлен его именем |
| `unreadable` | Файл не удалось прочитать (права, директория, битая ссылка) |
| `unparsable` | В файле нет age-identity |
| `misnamed` | Парсится, но identity принадлежит другому recipient, чем говорит имя файла — в строке показан **распарсенный** recipient |

Состояния — фиксированный словарь: текст ошибки ввода-вывода или парсера в вывод
не попадает никогда, потому что и то и другое повторяет содержимое файла. Для
`unreadable` и `unparsable` в колонке RECIPIENT стоит основа имени файла —
recipient и есть имя файла по построению, — а не что-то прочитанное изнутри.

### `dwe secrets key remove`

```
dwe secrets key remove <recipient> [--force] [--yes|-y]
```

Удаляет `~/.config/dwe/keys/<recipient>.key`. **Аргумент называет файл**, поэтому
файл `misnamed` удаляется под своим собственным именем, а не под тем recipient,
который показывает для него `key list`: попытка удалить его по этому recipient —
`secrets_key_not_found`.

Удаление файла, который СОДЕРЖИТ identity текущего проекта, отклоняется
(`secrets_key_in_use`), пока не передан `--force`: зашифрованные значения станут
здесь нечитаемыми, и, если ключ не экспортировали, он больше нигде не
существует. Проверка читает файл, а не его имя, поэтому она покрывает и файл
`misnamed`, несущий ключ этого проекта. Файл, который ничего не открывает — без
age identity, с ключом другого проекта или вообще никуда не ведущий (битый
симлинк), — удаляется без `--force`; именно это делает работающим совет выше
«удалите его и импортируйте правильный» для устаревшего keyfile. Отсутствующий
файл — `secrets_key_not_found`.

Файл, байты которого не удаётся **прочитать**, — единственный случай, на который
проверка ответить не может, и он отклоняется (`secrets_key_unreadable`) до
`--force`: на удаление файла право чтения не нужно, так что пропустить его
означало бы стереть ключевой материал, который никто не признал мёртвым.

В остальных случаях удаление подтверждается интерактивно. Там, где спросить
нельзя — нет терминала, `--output json`, `DWE_NONINTERACTIVE=1`, — это
`secrets_confirmation_required`, и путь дальше — `--yes`; отказ же ничего не
делает, печатает `kept <path>` и завершается с кодом 0. Локи проекта держатся
вокруг удаления, когда проект определён, — по той же причине, по которой их
держит `key import`: удаление, гоняющееся с `rekey`, сняло бы ключ, который
`rekey` как раз ставит.

### `dwe secrets rekey`

```
dwe secrets rekey
```

Генерирует новую пару ключей и перешифровывает на неё **каждый** закоммиченный
секрет — каждый маркер в файлах слоёв и каждый источник `*.age`. Запускайте,
когда identity мог утечь или когда тот, кто им владел, больше не должен читать
секреты проекта.

Эта машина обязана уметь прочитать каждый существующий секрет. Сначала
пробуется настроенный identity, затем каждый другой keyfile в директории ключей
(поэтому наполовину перекеенное дерево доводится до конца).

Порядок — это **восстановимая последовательность, а не транзакция**:

1. **Проход только на чтение** — расшифровать и провалидировать всё в память.
   Повреждённый маркер или нерасшифровываемый `.age` прерывает команду здесь,
   **не записав ничего**.
2. **Записать новый keyfile** — первая мутация. Старый keyfile сохраняется.
3. **Перешифровать** каждый файл `.age` (атомарно) и каждый файл слоя (по одной
   вклеенной строке на маркер, так что диф — одна строка на перешифрованное
   значение).
4. **Обновить `secrets.recipient` последним.**

Падение посередине оставляет на диске оба identity и смешанное дерево;
повторный запуск `rekey` — или просто `dwe secrets status` — сначала пробует
настроенный identity, а потом каждый другой keyfile, поэтому последовательность
сходится. Отказы после шага 2 говорят об этом явно, и JSON-конверт отличает их
от отказов на проходе-чтении (те несут `written: false`).

Удалите старый keyfile, когда каждый разработчик импортирует новый identity.

## Без ключа: что продолжает работать

Проект, чьи секреты здесь не расшифровываются, **всё равно загружается**.
Маркеры остаются в конфиге литералами, и:

| Поверхность | Поведение |
|-------------|-----------|
| `dwe status`, `dwe docs`, `dwe validate`, `dwe prompt`, `dwe commands` | Работают штатно |
| `dwe vars list` / `get` / `inspect`, TUI-браузер | Показывают `<encrypted>` — никогда шифротекст |
| `dwe secrets status` | Сообщает про каждое значение и причину; код возврата 0 |
| `dwe run`, `dwe restart`, `dwe deploy`, `dwe reset`, `dwe stop`, мастер деплоя | **Блокируются** валидатором preflight `secrets.unresolved` с указанием, что делать. В терминале `dwe run` / `dwe restart` и меню `dwe deploy` сначала [предлагают ввести identity](#предложение-в-dwe-deploy-dwe-run-и-dwe-restart) |
| `dwe render env`, `dwe render config` | **Падают**, называя значение, которое было бы записано |
| `dwe render ide` / `ai` / `git` | Работают — они рендерят по санитизированному конфигу и выдают маркер |

Отсутствие ключа никогда не отрендерит секрет как `""` и никогда не запишет
маркер в выходной файл.

`dwe stop` попал в список блокируемых потому, что он выполняет stop-хуки из
`lifecycle.yml` — это обычные пользовательские команды, которые могут
ссылаться на `${vars.*}`; стадию preflight `stop` он делит с `dwe reset`.
Чтобы погасить стек на машине без ключа, передайте `--skip-preflight`.

Зашифрованные `project.name` / `project.prefix` горячий путь `dwe prompt`
считает **невыставленными** (у него собственный мягкий парсер, полный конфиг он
не грузит) — зашифрованное имя проекта бессмысленно, а маркер в фильтре
compose-меток не совпал бы ни с одним контейнером.

## Защита вывода: маркер никогда не попадает в отрендеренный файл

Два рендерера работают без preflight (`dwe render env`, `dwe render config`), а
`dwe run` рендерит `.env` *до* своего preflight. Поэтому политику они соблюдают
сами:

- **`.env`** — проверяется каждое выдаваемое значение: системные переменные
  (включая `PROJECT` из `project.name`) и каждое правило `exports.env`. Маркер —
  это ошибка с именем переменной и её исходного пути и указанием на
  `dwe secrets status`. Срабатывает во всех четырёх местах записи `.env`:
  `dwe render env`, автоматическая регенерация перед `dwe docker up` / `run` /
  `exec` / `restart` / `build`, `dwe services enable` / `disable` и рендер
  `.env`, который `dwe run` делает до собственного preflight. Корневой `.env`
  также явно переводится в `0600`, поэтому существующий более свободный файл
  ужимается.
- **Конфиг-паки** — после рендера `${...}` вывод, всё ещё содержащий маркер,
  отклоняется с именем пути `to:` записи. Поскольку контекстом рендера служит
  сырой объединённый конфиг, это ловит любую подстановку нерасшифрованного
  маркера без отслеживания, какого именно.
- **Паки ide / ai / git** — их выводы обычно **отслеживаются git**, поэтому они
  вообще не видят открытого текста: эти три рендерера грузят **санитизированный**
  конфиг, собранный по сырым слоям без прохода расшифровки. Каждое поле,
  доступное шаблону (`.Raw`, `.Vars`, `.Project`, `.Runtime`, `.Services`,
  `.ServiceCfg`), несёт маркер там, где настоящий конфиг несёт открытый текст.
  Шаблон, читающий секрет, выдаёт шифротекст — уже закоммиченный, безвредный, —
  но не открытый текст. Это структурная гарантия, а не allowlist путей.

Выводы паков с источником `.age` пишутся с правами `0600` и явно `chmod`-ятся
(существующая цель `0644` ужимается). Остальные выводы паков сохраняют `0644`,
поэтому скалярный секрет, подставленный в отрендеренный `.env`, попадает в
hub-директорию из gitignore с обычными правами пака. Контейнер спокойно читает
файл `0600`, потому что работает под тем же UID/GID хоста, который `exports.env`
уже публикует.

## Валидация и preflight

Два валидатора домена `secrets` (`dwe validate secrets`):

| Валидатор | Вид | Срабатывает, когда |
|-----------|-----|--------------------|
| `secrets.recipient` | контент | Есть маркеры или источники `.age`, но `secrets.recipient` отсутствует либо не является корректным `age1…`; либо payload маркера повреждён (`corrupt`) |
| `secrets.unresolved` | готовность | Хоть одно значение в объединённом конфиге не расшифровано, либо источник `.age` резолвящегося конфиг-пака не расшифровывается загруженным identity |

`secrets.recipient` сам грузит сырые слои, когда конфиг не загрузился, поэтому
scoped-запуск `dwe validate secrets` всё равно диагностирует некорректный
recipient, а не остаётся слепым.

`secrets.unresolved` — **второе исключение** из правила, что в preflight
попадают только `env.*` и `checks.*` (первое — `config.validate`): это вопрос
готовности, а не контента — «может ли эта машина реально деплоить прямо
сейчас». Он подмешан и в `preflight.Run`, и в pre-flight-гейт мастера деплоя,
поэтому `dwe run` / `deploy` / `reset` и меню останавливаются с одной и той же
понятной подсказкой.

Он по-прежнему та же стена. Изменилось то, с чем человек сталкивается *до* неё:
в интерактивном `dwe run` / `dwe restart` / `dwe deploy` сначала срабатывает
[предложение ввести ключ](#предложение-в-dwe-deploy-dwe-run-и-dwe-restart),
поэтому к моменту preflight identity уже есть и валидатору нечего сообщать.
Запуск без терминала блокируется ровно так, как описано здесь; *отказ* от
предложения до валидатора вообще не доходит — команда завершается сразу, с той
же подсказкой.

Нерасшифрованные маркеры группируются **по причине**: одна диагностика на
причину со списком отсортированных путей. У разработчика без ключа все маркеры
не расшифрованы по одной причине; строка на каждый маркер похоронила бы
единственное осмысленное действие.

Скан источников `.age` повторяет то, что реально обходит `render config`,
поэтому выключенный сервис или нерезолвящийся пак невидимы валидатору ровно так
же, как и во время рендера.

**Здоровый проект говорит об этом.** Оба валидатора выдают строку `✓`, когда не
нашли проблем, поэтому `dwe validate secrets` после онбординга сообщает
`validation result: 2 checks`, а не `validation skipped (no files found)`. У
строки `secrets.recipient` нет сообщения — утверждение и есть сам target, — а
строка `secrets.unresolved` считает только что прочитанный инвентарь:
`1 encrypted value(s) and 0 config-pack source(s) readable via keyfile`.

Строки привязаны к тому, что валидатор действительно проверил: строке recipient
достаточно корректного `secrets.recipient` (проект, где сделали `dwe secrets
init`, но пока ничего не зашифровали, тоже её получит), а строка unresolved
появляется, только когда есть что читать *и* не возникло ни одной диагностики.
Проект без блока `secrets:` и без шифрованных значений остаётся молчаливым — ровно
как раньше. Identity называется словом-источником (`env` / `env-file` /
`keyfile`) — никогда путём и никогда с ключевым материалом. Preflight и гейт
мастера деплоя отфильтровывают строки `✓`, поэтому ни один из них не печатает
ничего лишнего.

## Куда попадает открытый текст

Расшифрованные значения по замыслу существуют в:

- **памяти процесса** — объединённый конфиг;
- **корневом `.env` проекта** — в gitignore, `0600`, и он уже дом для
  `exports.env`;
- **выводах конфиг-паков в hub-директории сервиса** — в gitignore через
  `/services/`;
- **`.dwe/generated.yml`** — `0600`, в gitignore, когда сбор `generated:` читает
  отрендеренный hub-файл с расшифрованным значением;
- **контейнере**, который читает hub-директорию;
- **выводе дочерних процессов**, которые запустил сам пользователь.

Их **держат вне**:

- **отслеживаемых git файлов** — выводы паков ide / ai / git рендерятся по
  санитизированному конфигу (см. [защиту вывода](#защита-вывода-маркер-никогда-не-попадает-в-отрендеренный-файл));
- **собственных эхо команд dwe** — трассировки `-v` / `--debug`, их копии в
  `.dwe/logs` и любая поверхность плана / dry-run редактируются (см. ниже);
- **вывода `dwe vars`** при отсутствии ключа — `<encrypted>`, а не шифротекст.

Значение, переданное в `dwe secrets set` **в командной строке, попадает в
историю шелла**, как любой другой аргумент. Для чего-то важного используйте
`--stdin` или скрытый промпт.

## Редактирование вывода

Каждое значение, расшифрованное загрузчиком конфига, регистрируется в подсистеме
трассировки, которая печатает `***` вместо него. Регистрация живёт в загрузчике,
потому что конфиг грузят ~60 мест вызова, а корневой хук команды — нет.

Редактирование покрывает три семейства вывода:

- **Диагностические эхо** — эхо команд по `-v` / `--debug` и копии в
  `.dwe/logs` для параллельных шагов пайплайна.
- **Причины пропуска на живом прогоне** — строка `Skipped: <шаг> (when: …)`,
  которую `dwe deploy run` и `dwe reset run` печатают на обычной
  многословности, и её эквивалент для параллельной группы. Причина — только
  для отображения: она никогда не пишется в `.dwe/deploy/state.yml`, поэтому на
  хэш деплоя не влияет.
- **Планы и dry-run** — `dwe deploy plan` (таблица, `--format shell` и
  `--output json`, включая поле `unresolved`), `dwe reset plan` и
  `dwe reset step --dry-run`. Редактирование — свойство самих функций отображения,
  которые собирают эти строки, поэтому оно применяется до того, как значение
  закавычат или встроят в аргумент `--set k=v`, и любая будущая печатающая
  поверхность получает его автоматически.

Поскольку `--format shell` тоже редактируется, **это предпросмотр того, что
будет выполнено, а не скрипт для запуска**: шаг, ссылающийся на секрет, печатает
`***` там, где стоит значение. Редактирование никогда не трогает то, что реально
исполняется — настоящий `dwe reset step <addr>` запускается с настоящим значением.

Три свойства, которые стоит знать:

- **Значения короче 4 рун не редактируются.** Редактирование `"1"` изрешетило бы
  каждую строку вывода. `dwe secrets set` такое значение всё равно сохранит, но
  предупредит в stderr, что оно не будет замаскировано — чтобы предел не
  обнаружился из вставленного в тикет плана.
- **Вывод дочерних процессов не редактируется** (явная не-цель). Команда,
  печатающая собственную конфигурацию, её напечатает.
- **Редактирование — не граница доступа.** `dwe vars get` и `dwe secrets get`
  печатают открытый текст по замыслу — см.
  [`vars.md` → Вывод не маскируется](vars.md#вывод-не-маскируется).

Редактирование — это объединение множеств, живущее в течение процесса, поэтому
параллельные пайплайны и сценарии `dwe test --parallel` видят один согласованный
набор.

## Поведение в контейнере

`dwe secrets` **не входит** в allowlist контейнерных команд. Ни один контейнер
не может сгенерировать, перекеить, экспортировать или импортировать ключ, а
также добавить секрет.

`DWE_AGE_KEY` и `DWE_AGE_KEY_FILE` вычищаются из клиентского окружения на шиме
**и** заново подставляются из собственного окружения демона, поэтому контейнер
не может указать хостовому `dwe` на файл по своему выбору, а хост, работающий с
identity только из переменной окружения, продолжает работать через мост.

**Чтение намеренно не закрыто.** `dwe vars get` из bridged-контейнера и так
доходит до хостового `dwe`, который держит identity, и возвращает открытый текст
— та же экспозиция, которая у контейнера уже есть через его отрендеренный `.env`
и конфиг-файлы. `dwe render config` тоже доступен и расшифровывает на стороне
хоста. Это принятое следствие, а не недосмотр: контейнер, который может прочитать
свой конфиг, может прочитать и свои учётные данные.

## Совместимость с CLI `age`

Здесь нет ничего приватно-форматного. Payload маркера — это base64 бинарного
age-файла с одной строфой X25519:

```bash
# Открыть маркер через CLI age:
dwe secrets get vars.telegram.token                       # способ dwe
echo 'YWdlLWVuY3J5…' | base64 -d | age -d -i ~/.config/dwe/keys/age1….key

# Открыть источник пака:
age -d -i ~/.config/dwe/keys/age1….key creds.json.age
```

Keyfile — обычный age-файл identity, поэтому `age`, `age-keygen -y` и любые
другие age-инструменты с ним работают. Этот аварийный выход — фича: секреты
проекта не зависят от того, установлен ли и работает ли `dwe`.

## JSON-вывод

Каждая подкоманда поддерживает `--output json` (с `--pretty`) и держит stdout
чистым; типизированные ошибки сериализуются в конверт `{"error":{…}}` в stderr.

| Команда | Форма |
|---------|-------|
| `init` | `{"recipient": "age1…", "keyfile": "/…/age1….key"}` |
| `status` | `{"recipient": "age1…", "identity": {"source": "keyfile\|env\|env-file\|", "keyfile": "…", "reason": "…", "error": "…", "hint": "…"}, "markers": [{"layer": "…", "path": "…", "state": "…", "reason": "…"}], "files": [{"file": "…", "state": "…", "reason": "…", "detail": "…"}]}` — у файловой строки `reason` остаётся в фиксированном словаре (`no_identity` / `wrong_identity` / `invalid_identity` / `corrupt` / `stale_key` / `unreadable`), а `detail` несёт свободный текст причины за `unreadable` |
| `set` | `{"path": "vars.…", "file": "workspace/defaults.yml"}` |
| `get` | `{"path": "vars.…", "value": "…"}` |
| `encrypt` / `decrypt` | `{"from": "…", "to": "…"}` |
| `key export` | `{"recipient": "age1…", "identity": "AGE-SECRET-KEY-1…"}` |
| `key import` | `{"recipient": "age1…", "keyfile": "/…/age1….key", "markers_readable": N, "files_readable": N}` — если инвентарь не удалось просканировать, вместо двух счётчиков приходит `report_error` |
| `key list` | `{"keys": [{"recipient": "age1…", "file": "/…/age1….key", "state": "ok\|unreadable\|unparsable\|misnamed", "current": true}]}` |
| `key remove` | `{"recipient": "age1…", "keyfile": "/…/age1….key", "removed": true}` |
| `rekey` | `{"old_recipient": "age1…", "recipient": "age1…", "keyfile": "…", "markers": N, "layers": ["…"], "files": ["…"]}` |

`key list` всегда отдаёт `keys` массивом — `[]`, когда директория пуста или
отсутствует, но никогда `null`. `key remove` всегда сообщает `removed: true`:
отказ — это типизированный конверт ошибки, а не payload, говорящий, что ничего
не произошло.

В `status` `identity` — объект, а не плоская строка: `source` — стабильный
словарь, по которому ветвится скрипт (**прочитанный** источник, заполняется и
при неудаче), `reason` — стабильное слово причины, `error` — человеческая
формулировка, `hint` — как починить. Неудача загрузки identity здесь **данные**,
а не ошибка: сообщить «identity нет, и вот где искали» — это и есть работа
команды.

Типизированные коды ошибок включают `secrets_already_initialized`,
`secrets_no_identity`, `secrets_identity_mismatch`, `secrets_not_encrypted`,
`secrets_path_invalid`, `secrets_file_invalid`, `secrets_value_ambiguous`,
`secrets_value_required`, `secrets_output_exists`, `secrets_raw_stream`,
`secrets_rekey_blocked`, `secrets_import_cancelled` (скрытый запрос
`key import` был отменён), `secrets_write_unsupported`
([отклонённая форма](#подкоманды) — файл не тронут; подсказка называет путь и
что нужно изменить), а для директории ключей — `secrets_key_in_use` (identity
текущего проекта, без `--force`), `secrets_key_unreadable` (keyfile, байты
которого не прочитались, — проверка не смогла это исключить; тоже `--force`),
`secrets_key_not_found`,
`secrets_confirmation_required` (удаление, которое негде подтвердить, без
`--yes`), `secrets_recipient_invalid` (некорректный аргумент `key remove`,
отклонённый до обращения к файловой системе), `secrets_key_list_failed` и
`secrets_key_remove_failed`.

## Чего здесь нет намеренно

Решено не делать:

- **Нет namespace `${secret.*}`.** Секрет — это значение `vars.*`, которое
  просто зашифровано at rest; второй namespace раздвоил бы каждого потребителя.
- **Нет маскирования в `dwe vars`** для *расшифрованных* значений — вывод не
  является границей доступа (см.
  [`vars.md` → Вывод не маскируется](vars.md#вывод-не-маскируется)).
  `<encrypted>` появляется, только когда значение не удалось расшифровать.
- **Нет списков recipient.** Один recipient на проект; скалярное поле позже
  можно вырастить в список, ничего не сломав.
- **Нет поддержки `.age` в паках ide / ai / git** — их выводы отслеживаются.
- **Нет `secrets unset`** — удалите ключ из YAML-файла.
- **Нет гейта на чтение со стороны контейнера** (см.
  [поведение в контейнере](#поведение-в-контейнере)).
- **Нет редактирования вывода дочерних процессов.**
