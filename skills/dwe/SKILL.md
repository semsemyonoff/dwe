# DWE — Dev Workspace Engine

DWE orchestrates Docker development environments on top of compose; it does not replace compose, so edit the compose file freely. Walk up from cwd to `workspace.yml` to find the project root; commands resolve it from any descendant. A root with only `workspace.yml` and commented scaffold files is a fresh init: see `references/populate-init-repo.md`.

## Orient and select

Once per session, run `dwe docs llms-txt --lang en` inside the project: it indexes live services, commands, both builtin registries, template syntax and docs. Read the root `AGENTS.md` if present: it supplies project-specific facts and rules; it wins on project facts, this skill on generic rules. The root file is hand-maintained; a service hub `AGENTS.md` is generated by the `ai` pack, so edit `workspace/templates/ai/<pack>/` and hand off `dwe render ai` instead. Neither has a `CLAUDE.md` beside it: Claude Code reads `AGENTS.md` natively, and a `CLAUDE.md` in or above cwd makes it skip every `AGENTS.md`.

Use live, binary-versioned docs rather than guessing: `dwe docs search <term> --lang en`, `dwe docs show <topic> --lang en`; verify `config/<area>` before editing under `workspace/`. Always use `--lang en` for docs; translations may lag. For parsed data use `--output json`, check the envelope before indexing, and use explicit read forms instead of bare TUI commands. Formats and exceptions: `references/authoring-commands.md` § Output formats.

For tests, lint, formatters, builds, codegen, migrations, seeds, cache/token operations or package scripts, check `dwe commands list --output json` once per session and after `workspace/commands/` changes, before running underlying npm/composer/make/docker commands. A hub may name groups for `dwe commands list <group> --output json`; if none matches, list all commands before falling back. Match IDs, not localized descriptions. Prefer `dwe cmd <id>`, which carries service, workdir, user, env and compose flags; inspect unfamiliar commands with `dwe cmd -i <id> --output json` for arguments and `confirmation:`. For an undeclared one-off use `dwe shell <service> -c '<cmd>'`, never `docker exec` or `docker compose exec`: shell resolves the service and applies its `cli:` block. Further command selection and output details: `references/authoring-commands.md`.

## Permission boundary

The following are reads, safe to run without asking even when reporting errors:

- `status`, `logs`, `validate` (including subcommands and `--stage`), `info`; `deploy plan`, `reset plan`, `deploy state show`, and `deploy eject` / `reset eject` **without `--out`**.
- `snapshot list|current|inspect`, `compose argv <subcommand>` (bare errors), `compose files`, `docker ps|logs|project-name`, `bridge status|logs`, `vars get|list|inspect`, `commands list [group]`, `cmd -i <id>`, `services list`, and `docs show|search|list|llms-txt`.
- `secrets status` and `secrets key list` expose no plaintext or key material. Status exits 0 even when nothing decrypts; `identity.reason` / `identity.hint` identify the fix.
- Bare `render env` without `--out` is host-only and writes nothing, but prints the entire exported secret set: **always scope it**, e.g. `dwe render env | grep -E '^<NAME>='`.
- `test list` is lock-free, without Docker, and includes `cost_profile` in JSON; `test clean --dry-run` is read-only.

`dwe cmd` and `dwe shell` are transports: judge the task, not the verb. Read-only inspection and verification (linters, type checks, check-mode formatters, tests touching nothing stateful) may run without asking. Ask first for migrations, seeds, resets, dependency installs, anything writing outside a build cache, uncertain tasks, or a declared `confirmation:`. Tests reaching the project's database or another stateful service may truncate and re-seed live data: inspect connections and ask first; "run the tests" is not permission to write against the live stack.

**Before any `dwe test run`, MUST read `references/integration-tests.md` § Unattended test gate.** It performs a full clean Docker deploy of a throwaway copy, not a harmless read. Validate first and inspect the scenario's cost profile; shared resources, isolation findings and host steps can require a hard stop. Run unattended only when the exact gate clears and cost is accounted for; otherwise hand the command to the user. Use isolated scenarios when a test needs the stack.

**Mutations are human handoffs, never invoke them yourself:** `init`; `deploy run`, `run`, `stop`, `restart`, destructive `reset run`; `services enable|disable --apply`; `vars set`; renders other than bare `render env`, including `--out` and `config --harvest`; deploy/reset eject `--out` and deploy state `clear|repair`; snapshot create/restore/rollback/remove/pack/unpack; bridge start/stop; docs generate/export/cache clear; `test clean` without `--dry-run`; and `test run` when its gate does not clear. This also applies to mutating tasks carried by `cmd` or `shell`.

`secrets init|set|get|encrypt|decrypt|rekey|key import|export|remove` write layers/keyfiles or print secret material: hand them over. Key import opens a hidden prompt; never ask for identity text to paste, as it would enter the transcript. Do not edit an `<encrypted>` value or `secrets.unresolved` to "fix" it: inspect `dwe secrets status --output json`; missing identity is fixed by user-run `dwe secrets key import` or `DWE_AGE_KEY`. Interactive `dwe run`/`restart`/`deploy` offer import themselves. Plaintext commits the credential; deletion breaks other users.

## Picking the apply command

Edit yml → show the diff → give the exact apply command → wait. **Before selecting an apply command, MUST read `references/pipelines-and-orchestration.md` § 8** (and the reset reference for destructive reset). In particular, per-service deploy requires its own `deploy.yml` and skips final stack up; it is not for a new service. `--force` is not a clean install. Never bypass the boundary through Docker, compose or project scripts, including via `dwe shell`: no `docker compose up/down`, `dwe docker up`, or `dwe compose raw` writes; DWE tracks state and holds locks.

## Rules

Mount the whole service hub rather than just `src/`; the `dir` / `dir_internal` / `work_dir_internal` combination and why it matters are in `references/pipelines-and-orchestration.md` § 9.

Never hand-edit `.env`, `.dwe/**` (including journal, generated secrets, logs and test runs), `workspace/local.yml`, or rendered hub files including hub `AGENTS.md`. Edit the source export rule, var, template or pack and hand off render/deploy. Free-form config belongs under `vars:`, not the strict config root. After `dwe services …` without `--apply`, use `dwe status` rather than guessing pending-op consumers; its banner is authoritative.
